# Phase 4.6.3: Logo State Lifecycle — Context

**Gathered:** 2026-06-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Ciclo de vida completo do estado com logotipo: upload (com input_snapshot e ordenação corrigida de outdated), remoção explícita (preservando proveniência no profile), e restauração de logos anteriores via histórico de assets archived com validação de drift.

**O que esta fase entrega:**
1. Upload de logo com transição transacional do brand profile — BrandDirector executa ANTES da mutação; em caso de sucesso, marca outdated e insere novo synced atomicamente; em caso de falha, profile anterior preservado como fallback
2. Captura de `metadata.input_snapshot` (6 campos sensíveis) em profiles synced para baseline de drift
3. Captura de `metadata.attempt_snapshot` em profiles failed para auditoria
4. Sincronização de `identity_state` e `logo_status` em toda operação (IDENTITY_TO_LOGO_STATUS mapping)
5. Remoção explícita de logo: assets archived, profile synced preservado, active_logo_asset_id preservado, identity_state → text_only
6. GET /logo/history: lista assets archived + profiles associados via FK active_logo_asset_id
7. POST /logo/restore: valida drift (6 campos), dois caminhos (sem drift → reativa; com drift → executa BrandDirector)
8. UI Step 2: 4 cenários visuais (logo ativo OK, logo ativo failed, pós-remove, modal de restore)
9. Isolamento de `brand_colors_chosen` — não recebe `logo_colors_detected`
10. `previous_identity_snapshot` NÃO populado (campo morto, candidato a remoção futura)

</domain>

<decisions>
## Implementation Decisions

### D01: active_logo_asset_id como proveniência (nunca nullado)

- Upload OK: asset.id do novo logo
- Remove: **preservado** (antes era nullado)
- Restore sem drift: asset.id do escolhido
- Restore com drift: asset.id do escolhido
- O estado visual é decidido por: `identity_state === 'logo'` AND exists asset com status='active'

### D02: Compensação controlada (não RPC, não BEGIN/COMMIT)

Algoritmo:
1. Salva ID do profile synced atual
2. Marca synced → outdated
3. Insere novo profile → synced
4. SE INSERT FALHAR → restaura anterior para synced

Ordem outdated→insert exigida pelo índice único `(store_id) WHERE status = 'synced'`. A compensação garante: se insert falhar, restaurar o profile anterior para synced — sem RPC, sem BEGIN/COMMIT. É compensação controlada no handler.

### D03: identity_state como canônico, logo_status como derivado

```
const IDENTITY_TO_LOGO_STATUS = {
  'text_only': 'explicit_none',
  'logo': 'uploaded',
  'visual_signature': 'generated',
};
```

Dual-population: ambos atualizados no mesmo UPDATE. Código novo lê `identity_state`. `logo_status` mantido para backward compat.

### D04: input_snapshot vs attempt_snapshot

- `input_snapshot`: Profiles synced, 6 campos (segment, subsegment, tone_of_voice, name, brand_color, accent_color). Baseline de drift.
- `attempt_snapshot`: Profiles failed, 6 campos. Auditoria.
- Distinção evita poluir semântica de drift.

### D05: Upload flow reordenado

Fases:
1. Pré-análise: upload, archive de assets ativos, geração de variantes, captura input_snapshot
2. BrandDirector ANTES de mutação no profile
3. Pós-análise: sucesso → transação (outdated+insert); falha → identity_state='logo', profile anterior synced como fallback, profile failed com attempt_snapshot

### D06: Remove flow (soft delete)

1. Assets ativos → archived
2. Profile permanece synced (direção visual mantida)
3. active_logo_asset_id preservado (proveniência)
4. identity_state → text_only
5. logo_status → explicit_none (sync)

### D07: GET /logo/history

- Query assets archived (variant_type='original')
- LEFT JOIN profiles via active_logo_asset_id FK
- Ordenado por version DESC
- drift_status computado server-side (comparação de 6 campos)
- Response: { logos: [{ version, asset, profile, created_at, visual_style, safe_color_tokens }] }

### D08: POST /logo/restore

- Aceita { asset_id }
- Valida pertence à store e está archived
- Arquiva assets ativos
- Carrega profile via FK, compara input_snapshot vs store atual

**Sem drift:** profile já synced → NÃO marcar outdated, apenas reativar assets; profile atual outdated, reativar profile escolhido para synced, reativar assets.

**Com drift:** Executar BrandDirector com logo restaurado + dados atuais; marcar atual outdated; criar NOVO profile synced (profile histórico NÃO reativado); reativar assets.

**BrandDirector failure no drift restore:** profile atual permanece synced; profile failed com attempt_snapshot; assets reativados mesmo assim.

### D09: brand_colors_chosen isolation

- `brand_colors_chosen` NÃO é populado com `logo_colors_detected`
- Populado apenas por picker manual de cores
- Correção postergada da 4.6.1

### D10: Matriz de decisão UX (4 cenários Step 2)

| Estado | Drop zone / Preview | Botões visíveis | "Continuar sem logo" | "Logotipos anteriores" |
|--------|-------------------|----------------|---------------------|----------------------|
| Novo (sem store) | Upload vazio | Upload + Assinatura | ✅ | ❌ |
| text_only sem profile | Upload vazio | Upload + Assinatura | ❌ | ❌ |
| text_only com profile | Upload vazio | Upload + Assinatura | ❌ | ✅ Se houver archived |
| logo | Preview ativo | Remover (único) | ❌ | ❌ |

</decisions>

<specifics>
## Specific Ideas

### Fluxo de Upload (corrigido)

```
1. Upload (validação, storage, variantes)
2. Arquiva assets ativos → archived
3. Captura input_snapshot (6 campos)
4. EXECUTA BRANDDIRECTOR
   ├── SUCESSO: transação (outdated→insert) + identity_state='logo'
   └── FALHA: identity_state='logo', profile anterior synced, profile failed com attempt_snapshot
```

### Fluxo de Remove

```
1. Assets → archived
2. Profile synced (preservado)
3. active_logo_asset_id (preservado)
4. identity_state → text_only
5. logo_status → explicit_none
```

### Fluxo de Restore

```
1. GET /logo/history → lista versões archived
2. POST /logo/restore { asset_id }
3. Valida drift (input_snapshot vs store atual)
   ├── SEM DRIFT: reativa assets + profile
   └── COM DRIFT: BrandDirector + novo profile + reativa assets
```

### Nenhuma migration nova

Sincronização identity_state + logo_status sob demanda (sem backfill).
`previous_identity_snapshot` não populado.

### Resolução de accent_color

`brand_colors_chosen[1]` → `safe_color_tokens.accent` → `inferred_accent_color` → `null`

</specifics>

# Plan 01: Retry Endpoint + Frontend Refactor

## Objective

Criar o endpoint dedicado `POST /api/store/[id]/logo/retry-brand-director` para re-execução do BrandDirector no asset ativo quando a análise inicial falha. Refatorar o frontend para consumir o novo endpoint sem `asset_id`.

## Context

O fluxo atual usa indevidamente `POST /logo/restore` como mecanismo de retry, mas o restore rejeita requisições quando `identity_state === 'logo'` (linha 79 do restore route). O novo endpoint substitui esse uso com validação adequada, preservação de `brand_colors_chosen` e `metadata.input_snapshot`, e sequência compensável.

Leia CONTEXT.md e os delta specs antes de implementar.

- src/lib/brand-assets/brand-director.ts — BrandDirectorService.analyze()

- openspec/changes/fase-4-6-3-1-logo-restore-scope-cleanup/specs/logo-retry/spec.md — spec completa
</read_first>

<action>
Criar `src/app/api/store/[id]/logo/retry-brand-director/route.ts` com:

1. Body vazio (sem asset_id — servidor resolve o active original)
2. Validar `identity_state === 'logo'` — HTTP 409 se não
3. Buscar asset original ativo (`variant_type='original'`, `status='active'`) — HTTP 400 se não
4. Buscar profile mais recente, validar: `status='failed'`, `source='logo_analysis'`, `active_logo_asset_id` match — HTTP 400 se não
5. Buscar fallback opcional (profile synced mais recente — pode ser null)
6. Download do buffer do logo do Supabase Storage
7. Executar `BrandDirector.analyze()` com mesmo `storeData` do upload (incluindo `userPrimaryColor`, `userAccentColor`)
</action>

<acceptance_criteria>
- Route existe em `src/app/api/store/[id]/logo/retry-brand-director/route.ts`
- Retorna HTTP 409 se `identity_state !== 'logo'`
- Retorna HTTP 400 se sem asset ativo ou sem perfil failed linkado
- Executa BrandDirector.analyze() com storeData incluindo userPrimaryColor e userAccentColor
</acceptance_criteria>

### Task 02: Implementar sequência compensável

<read_first>
- src/app/api/store/[id]/logo/retry-brand-director/route.ts (task anterior)
- src/app/api/store/[id]/logo/route.ts — POST /logo para referência de compensação
- openspec/changes/fase-4-6-3-1-logo-restore-scope-cleanup/design.md — decisões D01-D04
</read_first>

<action>
Implementar a lógica pós-BrandDirector:

**Sucesso com fallback:**
1. Marcar fallback synced → `outdated`
2. Preservar `brand_colors_chosen` do fallback no novo profile
3. Inserir novo profile `synced` com TODOS os campos do BrandDirector + `metadata.input_snapshot` (7 campos via `buildStoreProfileInputSnapshot(store)`)
4. Se insert falhar → restaurar fallback para `synced`, retornar HTTP 500

**Sucesso sem fallback (primeiro upload):**
1. Inserir novo profile `synced` com `brand_colors_chosen = []`
2. Se insert falhar → retornar HTTP 500

**Falha do BrandDirector:**
1. Não mutar nenhum registro
2. Retornar `{ success: false, error, retry: true }`
</action>

<acceptance_criteria>
- Com fallback: fallback marcado outdated, novo profile synced com brand_colors_chosen preservado
- Sem fallback: novo profile synced com brand_colors_chosen = []
- Insert fail com fallback: fallback restaurado para synced, HTTP 500
- Insert fail sem fallback: HTTP 500
- BrandDirector fail: nenhum profile alterado, retorna `{ success: false, error, retry: true }`
</acceptance_criteria>

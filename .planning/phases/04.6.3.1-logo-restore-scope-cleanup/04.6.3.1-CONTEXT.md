<domain>
## Phase Boundary

Cleanup retroativo do escopo de restore de logotipo implementado na fase 4.6.3. O lifecycle de logo foi simplificado: **excluir = irreversível**. O código de restore (endpoints, componente, types, spec canônica) tornou-se obsoleto e nunca foi removido. Esta fase remove o código morto e substitui o uso indevido do endpoint de restore como retry por um endpoint dedicado.

**O que esta fase entrega:**
1. Novo endpoint `POST /api/store/[id]/logo/retry-brand-director` — re-execução do BrandDirector no asset ativo quando a análise inicial falha
2. Refatoração do `handleRetryBrandDirector` no frontend para consumir o novo endpoint sem `asset_id`
3. Remoção de `POST /logo/restore` (313 linhas) — endpoint de restore
4. Remoção de `GET /logo/history` (92 linhas) — histórico de logos arquivados
5. Remoção de `GET /logo/versions` (31 linhas) — sem caller, dead code
6. Remoção do componente `LogoRestoreModal` (211 linhas)
7. Remoção de types mortos: `LogoHistoryItem`, `LogoRestoreRequest`, `LogoRestoreResponse`, `DriftStatus`
8. Remoção de state morto no formulário: `archivedCount`, `archivedCountLoading`, `fetchArchivedCount`
9. Remoção de `failedLogoAssetId` do state do formulário
10. Remoção de `handleGenerate` + dispatch `path.endsWith('/generate')` em `brand-profile/route.ts`
11. Remoção da spec canônica `openspec/specs/logo-restore/spec.md`
12. Atualização de 5 specs canônicas (logo-upload, store-identity-ui, store-identity-state, identity-state-transitions, store-brand-profile)

<decisions>
## Implementation Decisions

### D01: Endpoint de retry sem `asset_id` no body

O servidor resolve o único asset original ativo (`variant_type = 'original'`, `status = 'active'`) da loja. Isso elimina input manipulável pelo cliente, impede retry em logo arquivado, reduz validações e estado no frontend, e torna explícito que retry nunca restaura assets.

### D02: Pré-condição de perfil `failed`

O endpoint busca o perfil mais recente da loja (sem filtrar status) e valida:
- `status === 'failed'`
- `source === 'logo_analysis'`
- `active_logo_asset_id === asset.id`

Isso impede retry após sucesso (perfil synced não passaria) e garante que o retry só ocorre quando há falha prévia documentada.

### D03: Sequência compensável (não transação atômica)

Supabase não oferece transações entre chamadas independentes. A sequência depende da existência de fallback:

**Com fallback (segundo+ upload):**
1. Marca fallback synced → `outdated`
2. Insere novo profile `synced`
3. Se inserção falhar → restaura fallback para `synced`

**Sem fallback (primeiro upload):**
1. Insere novo profile `synced` diretamente (sem marcação prévia)
2. Se inserção falhar → retorna erro (nada a restaurar)

### D04: Profile `failed` permanece `failed`

O profile `failed` original não vira `outdated`. Permanece como registro de auditoria da tentativa. Só o fallback `synced` vira `outdated` quando substituído.

### D05: `handleGenerate` removido

O `handleGenerate` em `brand-profile/route.ts` duplica o retry com comportamento inferior — sem preservação de `brand_colors_chosen`, sem `metadata.input_snapshot`, e com `brand_colors_chosen = logo_colors_detected` (incorreto). A função é roteada por dispatch interno (`path.endsWith('/generate')`) sem rota Next.js correspondente — é código morto. Remove-se a função e o dispatch.

### D06: Restore de logo removido, VS restore preservado

A remoção de restore de logo não afeta o restore de Visual Signature, que permanece disponível com toda sua lógica de drift detection e reconciliação. As referências nas specs de identity-state e transitions são ajustadas para refletir que apenas VS pode ser restaurado.

### D07: "Logotipos anteriores" removido da UI

A coluna "Logotipos anteriores" desaparece da matriz de decisão UX em todos os estados. Archived logos permanecem no banco mas não são mais acessíveis pela UI.

### D08: Matriz UX pós-cleanup

| Estado | Drop zone / Preview | Botões | "Continuar sem logo" |
|--------|-------------------|--------|---------------------|
| Novo (sem store) | Upload vazio | Upload + Assinatura | ✅ |
| `text_only` sem profile | Upload vazio | Upload + Assinatura | ❌ |
| `text_only` com profile | Upload vazio | Upload + Assinatura | ❌ |
| `logo` com perfil `synced` | Preview ativo | Remover | ❌ |
| `logo` com perfil `failed` | Preview ativo | Remover + Tentar novamente | ❌ |
| `visual_signature` | Assinatura ativa | Alterar / Remover | ❌ |

## Specific Ideas

### Novo Endpoint: POST /api/store/[id]/logo/retry-brand-director

```
POST /api/store/[id]/logo/retry-brand-director
Content-Type: application/json
Body: {} (vazio)

Validações:
  1. Store em identity_state = 'logo' → 409 se não
  2. Asset ativo original (variant_type='original', status='active') → 400 se não
  3. Profile mais recente: status='failed', source='logo_analysis', active_logo_asset_id match → 400 se não
  4. Fallback opcional: profile synced mais recente (pode ser null no primeiro upload)

Sucesso com fallback:
  1. Marca fallback synced → outdated
  2. Preserva brand_colors_chosen do fallback
  3. Insere novo profile synced com ALL BrandDirector output + input_snapshot
  4. Se insert falhar → restaura fallback para synced, retorna 500
  5. Retorna { profile, success: true }

Sucesso sem fallback:
  1. Insere novo profile synced com brand_colors_chosen = []
  2. Se insert falhar → retorna 500
  3. Retorna { profile, success: true }

Falha do BrandDirector:
  1. Nenhum profile alterado
  2. Retorna { success: false, error, retry: true }
```

# Phase 4.6.4: Visual Signature Lifecycle — Context

**Gathered:** 2026-06-19
**Status:** Ready for planning
**Source:** OpenSpec — `openspec/changes/fase-4-6-4-visual-signature-lifecycle/`

<domain>
## Phase Boundary

Ciclo de vida completo da assinatura visual: geração com metadados, aprovação com identity_state sync, rejeição com feedback, alteração, remoção com fallback, restore com validação de drift via `input_snapshot` + `content_used`.

**O que esta fase entrega:**
1. Aprovação seta `identity_state = 'visual_signature'` e `logo_status = 'generated'` na store — corrige UI inconsistente
2. Geração persiste JSON de metadados (`content_used`, `visual_direction`, `intended_palette`) em `metadata.artDirectorOutput` + snapshot dos dados da store em `metadata.input_snapshot`
3. `DELETE /visual-signature` (novo): arquiva signature ativa, transiciona `identity_state` para `text_only`, preserva profile como `synced` fallback
4. `GET /visual-signature` evoluído como histórico — adiciona `approved_at`, `art_direction`, `restore_eligibility` (server-side)
5. `POST /visual-signature/restore` (novo): restaura signature archived como active com validação de drift via `input_snapshot` + `content_used`
6. `POST /logo` recusa upload quando `identity_state = 'visual_signature'` — toda transição passa por `text_only`
7. `POST /logo/restore` recusa quando `identity_state = 'visual_signature'` ou `identity_state = 'logo'` — só permitido em `text_only`
8. Profile reconciliation padronizada: `reconcileProfiles()` centralizada — ao ativar nova identidade, marca incompatíveis como `outdated`; ao remover para `text_only`, preserva anterior como `synced` fallback
9. Propagação de `rejectionContext` da fase `feedback` para `generate()` na fase `review` do modal
10. UI Step 2 reflete `identity_state` como fonte primária com preview VS, "Alterar"/"Remover", histórico separado de logo

**Não escopo desta fase:**
- Arquitetura de prompt 1-passo vs 2-passos — ortogonal ao lifecycle (microfase futura)
- Consumo de cores/visual_elements na geração de campanha — fase futura
- Refinamento do prompt `store-identity-art-director.md` — microfase separada
- Créditos para gerações extras (limite 3) — monetização
- Correção de `brand_colors_chosen` populado com `logo_colors_detected` — 4.6.1 postergada
- Preview refresh pós-aprovação sem reload — UX separada

</domain>

<decisions>
## Implementation Decisions

### D01: Content_used + input_snapshot no metadata da geração

- Após `AiImageGenerator.generate()` bem-sucedido, extrair JSON do `response.output.message` (content_used, visual_direction, intended_palette) e persistir em `metadata.artDirectorOutput`
- `input_snapshot` com 10 campos da store no momento da geração: name, segment, subsegment, tone_of_voice, positioning, short_description, slogan, city, state, brand_color
- Em retry (prompt simplificado sem retorno JSON): `content_used` inferido por heurística conservadora — todos os campos como `true`
- Nenhuma migration nova — `metadata` já é jsonb

### D02: Approve seta identity_state

- `approve/route.ts`: adicionar `UPDATE stores SET identity_state = 'visual_signature', logo_status = 'generated'`
- Ordem: carregar signature → arquivar active anterior → ativar nova → setar identity_state → reconciliar profiles

### D03: DELETE /visual-signature — arquivamento com fallback

- Carrega signature ativa → seta `archived` → `identity_state = 'text_only'`, `logo_status = 'explicit_none'`
- `visual_signature_attempts` preservado (não reseta)
- Brand profile `without_logo` permanece `synced` — fallback intencional de direção visual
- 404 se não houver signature ativa: `{ "error": "Nenhuma assinatura visual ativa para remover." }`

### D04: GET /visual-signature evoluído como histórico

- `approved_at`: reliable apenas para signature atualmente ativa (seu `updated_at`); `null` para archived/never-active
- `art_direction`: de `metadata.artDirectorOutput` ou `null` se indisponível
- `restore_eligibility`: computado server-side comparando `input_snapshot` vs store atual usando `content_used`:
  - `reason: 'ok'` → sem drift, pode restaurar
  - `reason: 'critical_drift'` → drift detectado, `drift_fields` populado
  - `reason: 'missing_metadata'` → sem metadados (pré-feature), bloqueado

### D05: POST /visual-signature/restore com drift validation

- Aceita `{ signature_id: "uuid" }`
- Valida pertence à store, pode estar `archived` ou `active` (se active, no-op)
- Rejeita se `identity_state = 'logo'` — usuário deve remover logo antes
- Drift validation: name/segment sempre críticos; city/state/slogan condicionais a `content_used`
- Se drift: retorna `{ success: false, drift: { critical: true, fields, requires_regeneration: true } }`
- Sem drift: arquiva active atual → ativa escolhida → identity_state sync → reconcilia profiles
- Restore não consome geração
- Se assinatura nunca foi aprovada (sem profile): executa `BrandProfilerWithoutLogoService.generate()`

### D06: POST /logo recusa baseado em identity_state

- Se `identity_state = 'visual_signature'`: retorna 409 com `requires_identity_removal: true`
- Usa `stores.identity_state` como fonte — não status de assets/profiles
- Consistente com regra: toda transição passa por `text_only`

### D07: POST /logo/restore — identity_state validation

- Só permitido quando `identity_state = 'text_only'`
- Se `identity_state = 'visual_signature'`: 409 com `requires_identity_removal: true`
- Se `identity_state = 'logo'`: 409 com `requires_logo_removal: true`

### D08: Profile reconciliation padronizada

- Função compartilhada `reconcileProfiles(storeId, options)` em `src/lib/brand-assets/profile-reconciliation.ts`
- Opções: `activateProfileIds`, `outdatedSources`, `markIncompatibleAsOutdated`, `preserveCurrentAsFallback`
- Ao ativar nova identidade: marcar synced incompatíveis como outdated, depois ativar target
- Ao remover para text_only: profile anterior permanece synced (fallback)
- Substituir lógicas manuais de outdated/synced no approve, POST /logo, DELETE /logo, restore

### D09: Rejection feedback propagation

- `VisualSignatureApprovalModal`: armazenar `rejectionContext` no estado do modal
- Ao gerar nova versão da fase "review" (attempts < 3): passar `rejectionContext` armazenado para `generate-without-logo`
- Se rejeitou sem feedback: rejectionContext = "sem feedback específico", instruir nova direção

### D10: Step 2 UI com identity_state como fonte primária

| identity_state | Preview | Ação principal | Drop zone | "Não tenho logo" | "Continuar sem logo" | Histórico |
|---|---|---|---|---|---|---|
| `text_only` | Direção visual | Enviar logo / Criar assinatura | Sim | Sim / Criar assinatura | Não, se direção já existe | "Assinaturas anteriores", se houver |
| `logo` | Logo ativo | Remover logo | Não | Não | Não | Logos anteriores |
| `visual_signature` | Assinatura ativa | **Alterar / Remover** | **Não** | **Não** | **Não** | **Assinaturas anteriores** |

- Cores (`brand_colors_chosen`) continuam editáveis com VS ativa — não disparam drift nem regeneração
- Novo componente `visual-signature-history-modal.tsx` (separado de `logo-restore-modal.tsx`)

</decisions>

<specifics>
## Specific Ideas

### Fluxo de Geração (generate-without-logo) — atualizado
1. Verifica limite: COUNT total de signatures por store_id, filtrando type IN ('ai_generated', 'automatic_generated')
2. Se já existe draft pendente → marca como 'archived'
3. Captura rejection_feedback se houver (opcional)
4. Executa StoreIdentityArtDirectorService.generate():
   - Extrai JSON do response.output.message: { content_used, visual_direction, intended_palette, ... }
   - content_used → metadata.artDirectorOutput
   - Snapshot da store → metadata.input_snapshot
5. Retry: content_used inferido por heurística (tudo true)
6. Cria store_visual_signatures com status='draft'
7. Incrementa visual_signature_attempts

### Fluxo de Aprovação (approve) — corrigido
1. Carrega signature pertencente à store
2. Arquiva active anterior (se houver)
3. Seta escolhida como 'active'
4. **NOVO:** Atualiza stores: identity_state='visual_signature', logo_status='generated'
5. Reusa brand profile existente ou executa BrandProfilerWithoutLogoService
6. Ao reativar profile, marca outros synced como outdated antes de ativar o target

### Fluxo de Remoção
DELETE → carrega active → archived → identity_state='text_only' → logo_status='explicit_none' → attempts preservado → profile synced (fallback)

### Fluxo de Restore
POST { signature_id } → valida pertence → valida identity_state (rejeita se 'logo') → valida drift (input_snapshot vs current + content_used) → sem drift: arquiva active → ativa → sync → reconcilia; sem profile: executa BrandProfilerWithoutLogoService

### Fluxo "Alterar" (UI)
User clica "Alterar" → generate-without-logo (nova draft) → abre VisualSignatureApprovalModal → se aprova: active anterior → archived, nova → active; se fecha: draft preservada, original permanece

### Fluxo de cores com VS ativa
brand_colors_chosen continua editável. Cores não invalidam assinatura. Não disparam drift. São contexto de campanha, não da assinatura.

</specifics>

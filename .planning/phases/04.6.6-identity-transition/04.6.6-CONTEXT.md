# Phase 4.6.6: Identity Transition — Context

**Gathered:** 2026-06-23
**Status:** Ready for planning
**Source:** OpenSpec — `openspec/changes/fase-4-6-6-identity-transition/`

<domain>
## Phase Boundary

Corrigir e simplificar o fluxo de transição de identidade da loja, usando `text_only` como hub obrigatório entre `logo` e `visual_signature`. Alinhar as ações da UI ao estado vigente.

**O que esta fase entrega:**
1. **Orquestrador central** (`src/lib/identity-transitions.ts`): valida, executa e confirma as 4 transições permitidas (`text_only → logo`, `logo → text_only`, `text_only → visual_signature`, `visual_signature → text_only`)
2. **Validação de estado nas APIs**: `POST /logo`, `DELETE /logo`, `POST /visual-signature/approve`, `DELETE /visual-signature`, `POST /visual-signature/restore` — todas usam o orquestrador para garantir transições seguras
3. **UI state-action matrix**: `logo` exibe apenas "Remover logo"; `visual_signature` exibe apenas "Remover assinatura visual"; `text_only` exibe ações para enviar logo ou gerar/gerenciar VS
4. **"Continuar sem logo" substituído**: link removido, substituído por card informativo no Step 2
5. **Aviso pré-remoção de logo**: diálogo de confirmação antes de chamar `DELETE /logo`
6. **Invariantes I1–I6**: `text_only` sem asset ativo (mas pode ter profile `synced`), `logo` exige logo ativo, `VS` exige VS ativa, sem troca direta, falha preserva estado, persistência crítica antes da transição

**Não escopo:**
- Cores, `manual_color_override`, paleta manual
- Realinhamento/drift/revalidação de direção visual
- Feedback para gerar nova direção visual sob demanda
- Idempotência global
- Histórico/reaplicação/gerenciamento de versões de logo
- Drift, revalidação ou realinhamento de VS antiga
- Troca direta `logo ↔ visual_signature`
- Troca direta `visual_signature v1 → v2`
- Lifecycle avançado de VS (arquivamento inteligente, reuso automático)

</domain>

<decisions>
## Implementation Decisions

### D0: `identity_state` representa asset visual ativo, não direção visual

`text_only` significa ausência de logo e de VS ativos, mas a loja pode manter um brand profile `synced` como direção visual vigente, inclusive herdado de logo/VS removidos. Isso evita confusões recorrentes de fases anteriores.

### D1: Orquestrador central de transições

Criar `src/lib/identity-transitions.ts` com orquestrador que valida `identity_state`, executa persistência crítica, atualiza estado e compensa em falha. Ele não reimplementa BrandDirector, geração de VS, análise de logo, cores ou lifecycle avançado.

Lifecycle da transição:
1. Validar `identity_state` atual (rejeitar se incompatível — I4)
2. Executar persistência crítica (arquivar asset anterior nas remoções; ativar novo asset nas ativações)
3. Só então atualizar `identity_state` (I6)
4. Se falhar antes da persistência crítica, manter estado anterior (I5)
5. Se persistência crítica concluir mas `identity_state` falhar, executar compensação ou retornar erro registrando estado parcial — UI nunca declara sucesso

### D2: Dupla validação (API + UI)

API rejeita transição se `identity_state` não corresponder; UI só exibe ações compatíveis. O usuário nunca deve ver um botão que leva a erro 409.

### D3: UI state-action matrix via hook

Hook `useIdentityActions(identityState, storeData)` retorna ações disponíveis:

| `identity_state` | Ações de identidade exibidas |
|---|---|
| `text_only` | "Enviar logotipo", "Gerar assinatura visual" (ou "Gerenciar assinatura visual" se VS existe) |
| `logo` | "Remover logo" (única ação de identidade) |
| `visual_signature` | "Remover assinatura visual" (única ação de identidade) |

### D4: "Continuar sem logo" substituído por card

Link removido do Step 2. Substituído por card informativo exibido em `text_only`: "Sem logo por enquanto? Você pode escolher as cores da loja, se quiser, e clicar em Salvar. O Vendeo vai gerar uma direção visual usando os dados básicos da loja."

### D5: Remoção de logo sem histórico

`DELETE /logo` arquiva o logo ativo, sem oferecer reaplicação na UI. Aviso pré-remoção exibido pela UI (não pela API): "Ao remover o logo, ele não ficará disponível para reaplicação pela interface. Você poderá enviar o arquivo novamente quando quiser."

### D6: Visual signature restore limitado à validação de transição

`POST /visual-signature/restore` permite apenas quando `identity_state = text_only`. Bloqueia se `identity_state = logo` ou `visual_signature`. Sem drift, revalidação ou realinhamento de VS antiga.

### D7: Upload de logo só de text_only

`POST /logo` bloqueado se `identity_state = logo` (409: remova o logo ativo primeiro) ou `visual_signature` (409: remova a VS primeiro). Permitido apenas de `text_only`. Validação acontece antes de ativar asset ou atualizar store.

</decisions>

<specifics>
## Specific Ideas

### Regras de transição (text_only é hub)
```
text_only → logo           (enviar logo)
logo → text_only           (remover logo)
text_only → VS             (gerar/aplicar VS)
VS → text_only             (remover VS)
```

Todas as demais transições são bloqueadas:
- `logo → VS` — deve remover logo antes
- `VS → logo` — deve remover VS antes
- `logo → logo` — substituição direta bloqueada, deve remover antes
- `VS → VS` — substituição direta bloqueada nesta fase

# Phase 4.6.7: User Color Preferences Persistence — Context

**Gathered:** 2026-06-25
**Status:** Ready for planning
**Source:** OpenSpec — `openspec/changes/fase-4-6-7-user-color-preferences-persistence/`

<domain>
## Phase Boundary

Estabelecer `brand_colors_chosen` como fonte da verdade exclusiva para escolhas manuais de cor pelo usuário, com suporte a escolha parcial (null), deprecação de `manual_color_override` em todas as camadas, e ação "Voltar para cores sugeridas".

**O que esta fase entrega:**
1. **Schema**: `brand_colors_chosen` muda de `string[]` para `Array<string | null>` — null em qualquer posição significa "usuário não escolheu esta cor"
2. **PATCH brand-profile**: Aceita `Array<string | null>` com validação por posição; não escreve mais `manual_color_override`; `{ colors: [] }` faz reset
3. **Text-only inference**: Aceita `userChosenColors` opcional no body; preserva escolha existente ou persiste recebido; `manualColorOverride` ignorado
4. **Realinhamento**: Preserva `brand_colors_chosen` do profile anterior; não popula com `safe_color_tokens`
5. **Logo upload**: Preserva `brand_colors_chosen` existente; não zera incondicionalmente; não consulta `manual_color_override`
6. **Remoção de logo**: Não limpa `brand_colors_chosen` (escolha de cor independente do logo)
7. **VS approval**: Condição de preservação via `brand_colors_chosen` em vez de `manual_color_override.enabled`
8. **UI — estado local**: `brandColorsChosen` migra para `Array<string | null>`; save bifurca entre PATCH (com profile) e estado local (sem profile)
9. **UI — hidratação**: Color pickers respeitam null positions; `[]` exibe `safe_color_tokens` como fallback
10. **UI — Voltar para cores sugeridas**: Botão discreto visível apenas com escolha manual ativa; reset via PATCH ou estado local
11. **Deprecação**: `manual_color_override` não é mais escrito por nenhum fluxo novo; readers substituídos por verificação direta de `brand_colors_chosen`

**Não escopo:**
- Alterar prompt de campanha, drift detection, logo processing, VS generation, ou creative direction
- Remover campos deprecated dos schemas do Supabase (migration futura)
- Criar fluxo "usar sempre estas cores"
- Backfill de registros antigos
- Migration de dados — JSONB aceita null naturalmente

</domain>

<decisions>
## Implementation Decisions

### D1 — `brand_colors_chosen` passa para `Array<string | null>`

Mudar o tipo em `BrandProfileRecord`, `BrandProfileSnapshot`, `CreateBrandProfileInput` e estado do formulário de `string[]` para `Array<string | null>`. Estados válidos: `[]` (sem escolha), `[hex, null]` (parcial), `[null, hex]` (parcial), `[hex, hex]` (completo).

### D2 — Escolha manual derivada de `brand_colors_chosen`, não de `manual_color_override`

`hasUserChosenColors = brand_colors_chosen.some(c => c !== null && /^#[0-9A-Fa-f]{6}$/.test(c))`. Nenhum campo auxiliar é fonte de verdade para determinar se há escolha manual ativa.

### D3 — PATCH aceita `null` e não escreve `manual_color_override`

Body aceita `{ colors: Array<string | null> }` com validação por posição (hex válido ou null). Para de escrever `manual_color_override` no brand profile e `stores.manual_color_override`. Mantém exigência de synced profile existente (404 se não houver).

### D4 — "Voltar para cores sugeridas" via PATCH com `{ colors: [] }`

Reutiliza PATCH com `{ colors: [] }` para limpar escolha manual. Botão discreto visível apenas quando `hasUserChosenColors === true`. Reset não regenera assets visuais.

### D5 — Fluxos automáticos preservam `brand_colors_chosen`

Logo upload, VS approval, realinhamento e text-only inference preservam `brand_colors_chosen` existente quando há escolha manual. Nenhum fluxo automático gera valores para `brand_colors_chosen`. Text-only inference é exceção: persiste `userChosenColors` recebidos na requisição para loja nova.

### D6 — Remoção de logo não limpa `brand_colors_chosen`

`handleRemoveLogo` deixa de chamar `setBrandColorsChosen([])`. Escolha manual de cores é independente do estado do logotipo.

### D7 — Color picker persiste par canônico

Ao alterar qualquer picker, o sistema lê ambos os campos: campo vazio ou placeholder `#RRGGBB` → `null`; HEX válido → valor. Array montado como `[primaryOuNull, accentOuNull]`. Se ambos null → `[]`. Persistência via PATCH em tempo real (se profile existe) ou estado local (se não existe).

</decisions>

<specifics>
## Specific Ideas

### Fluxo de dados — escolha manual de cores
```
User altera color picker
  → onChange (nativo) ou onBlur (texto)
    → Ler par canônico [primaryOuNull, accentOuNull]
      → Se existe synced profile: PATCH /api/store/[id]/brand-profile { colors: [...] }
      → Se não existe: manter em estado local brandColorsChosen
        → No save/text-only inference: enviar como userChosenColors
```

### Fluxo de dados — Voltar para cores sugeridas
```
User clica "Voltar para cores sugeridas"
  → Se existe synced profile: PATCH { colors: [] }
  → Se não existe: brandColorsChosen local = []
  → Pickers exibem safe_color_tokens ou fallback
  → Nenhum asset visual alterado
```

### Fluxos automáticos — preservação
```
Logo upload / VS approval / Realinhamento:
  1. Ler profile anterior
  2. Se brand_colors_chosen tem ao menos 1 HEX válido → preservar
  3. Senão → brand_colors_chosen = []
  4. manual_color_override NÃO consultado
```

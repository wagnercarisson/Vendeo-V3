    The route must follow this exact flow:

    1. **Parse JSON body** — try/catch `request.json()`. On failure (SyntaxError or similar), return:
       `NextResponse.json({ error: { message: "Corpo da requisição inválido" } }, { status: 400 })`

    2. **Validate input with safeParse** — `CampaignGenerationInputSchema.safeParse(body)`. On failure:
       `NextResponse.json({ error: { message: "Dados de entrada inválidos para geração de campanha", details: parsed.error.flatten().fieldErrors } }, { status: 400 })`
       Include field-level details for validation_error (better DX).

    3. **Select provider** — Call `createDefaultProvider()` from service.ts. This always returns MockProvider in 3.1.

    4. **Instantiate service** — `new CampaignIntelligenceService(provider)`

    5. **Call service.generate()** — Await result.

    6. **Map result to HTTP response**:
       - `result.success === true` → `NextResponse.json(result.data, { status: 200 })`
       - `result.code === "provider_failure"` → `NextResponse.json({ error: result.error }, { status: 502 })`
       - `result.code === "invalid_output"` → `NextResponse.json({ error: result.error }, { status: 500 })`

    Imports:
    - `import { NextRequest, NextResponse } from "next/server"`
    - `import { CampaignGenerationInputSchema } from "@/lib/campaign-intelligence/schema"`
    - `import { CampaignIntelligenceService, createDefaultProvider } from "@/lib/campaign-intelligence/service"`
    - Use `@/` path aliases (matching existing store route convention)

    Constraints enforced by the design:
    - NEVER access `process.env.OPENAI_API_KEY` in the route — provider selection is encapsulated in createDefaultProvider
    - NEVER forward raw provider output or error details — the service returns sanitized error objects
    - Route imports ONLY from schema.ts and service.ts — no direct provider imports
    - Route is thin: parse → validate → call service → map response. No business logic.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP Request → Next.js route | Untrusted client input enters the system here — first line of defense |
| Route → Service | Validated CampaignGenerationInput crosses into business logic — already validated by Zod safeParse |
| Service → HTTP Response | Sanitized CampaignSpec or error object returned to client — all raw data already stripped |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3.1-07 | Spoofing | route.ts JSON body parsing | mitigate | try/catch on request.json() catches malformed bodies, returns 400 before any processing |
| T-3.1-08 | Information Disclosure | route.ts error responses | mitigate | Service returns sanitized error objects; route maps codes to status (502/500) without adding raw data. No process.env, stack traces, or provider internals in responses |
| T-3.1-09 | Tampering | route.ts error status mapping | mitigate | Explicit switch/case on result.code: provider_failure → 502, invalid_output → 500; no fallthrough to uncontrolled status codes |
</threat_model>

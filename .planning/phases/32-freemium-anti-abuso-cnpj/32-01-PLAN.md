    **`src/lib/cnpj/validate.ts`** (per spec scenarios):
    - `validateCnpj(raw: string): CnpjOutput | Error`
    - Passo 1: Normaliza via normalizeCnpj
    - Passo 2: Valida comprimento === 14, senão `Error("CNPJ deve ter 14 dígitos")`
    - Passo 3: Valida apenas dígitos via regex `/^\d{14}$/`
    - Passo 4: Rejeita sequências conhecidas: array `["00000000000000", "11111111111111", "22222222222222", ... "99999999999999"]`
    - Passo 5: Valida dígitos verificadores (algoritmo oficial do CNPJ):
      ```
      // Primeiro dígito: pesos [5,4,3,2,9,8,7,6,5,4,3,2]
      // Soma = ∑ (digito[i] * peso[i])
      // Resto = soma % 11
      // Se resto < 2 → digito = 0, senão digito = 11 - resto
      // Segundo dígito: pesos [6,5,4,3,2,9,8,7,6,5,4,3,2]
      ```
    - Se inválido: `Error("CNPJ inválido")`

    **`src/lib/cnpj/hash.ts`** (per D1):
    - `hashCnpjRoot(root: string): string`
    - Lê `process.env.CNPJ_PEPPER`
    - Usa `crypto.createHmac('sha256', pepper).update(root).digest('hex')`
    - Retorna hex string de 64 caracteres
    - Documentar: "USO RESTRITO — em produção, o hash é calculado dentro da RPC (service_role). Esta função é para testes e contexto de servidor."

    **`src/lib/cnpj/mask.ts`** (per D2):
    - `maskCnpj(normalized: string): string`
    - Recebe 14 dígitos
    - Retorna `"**.***.***/" + sufixo(8,12) + "-**"`
    - Onde sufixo são os dígitos 8-11 (índices 8 a 11, 0-indexed), preservados para identificar estabelecimento
    - Ex: `"12345678000190"` → `"**.***.***/0001-**"`
    - Valida que input tem 14 dígitos, senão retorna string original

    **`src/lib/cnpj/similarity.ts`** (per D5):
    - `compareBusinessName(name: string, razaoSocial: string, nomeFantasia?: string): CnpjValidationScore`
    - Implementar Levenshtein distance (algoritmo iterativo O(n*m))
    - `similarity(a, b) = 1 - (distance / max(len(a), len(b)))`
    - Calcular score entre name e razaoSocial
    - Se nomeFantasia presente, calcular também e usar o melhor
    - Retornar CnpjValidationScore com label:
      - `bestScore >= 0.8` → `'match'`
      - `bestScore >= 0.4` → `'partial'`
      - `bestScore < 0.4` → `'mismatch'`
    - NUNCA lançar erro — validação cadastral é score, não bloqueio (per D5)
    - Comparações case-insensitive (toLowerCase antes)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | CNPJ raw trafega na requisição POST /api/store |
| API→RPC (service_role) | cnpj_normalized + cnpj_root_hash (pré-calculado pela rota) passados como parâmetros |
| DB→log | cnpj_root_hash indexado; cnpj_normalized como dado sensível com RLS |
| env→hash | CNPJ_PEPPER lido de `process.env` na rota server-side, nunca no código ou banco |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-01 | Spoofing | hashCnpjRoot() | mitigate | HMAC-SHA256 com pepper server-side (`process.env.CNPJ_PEPPER`). Rota server-side calcula root_hash e passa para RPC |
| T-32-02 | Information Disclosure | stores.cnpj_normalized | mitigate | Partial unique index + RLS. CNPJ nunca exposto cru em UI, API response ou logs |
| T-32-03 | Tampering | create_store_with_cnpj RPC | mitigate | service_role only. RPC aceita root_hash mas apenas de caller autenticado (supabaseAdmin). Validação dupla: rota valida CNPJ antes, RPC armazena |
| T-32-04 | Removed | get_cnpj_pepper() | removed | Abordagem substituída: rota server-side calcula root_hash com `process.env.CNPJ_PEPPER`. Sem `current_setting` no PostgreSQL |
| T-32-05 | Repudiation | freemium_entitlements | mitigate | Append-only com created_at, store_id ON DELETE SET NULL (histórico permanente) |
| T-32-SC | Tampering | npm install (crypto) | accept | crypto é built-in Node.js, nenhum pacote externo instalado |
</threat_model>

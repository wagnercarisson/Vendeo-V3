# Phase 4.3.2: Creative Direction & Context Awareness - Context

**Gathered:** 2026-05-29
**Status:** Ready for planning
**Source:** OpenSpec change `phase-432-creative-direction-context-awareness`

<domain>
## Phase Boundary

Extend the Phase 4.3.1 generation pipeline (already validated) with:

1. **Product category inference** during input validation — no extra API call, reuses existing vision model
2. **Contextual creative direction** — `campaign-image-director.md` gains sections for persona, category awareness, commercial repertoire, validation summary
3. **Validation-to-review alignment** — `ImageReviewService` receives `validationContext`; `applyValidationContextToReviewResult()` filters only user-approved conflicts post-parse
4. **Sanitized technical events** — pipeline emits real `detail` metadata per phase for "Detalhes técnicos" panel
5. **Zero database changes** — every requirement is in-memory/configuration only
</domain>

<decisions>
## Implementation Decisions

### Decision 1: Category inference extends existing InputValidationService
- `campaign-input-visual-check.md` prompt adds `inferredCategory` field to JSON response
- `InputValidationResult` type gains optional `inferredCategory?: string`
- `InputValidationService.parseResult()` extracts `inferredCategory` from model response
- No separate API call — vision model already analyzes the image
- `GenerateImageRequest` gains optional `inferredCategory?: string` propagated from validation

### Decision 2: CreativeBrief as prompt variables (no new class)
- `ImageGenerationService.buildPromptVariables()` extended with:
  - `creativePersona` — `"Você é um diretor de marketing especializado em {segment label}."`
  - `inferredCategory` — product category (inferred or store segment fallback)
  - `hasCategoryConflict` — `"sim"` / `"nao"` based on `isSameCategory()` comparison
  - `categoryConflictDirective` — conditional directive (empty when no conflict)
  - `commercialRepertoire` — output of `buildCommercialRepertoire(body)`
  - `inputValidationSummary` — output of `buildValidationSummary(body, effectiveProductName)`
- `campaign-image-director.md` gains 3 new sections (preserving all existing content)

### Decision 3: ValidationContext type for review alignment
- Define `ValidationContext` interface with:
  - `inputCorrection?` — `{ field: "productName"; from: string; to: string; reason: string }`
  - `allowedConflicts?` — `Array<{ type: "product_image_conflict" | "product_image_low_confidence"; userAction: "user_confirmed_continue" | "accepted_suggestion" }>`
  - `overrides?` — `{ productImageCheck?: "user_confirmed_continue" }`
- `generated_product_mismatch` NEVER appears in allowedConflicts
- Export from `image-review-service.ts` alongside `ImageReviewInput`
- `ImageReviewInput` gains optional `validationContext?: ValidationContext`
- `ImageReviewService` receives `validationContext` only for prompt rendering — NO internal filtering
- `campaign-image-reviewer.md` gains optional "Contexto de Validação" section

### Decision 4: applyValidationContextToReviewResult() as explicit post-parse step
- Pure function — not part of ImageReviewService
- Called in `ImageGenerationService.generateImage()` immediately after `await this.imageReview.review()`
- Only removes `product_image_conflict` and `product_image_low_confidence` when user confirmed override
- Never removes: `wrong_price`, `wrong_store_name`, `wrong_product_name`, `generated_product_mismatch`, `illegible_text`, `insufficient_image`, `wrong_cta`, `bad_composition`, `invented_badge`, `distorted_product`, `empty_review`, `review_low_confidence`
- Recalculates `passed`/`failureType` after filtering

### Decision 5: Sanitized technical detail events in pipeline
- Pipeline emits `detail` at: `input_validation`, `prompt_assembly`, `image_generation` (each attempt), `quality_review`, `done`
- Details are real metadata strings — safe-by-construction
- `GenerationProgress` already applies `sanitizeDetail()` as defense-in-depth
- Pipeline is source of detail events, not UI

### Decision 6: isSameCategory() uses mapped groups, not string comparison
- `CATEGORY_TO_SEGMENT_GROUP: Record<string, string[]>` mapping
- Conservative — unknown categories default to `hasCategoryConflict: false`
- Fallback when inferredCategory missing: use storeSegment, no conflict
- Implemented as private method or utility function

</decisions>

# Phase 4.4.1: Existing Logo & Store Brand Direction Foundation — Context

**Gathered:** 2026-06-02
**Status:** Ready for planning
**Source:** OpenSpec change artifacts (phase-4-4-1-existing-logo-store-brand-direction-foundation)

<domain>
## Phase Boundary

Implementar a fundação de identidade visual persistida para lojas **com logotipo existente**, incluindo upload de logo com validação, versionamento de assets, geração de variantes técnicas via sharp, análise pelo Store Brand Director (LLM), persistência de brand profile estruturado e integração mínima na geração de campanhas.

Isso permite que lojistas com logo enviem sua marca ao Vendeo, resultando em campanhas com identidade visual real da loja — cores reais, logo aplicado, direção de marca — em vez de peças genéricas baseadas em fallback por segmento.

</domain>

<decisions>
## Implementation Decisions

### D-01: Storage — bucket `store-brand-assets` dedicado
- Bucket `store-brand-assets` com path: `{store_id}/{variant_type}/{uuid}.{ext}`
- Bucket dedicado evita misturar com visual-signatures ou outros assets
- Políticas: public read SELECT, service_role INSERT; CORS configurado para domínio da app

### D-02: Database — tabela `store_brand_assets`
- Cada asset (original + cada variante técnica) é um registro independente
- Variantes apontam para o original via `parent_asset_id` (self-FK)
- Partial unique index: `(store_id, asset_type, variant_type) WHERE status = 'active'`
- `storage_path` nullable — pode ser null quando `status = 'failed'`; obrigatório para `active` e `archived`
- CHECK: status IN ('active', 'archived', 'failed')
- CHECK: variant_type IN ('original', 'normalized', 'on_light', 'on_dark', 'square_safe', 'horizontal_safe')
- Versionamento incremental: cada upload incrementa version; anterior vai para archived

### D-03: Database — tabela `store_brand_profiles`
- FK `active_logo_asset_id` → `store_brand_assets(id)`
- Partial unique index: `(store_id) WHERE status = 'synced'`
- CHECK: status IN ('processing', 'synced', 'outdated', 'failed', 'archived')
- Ciclo de vida V1: upload → análise IA → profile criado diretamente como `synced` ou `failed`
- `processing` reservado para versão futura com fila/job durável — NÃO usado nesta V1
- Novo upload → profile anterior vai para `outdated`
- Lojista altera cores → profile atualizado in-place (mesmo active)
- Soft delete do logo → profile vai para `archived`

### D-04: Database — novos campos em `stores`
- `subsegment` (text, nullable), `tone_of_voice` (text, nullable), `positioning` (text, nullable), `short_description` (text, nullable), `slogan` (text, nullable)
- `subsegment`: campo opcional simples. Sem matriz complexa por segmento nesta fase.

### D-05: Validação em cadeia no upload
1. Extensão: .png, .jpg, .jpeg, .webp — rejeitar .svg
2. MIME real: validar file.type no client + file-type/sharp no server
3. Tamanho: max 5MB
4. Dimensões mínimas: 200x200px (via sharp)
5. Integridade: sharp verifica se arquivo não está corrompido
6. Erro unificado: "Formatos aceitos: PNG, JPG ou WEBP."

### D-06: Geração de variantes técnicas via sharp
| Variante | Técnica |
|----------|---------|
| original | Cópia exata (sem alteração) |
| normalized | Redimensionar para canvas 500x500 com fundo transparente, preservando aspect ratio |
| on_light | Normalized + overlay fundo branco #FFFFFF |
| on_dark | Normalized + overlay fundo escuro #1A1A2E |
| square_safe | Normalized centralizado em canvas quadrado 500x500 |
| horizontal_safe | Normalized em canvas horizontal 800x300 |
- Se variante falhar: status `failed` com metadata do erro. Não bloquear as demais.
- SVG bloqueado com mensagem: "Formatos aceitos: PNG, JPG ou WEBP."

### D-07: Store Brand Director — análise IA inline (V1)
- Processamento inline na mesma requisição HTTP (sem fila/job)
- Prompt: `prompts/store-brand-director-with-logo.md`
- LLM recebe logo image + store data, retorna JSON estruturado
- Profile criado diretamente como `synced` (sucesso) ou `failed` (erro)
- LLM nunca redesenha, recria, recolor ou altera criativamente o logo
- Logo é preservado como enviado — variantes são adaptações técnicas de canvas apenas

### D-08: API endpoints
- `POST /api/store/[id]/logo` — upload com processamento inline completo
- `GET /api/store/[id]/logo` — dados do logo ativo (original + variantes)
- `GET /api/store/[id]/logo/versions` — histórico de versões
- `DELETE /api/store/[id]/logo` — soft delete
- `GET /api/store/[id]/brand-profile` — brand profile ativo
- `POST /api/store/[id]/brand-profile/generate` — regenerar profile via IA
- `PATCH /api/store/[id]/brand-profile/colors` — atualizar cores escolhidas
- `POST /api/store/[id]/brand-profile/archive` — arquivar profile
- `PATCH /api/store/[id]` — estendido para novos campos

### D-09: Integração com campanha — brand profile como contexto direcional
- `CreativeBrief` assembly: verificar brand profile ativo (status=synced)
- Injetar campaign_guidelines, campaign_brief, brand_personality, visual_style, visual_tone, brand_colors_chosen como variáveis de contexto no prompt do Campaign Director
- Contexto é direcional, não mandatório — diretor de campanha mantém julgamento criativo
- Quando não há profile ativo: campos vazios, fallback por segmento inalterado
- Renderer: brand_colors_chosen > safe_color_tokens > store.brand_color > segment fallback
- Logo variant selection: on_dark (tema escuro) → original → normalized → visual signature → store name text

### D-10: Pré-resolução de brand assets em StoreIdentitySnapshot
- Brand assets resolvidos no snapshot/contexto ANTES da renderização
- Não fazer chamada assíncrona ao banco dentro de `resolveStoreIdentity` ou renderer
- `StoreIdentitySnapshot` enriquecido com brand profile + logo variants no momento da montagem do CreativeBrief

### D-11: UI — store-identity page
- Seção de upload drag-and-drop ou clique
- Preview circular do logo após upload
- Status simples: "Enviando...", "Processando...", "Pronto"
- Seletor de cores com paleta sugerida das cores detectadas (logo_colors_detected)
- Lojista pode alterar cores livremente — sem alerta de divergência
- Variantes técnicas NÃO exibidas na UI
- Novos campos: subsegment (text), tone_of_voice (select), positioning (text), short_description (textarea), slogan (text) — todos opcionais

### D-12: Resolução de identidade visual — prioridade atualizada
1. `store_brand_assets` (logo ativo) — prioridade máxima, suprime oferta de assinatura visual
2. Visual signature ativa (existente de fase anterior)
3. Fallback textual (nome da loja)

### D-13: Ordem de migrações (rígida)
1. `store_brand_assets` — antes de `store_brand_profiles` (profiles tem FK → assets)
2. `store_brand_profiles` — depois de assets
3. Adicionar campos em `stores` — depois de profiles (independente, mas por clareza)

### D-14: Operações atômicas em upload
- Antes de inserir novos assets ativos: arquivar assets ativos anteriores + marcar profile anterior como outdated
- Isso evita violação do partial unique index `(store_id, asset_type, variant_type) WHERE status = 'active'`
- Agrupar operações críticas de banco em transação ou fluxo de rollback controlado
- Storage (upload de arquivos) não participa da transação Postgres — considerar rollback manual se storage falhar após DB insert

### D-15: Non-goals (escopo fechado)
- Upload de SVG (bloqueado na V3 v1)
- Upload de ícone (fora da V3 v1)
- Geração/recriação/redesign/coloração criativa do logo
- Loja sem logo (fase futura 4.4.2)
- Editor de logo ou assinatura visual sem logo
- Exposição de variantes técnicas ou análise técnica ao lojista na UI
- Tela de restauração de logo antigo
- Modal de conflito entre cor detectada e cor escolhida
- Geração de assinatura visual (store-visual-signature) — esta fase apenas resolve prioridade

</decisions>

<specifics>
## Specific Requirements

1. **Database Migrations (ordem rígida):** store_brand_assets → store_brand_profiles → stores (add columns)
2. **Storage Setup:** bucket `store-brand-assets` with public read, service_role write, CORS
3. **Image Processing:** install sharp, create `src/lib/image-processing.ts` with validateImage, getImageDimensions, checkImageIntegrity, variant generation functions
4. **Logo Upload API:** `POST /api/store/[id]/logo` — multipart, validation inline, variant generation, Store Brand Director analysis, all synchronous
5. **Logo Query APIs:** GET logo, GET versions, DELETE soft delete
6. **Brand Profile APIs:** GET active, POST generate/regenerate, PATCH colors, POST archive
7. **Store API Extension:** PATCH /api/store/[id] com novos campos
8. **Store Brand Director Prompt:** `prompts/store-brand-director-with-logo.md`
9. **AI Integration:** LLM call with image + store data, parse structured JSON response
10. **Store Identity Resolution:** enriquecer StoreIdentitySnapshot com brand profile, pré-resolver antes da renderização
11. **Campaign Integration:** CreativeBrief com brand profile context, renderer com cores do profile, logo variant selection
12. **UI:** upload de logo com validação client-side, preview circular, seletor de cores com sugestões, campos de direção de marketing
13. **Visual Signature Priority:** logo ativo suprime oferta de assinatura visual
14. **Validation:** typecheck, lint, build + 11 cenários de teste manual especificados

</specifics>

# Phase 04.6.2: Visual Direction Drift Detection — Context

**Gathered:** 2026-06-13
**Status:** Ready for planning
**Source:** OpenSpec design artifacts (fase-4-6-2-visual-direction-drift-detection)

## Domain

### Phase Boundary

Detect when store sensitive fields (segment, subsegment, tone_of_voice, name, brand_color, accent_color) diverge from the snapshot that generated the active brand profile. Surface the misalignment via non-intrusive UX (banner → discreet button) in Step 2, the sole surface. Persist dismiss across sessions so the banner reappears only when data changes again.

### Problem

Currently when the lojista changes store registration data (segment, subsegment, tone_of_voice, name, or colors), the system persists the new values without any verification that the existing visual direction (active brand profile) is still coherent. The brand profile remains frozen at the state that generated the last inference, regardless of how many changes the lojista makes afterward.

The field `stores.previous_identity_snapshot` exists but is reserved for identity state transitions (text_only ↔ logo ↔ visual_signature). The field `store_brand_profiles.metadata` is jsonb and already exists — no migration needed.

### Solution

Store an `input_snapshot` in `store_brand_profiles.metadata` after every successful text_only inference (nesta fase). On each Step 2 mount, compute a normalized current visual state and compare it against the snapshot. If sensitive fields differ, show a drift banner. On dismiss, store a `drift_dismissed_snapshot` that is compared against the current state (not the input snapshot) so the banner reappears only when data changes again.

## Implementation Decisions

### D1: input_snapshot location
- `store_brand_profiles.metadata.input_snapshot` (not `stores.previous_identity_snapshot`)
- `metadata` is already jsonb — no migration needed
- Snapshot stays collocated with the profile that generated it

### D2: Sensitive fields
| Field | Sensitive? | Criterion |
|-------|-----------|-----------|
| `segment` | Yes | Primary factor for color and style decisions |
| `subsegment` | Yes | Refines direction within segment |
| `tone_of_voice` | Yes | Maps directly to visual_tone + visual_style |
| `name` | Yes | Alters brand perception |
| `brand_color` / `accent_color` | Special | Included in input_snapshot for cross-session persistence |
| `positioning` | No | Alone does not justify re-inference |

### D3: Snapshot structure
```json
{
  "input_snapshot": {
    "segment": "moda-feminina", "subsegment": "moda-feminina",
    "tone_of_voice": "elegante", "name": "Maria Boutique",
    "brand_color": "#FF6B6B", "accent_color": "#4ECDC4"
  },
  "drift_dismissed_snapshot": {
    "segment": "moda-feminina", "subsegment": "moda-feminina",
    "tone_of_voice": "elegante", "name": "Maria Boutique",
    "brand_color": "#FF6B6B", "accent_color": "#4ECDC4"
  }
}
```
Both live in `store_brand_profiles.metadata`. Same schema, different semantics.

### D4: Detection algorithm
```
1. No synced profile or no input_snapshot? → no drift
2. currentVisualState ≠ input_snapshot? → drift exists
3. Drift + drift_dismissed_snapshot == currentVisualState? → dismissed (discreet button)
4. Otherwise → new drift (banner)
```
Dismiss comparison is against current state, not input_snapshot — ensures banner reappears when data changes again.

### D5: Color resolution in currentVisualState
- `brand_color`: `stores.brand_color` (may be null)
- `accent_color`: `brand_colors_chosen[1]` → `safe_color_tokens.accent` → `inferred_accent_color` (first non-null wins)
- `brand_colors_chosen`, `safe_color_tokens`, `inferred_*` are never compared directly — only used as fallbacks for normalization

### D6: Color dirty tracking (session-only)
- On mount, capture initial color picker values
- onChange compares current vs initial value
- Used for UX copy augmentation ("você alterou campos e cores"), NOT for drift detection
- `brand_colors_chosen` empty (text_only) does NOT cause false positives — normalization handles this

### D7: UX flow
- **Step 2 mount**: banner with [Realinhar] [Ignorar], or discreet button if dismissed
- **Save Step 2**: no interruption — banner/button persists
- **Exit Step 2**: beforeunload only for unsaved form data, never for drift
- **New store**: no drift detection (mode=create)
- **Scope boundary**: Campaign generation flow is NOT modified in this phase

### D8: Realinhamento uses latest data
- Sensitive fields: current store values (already persisted)
- Colors: most recent — from form if dirty, otherwise from normalized current visual state

### D9: Dismiss persistence via dedicated API
- New route: `PATCH /api/store/[id]/brand-profile/metadata`
- Receives `{ drift_dismissed_snapshot: {...} }`, deep-merges into metadata JSONB
- Dedicated route — does not mix store concerns with brand profile metadata

## Specific Ideas

### DriftStatus type
```typescript
type DriftStatus = 'none' | 'new' | 'dismissed'
```

### DriftSnapshot structure
```typescript
type DriftSnapshot = {
  segment: string | null
  subsegment: string | null
  tone_of_voice: string | null
  name: string | null
  brand_color: string | null
  accent_color: string | null
}
```

### currentVisualState normalization
```typescript
function currentVisualState(store: Store, profile: BrandProfileRecord): DriftSnapshot {
  return {
    segment: store.segment,
    subsegment: store.subsegment,
    tone_of_voice: store.tone_of_voice,
    name: store.name,
    brand_color: store.brand_color,
    accent_color: profile?.brand_colors_chosen?.[1]
      ?? profile?.safe_color_tokens?.accent
      ?? profile?.inferred_accent_color
  }
}
```

### D10: Drift delivery mechanism — modal bloqueante no save

| Aspect | Decision |
|--------|---------|
| When | On "Salvar" click, when `driftStatus === 'new'` |
| UX | Modal bloqueante (sem escape, sem outside click, sem X) |
| Buttons | "Realinhar direção visual" (âmbar), "Manter direção visual atual" (outline), "Cancelar" (texto) |
| Realinhar | POST /infer → `executeStep2Save()` |
| Manter | PATCH metadata (dismiss) → `executeStep2Save()` |
| Cancelar | Fecha modal, não salva, volta ao form |
| Rationale | Inline banner era inconsistente (podia ser "atravessado") e não forçava decisão explícita do lojista |

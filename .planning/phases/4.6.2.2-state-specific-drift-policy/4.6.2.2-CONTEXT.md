# Phase 4.6.2.2: State-Specific Drift Policy — Context

**Gathered:** 2026-06-30
**Status:** Planning — 0/7 plans
**Source:** OpenSpec — `openspec/changes/fase-4-6-2-2-state-specific-drift-policy/`

<domain>
## Phase Boundary

**Propósito:** Implementar políticas de drift distintas por `identity_state` (text_only, logo, visual_signature), diagnóstico independente de critical vs sensitive drift, e o fluxo de substituição excepcional de VS para drift crítico com dois tiers de safety.

**O que esta fase entrega:**

1. **Política de drift por estado** — `getDriftPolicy()` com três matrizes (text_only: 7 sensíveis; logo: 6 sensíveis, name excluído; visual_signature: 4 sensíveis + N críticos condicionais)
2. **Diagnóstico independente** — `evaluateCriticalDrift()` (VS snapshot, server-side) e `evaluateSensitiveDrift()` (BP snapshot) como funções separadas
3. **`computeDriftStatus` parametrizável** — aceita `fields: readonly string[]` obrigatório. `DRIFT_FIELDS` removido.
4. **`src/lib/visual-signature/drift-revalidator.ts`** — NOVO, revalidação server-side de drift crítico usando VS snapshot canônico
5. **Compensação no realinhamento** — inferir antes de mutar em todos os caminhos (text_only, logo, visual_signature)
6. **Brand profiler `mode: 'regenerate'`** — ignora cache, re-infere preservando `content_used` e `visual_signature_id`
7. **GET /visual-signature com `critical_drift.status`** — 'none' | 'new' | 'dismissed'
8. **GET /brand-profile?status=synced** — filtra perfil ativo
9. **Fluxo de substituição excepcional VS** — DriftCriticalModal → ApprovalModal mode:'substitution' → geração com revalidação → aprovação com dois tiers (Tier 1: archive/activate com compensação; Tier 2: BP com fallback)
10. **POST /dismiss-critical-drift** — persiste snapshot no metadata da VS
11. **Bifurcação do save** — criticalStatus === 'new' → DriftCriticalModal; sensitiveStatus === 'new' → DriftDecisionModal
12. **Badge "Desalinhado"** na preview apenas quando `effectiveStatus === 'new'`

</domain>

<decisions>
## Implementation Decisions

### D1 — `getDriftPolicy` como função pura em `drift.ts`

`DRIFT_FIELDS` constante vira `getDriftPolicy(identityState, contentUsed?)` retornando `{ sensitive: readonly string[], critical: readonly string[] }`.

| Estado | Campos sensíveis | Campos críticos (condicionais) |
|--------|-----------------|-------------------------------|
| text_only | name, segment, subsegment, tone_of_voice, positioning, short_description, slogan | — |
| logo | segment, subsegment, tone_of_voice, positioning, short_description, slogan | — |
| visual_signature | subsegment, tone_of_voice, positioning, short_description | name, segment (+ slogan/city/state se content_used) |

### D2 — `evaluateCriticalDrift` e `evaluateSensitiveDrift` independentes

Para estado `visual_signature`, o diagnóstico é bifurcado:
- `evaluateCriticalDrift(vsSnapshot, contentUsed, store)` — server-side, compara VS `input_snapshot` (11 campos) com store atual
- `evaluateSensitiveDrift(bpSnapshot, store, fields)` — comparável ao `computeDriftStatus` atual, parametrizável

Frontend **não** executa evaluateCriticalDrift localmente — consome `activeVsSummary.critical_drift.status` do backend.

### D3 — `computeDriftStatus` com campos parametrizáveis

`fields` é obrigatório. `DRIFT_FIELDS` é removido. Todos os callers migrados explicitamente para `getDriftPolicy(state).sensitive`. Sem fallback oculto.

### D4 — VS snapshot como fonte canônica para campos críticos

VS `input_snapshot` (11 campos: name, segment, subsegment, tone_of_voice, positioning, short_description, slogan, city, state, brand_color, accent_color) é a fonte única para `evaluateCriticalDrift`. BP snapshot (7 campos) usado exclusivamente para `evaluateSensitiveDrift`.

### D5 — Propriedades ausentes em snapshots antigos

Propriedades ausentes são tratadas como "não comparar" (skip no campo). Tanto em `drift-validator.ts` quanto em `evaluateCriticalDrift`.

### D6 — Compensação — inferir antes de mutar

A regra varia por caminho. Princípio comum: inferir ANTES de mutar.

- **text_only/logo:** inferir → marcar anterior outdated → INSERT novo → restaurar se insert falhar
- **VS sensível (mesmo visual_signature_id):** inferir (mode:'regenerate') → UPDATE do BP existente → se update falhar, anterior permanece intacto (sem restauração — não houve mudança de status)
- **Substituição crítica (nova VS):** INSERT novo BP (novo visual_signature_id, índice único não conflita)

### D7 — DriftCriticalModal com bifurcação crédito/sem crédito

Com crédito (< 3 signatures): "Atualizar assinatura visual" → ApprovalModal mode:'substitution'. Sem crédito: alerta + "Manter direção atual" (dismiss + save) + "Remover mesmo assim" (VS → text_only).

### D8 — GET /visual-signature com critical_drift.status

Cálculo: `reason = restore_eligibility.reason`. Se `reason === 'ok'` → `status = 'none'`. Se `reason === 'critical_drift' | 'missing_metadata'`: compara `visual_signature_drift_dismissed_snapshot` com store atual → match = 'dismissed', senão = 'new'.

### D9 — Guardas do backend no generate-without-logo (mode: substitution)

1. Loja existe e ativa; 2. Lock de geração; 3. `identity_state === 'visual_signature'`; 4. Drift crítico revalidado; 5. Limite < 3 signatures; 6. Drafts históricos não bloqueiam.

### D10 — Guardas do approve mode: substitution

Revalidar drift crítico (VS ativa, não a nova), arquivar VS anterior, ativar nova, restaurar se falhar. Não chamar `identity-transitions`. BP gerado apenas após ativação (Tier 2).

### D11 — brand-profiler mode 'regenerate'

Tipo `ProfilerMode = 'reuse' | 'regenerate'`. `reuse` (atual, default): busca perfil existente. `regenerate`: ignora cache, re-infere todos os campos. Usado exclusivamente pelo realinhamento VS-sensível.

### D12 — ApprovalModal com mode prop

`mode: 'standard' | 'substitution'`. `standard`: fluxo atual de criação. `substitution`: começa em checking, chama `/generate-without-logo` com mode:'substitution', approval envia POST /approve com mode:'substitution'.

### D13 — POST /dismiss-critical-drift

Body vazio. Lê store.name, store.segment, store.slogan, store.city, store.state. Merge no metadata preservando campos existentes. Persiste `visual_signature_drift_dismissed_snapshot`. Retorna 204.

### D14 — Bifurcação do save no Step 2

```typescript
if (criticalStatus === 'new') → DriftCriticalModal
else if (sensitiveStatus === 'new') → DriftDecisionModal
else → salva direto
```

Non-blocking em todos os cenários.

</decisions>

<domain>
## Phase Boundary

**Propósito:** Substituir o botão "Continuar sem logo" / "Continuar sem assinatura" na fase `"error"` do `VisualSignatureApprovalModal` por um botão "Cancelar" que apenas fecha o modal sem persistir decisão de identidade. Corrigir também a sobrescrita de `logo_status` em falhas de substitution mode.

**O que esta fase entrega:**

1. **Cancelar na fase error** — Substituir `handleContinueWithoutLogo` por `handleCancel` que chama apenas `onClose()`. Sem PATCH, sem `onComplete()`, sem nova requisição.
2. **Label do botão secundário** — Muda de "Continuar sem logo/assinatura" para "Cancelar" na fase error.
3. **Label primário preservado** — `state.drift` continua decidindo entre "Ajustar assinatura" (drift presente) e "Tentar novamente" (sem drift).
4. **Proteção substitution mode** — Em `generate-without-logo/route.ts`, falha de geração com `mode='substitution'` não altera `logo_status`. VS ativa permanece com status inalterado.
5. **Remoção da rota `/logo-status`** — Após confirmar zero consumidores externos, remover `src/app/api/store/[id]/logo-status/route.ts`. BREAKING para qualquer caller não identificado.
6. **Testes comportamentais** — Infraestrutura Testing Library + jsdom para renderizar o modal e validar que "Cancelar" fecha sem mutações.

**Não escopo desta fase:**
- Redesenho completo do modal
- Alteração nas mensagens de erro (já são informativas)
- Comportamento de exhausted state ou approval standard
- `DriftCriticalModal` / `DriftDecisionModal`
- Redesenho do protocolo de substitution mode (apenas preservação de `logo_status` em falha)
- `identity-transitions.ts` — inalterado
- Remoção de `text_only_origin` (dormant, sem impacto)

</domain>

<decisions>
## Implementation Decisions

### D01: Cancelar chama apenas onClose()

`handleCancel` chama exclusivamente `onClose()`. Nenhum fetch, nenhum `onComplete()`, nenhuma mutação de estado além do fechamento do modal. O formulário pai já retém o estado anterior — o modal foi aberto sem mutação de estado do formulário, então fechá-lo simplesmente restaura a UI ao estado anterior.

```typescript
const handleCancel = useCallback(() => {
    onClose();
}, [onClose]);
```

### D02: Label primário usa state.drift

O modal usa `state.drift` internamente (não a prop `hasActiveSignatureDrift`) para decidir o label primário na fase error. Quando `state.drift` está presente: "Ajustar assinatura". Caso contrário: "Tentar novamente". O botão secundário mantém "Cancelar" em todos os cenários de erro.

### D03: Remoção da rota /logo-status com verificação prévia

O endpoint `PATCH /api/store/[id]/logo-status` é interno e seu único caller conhecido é o `handleContinueWithoutLogo` dentro do `VisualSignatureApprovalModal`, que está sendo substituído por `handleCancel`. Antes de remover, confirmar via grep que não há outros consumidores. A remoção é **BREAKING** para qualquer caller não identificado.

### D04: Falha em substitution mode não altera logo_status

Em substitution mode ou storage error, o erro de geração não deve tocar `logo_status`:
- **mode: 'standard', non-storage error**: `logo_status = 'failed'` (tentativa de criação falhou, store em `text_only`)
- **mode: 'standard', storage error**: `logo_status` não alterado (falha de infraestrutura)
- **mode: 'substitution', any error**: `logo_status` não alterado (VS ativa permanece)

### D05: Testes comportamentais com renderização real

Os testes atuais em `src/components/flow/__tests__/visual-signature-approval-modal.test.ts` não renderizam o componente — apenas testam funções isoladas. Esta fase adiciona infraestrutura Testing Library + jsdom para renderizar o `VisualSignatureApprovalModal` com fase "error" e validar comportamento real do clique.

### D06: Tratamento de timeout documentado

Timeout do cliente (190s) < backend (300s). Cancelar não cancela processamento anterior — geração prévia pode completar depois, persistindo estado divergente. Documentado como caveat conhecido.

</decisions>

<specifics>
## Fluxos Específicos

### Fluxo "Cancelar" na fase error

```
Estado atual (handleContinueWithoutLogo):
  Error → "Continuar sem logo" → PATCH /logo-status → onComplete({ logoStatus }) → modal fecha
    ├── DB: logo_status='explicit_none' sem identity_state correspondente
    └── React: identityState='visual_signature' divergente do DB

Estado novo (handleCancel):
  Error → "Cancelar" → onClose() → modal fecha
    └── Zero mutações adicionais. Formulário pai retém estado anterior.
```

### Estado resultante por cenário

| Cenário | Mutação já ocorrida no backend | Após "Cancelar" |
|---------|-------------------------------|-----------------|
| Standard mode — erro de geração (text_only) | `logo_status='failed'`, `identity_state='text_only'` | Nenhuma mutação adicional. Step 2 reexibe estado 'text_only'. |
| Standard mode — drift (hasActiveSignatureDrift) | Nenhuma (erro pré-geração) | Nenhuma mutação. Step 2 reexibe estado anterior. |
| Substitution mode — erro de geração (VS ativa + drift) | Com fix: `logo_status` NÃO alterado, `identity_state` permanece 'visual_signature' | Nenhuma mutação adicional. Step 2 reexibe VS ativa. |

### Condições do label na fase error

```
state.drift está presente? → Botão primário: "Ajustar assinatura"
state.drift ausente?       → Botão primário: "Tentar novamente"
Sempre                     → Botão secundário: "Cancelar"
```

### Regra de substitution mode (generate-without-logo/route.ts ~402-408)

```typescript
if (mode === 'substitution' || isStorageError) {
  // Não altera logo_status — VS ativa permanece
} else {
  // mode === 'standard' + erro não-storage
  logo_status = 'failed';
}
```

<domain>
## Phase Boundary

Tornar o fluxo cadastral do Vendeo compatível com CNPJ numérico e alfanumérico canônico, preservando integralmente o comportamento de CNPJs numéricos existentes. A fase cobre normalização, DV oficial, máscara, inputs, APIs, persistência, constraint PostgreSQL, hash de raiz, cache, provedores externos, testes e evidências locais.

A fase NÃO altera política comercial, oferta F50.2, trial de 28 dias, bloqueio por raiz, `freemium_entitlements`, ownership, RLS, saldos, grants, enrollments ou modelo institucional. F50.4 (oferta individualizada por CNPJ completo) permanece futura e fora de escopo.

</domain>

<decisions>
## Implementation Decisions (locked from OpenSpec)

### Representação canônica
- CNPJ normalizado tem 14 caracteres: posições 1–12 `[A-Z0-9]`, posições 13–14 `[0-9]`.
- Letras sempre maiúsculas.
- A normalização de domínio/API remove SOMENTE formatação conhecida: `.`, `/`, `-` e espaços. Acentos, emojis, símbolos e letras não ASCII NÃO são removidos; permanecem e invalidam a entrada.
- A raiz continua sendo `normalized.slice(0, 8)`.
- CNPJs numéricos existentes mantêm valor, hash, máscara e chave de cache.

### Validação e DV
- Algoritmo oficial módulo 11; valor do caractere = `charCode − 48` (`A = 17` … `Z = 42`).
- Pesos: 1º DV `[5,4,3,2,9,8,7,6,5,4,3,2]`; 2º DV `[6,5,4,3,2,9,8,7,6,5,4,3,2]`.
- `resto < 2 → DV = 0`; senão `DV = 11 − resto`.
- Aceitar todas as letras `A–Z`, incluindo `I`, `O`, `U`, `Q` e `F` (IN RFB nº 2.229/2024; exclusão de letras ambíguas não confirmada).
- Rejeitar sequências numéricas conhecidas (`00000000000000`, `11111111111111`, ...).
- Vetores: válido `12.ABC.345/01DE-35`; inválido por DV `12.ABC.345/01DE-34`; inválido por formato `12.ABC.345/01DE-3A`; primeiro CNPJ emitido `00.000.000/E08G-12` para smoke.

### UI fail-closed
- `formatCnpjInput(raw, previousValue)` mantém o último valor válido se detectar caractere desconhecido; não remove silenciosamente.
- `hasInvalidCnpjChars(raw)` detecta acentos, emojis e símbolos.
- Detecção no `onChange`/colagem, não apenas no blur.
- Com erro local: exibir erro, limpar estado de lookup, bloquear `/api/cnpj/lookup` no blur e bloquear submissão.
- O erro só é limpo após `validateCnpj` retornar sucesso; entradas parciais válidas mantêm o erro.
- Cobrir autosave e respostas de lookup anteriores ainda em andamento (não permitir que resposta antiga limpe erro/grave dado após entrada inválida).
- API/domínio continuam estritos: chamada direta com `12.ABC.345/01DE-35😀` retorna `400`.

### Mascaramento
- `maskCnpj` preserva o sufixo de 4 caracteres (posições 9–12), que pode ser alfanumérico.
- Entrada fora do padrão retorna placeholder `"CNPJ inválido"`; nunca devolve o identificador fiscal integral.

### Provedores, fallback e cache
- Interface de provedor declara `supportsAlphanumeric` (capacidade comprovada, não feature flag).
- `404` de CNPJ alfanumérico só é `not_found` conclusivo se o provedor declarar suporte; caso contrário é ambíguo (`unavailable`), aciona fallback e não é cacheado como inexistência.
- `400/422` de CNPJ alfanumérico = `unsupported_format` explícito.
- `unsupported_format` definitivo só quando TODOS os provedores tentados rejeitarem explicitamente o formato.
- `unsupported_format` + `unavailable` = `unavailable` (não foi possível concluir rejeição global).
- `unavailable`, `unsupported_format` e `not_found` ambíguo NÃO são cacheados.
- Cache usa `cnpj_normalized` canônico; caixa/pontuação não criam chaves duplicadas.

### APIs e atomicidade
- `POST /api/store`: `unsupported_format`/`unavailable` → loja criada com `verification_status = 'defer'`, reason correspondente, sem grant.
- `POST /api/store/update-cnpj`: indisponibilidade → `503` com mensagem controlada, sem persistir dados fiscais.
- `GET /api/cnpj/lookup`: alfanumérico aceito; `unsupported_format` só quando definitivo; mistura → `unavailable`.
- `reconsult-cnpj`: erro controlado, sem sobrescrever dados oficiais.
- Schemas Zod e contratos usam o padrão canônico.
- Preservar atomicidade entre `cnpj_normalized`, `cnpj_root_hash`, `razao_social`, `nome_fantasia` e status de verificação.

### Banco e migration
- Migration forward-only, transacional e fail-closed.
- Pré-checagem aborta se houver CNPJ não nulo fora do padrão, CNPJ sem root hash ou dados fiscais sem CNPJ.
- Recriar `chk_stores_cnpj_atomic` com `^[A-Z0-9]{12}[0-9]{2}$` via `NOT VALID` + `VALIDATE CONSTRAINT`.
- Nenhum `UPDATE` em `stores.cnpj_normalized`, `cnpj_root_hash` ou `cnpj_lookup_cache`.
- Preservar `idx_stores_cnpj_normalized`, `idx_stores_cnpj_root_hash` e unicidade global.
- Atualizar comentários de colunas apenas onde o contrato mudou.
- Destino do banco local deve ser explicitamente fixado antes de qualquer aplicação de migration; usar instância isolada, nunca remoto/produção.
- Alvo fixado pela pesquisa: `vendeo-f562a-isolated`, workdir `C:\Users\wagne\AppData\Local\Temp\opencode\vendeo-f562a-isolated`, DB `127.0.0.1:56322`, container `supabase_db_vendeo-f562a-isolated` (PG 17.6). Aplicar somente o arquivo único da F50.3 via `psql --single-transaction`; proibido `supabase migration up`, `db reset` ou `db push` nesse workdir (ledger não contém as 5 migrations de 2026-10-20).
- Coordenar timestamps de migration com a worktree paralela de assinatura visual; não tocar superfície alheia.

### Rollback
- Antes de existir CNPJ alfanumérico: rollback da aplicação é possível.
- Depois do primeiro CNPJ alfanumérico: NÃO voltar para versão numeric-only; usar correção forward-only ou versão emergencial que leia/preserve o valor, com write freeze se necessário.
- Só recriar a constraint numérica se a contagem de CNPJs alfanuméricos for zero.

### Fora de escopo preservado
- F50.4, modelo institucional/matriz-filiais, agências, organizações, migração de ownership, cobrança institucional.
- Reativação do freemium legado; a limitação `substring(cnpj_normalized, 9, 4) = '0001'` fica registrada para revisão futura.
- Ativação de flags, provedores pagos, migrations remotas, deploy, push, sync ou archive.

### Resoluções de lacunas encontradas na pesquisa (sem mudar o OpenSpec)
- **Persistência canônica obrigatória:** `POST /api/store/update-cnpj` deve usar `cnpjResult.normalized` para duplicidade, hash, RPC e persistência. Nunca usar a entrada crua. O mesmo vale para `POST /api/store`, `reconsult-cnpj` e admin create-test.
- **Exibição do CNPJ persistido:** `store-identity-form.tsx` deve usar `formatCnpj`, não regex `(\d{2})...`, para não renderizar o valor alfanumérico cru.
- **Campo vazio em CNPJ opcional:** em formulários onde o CNPJ é opcional (draft), esvaziar o campo limpa o erro local e mantém o estado “sem CNPJ”; não realiza lookup nem envia dados fiscais. Em formulários onde o CNPJ é obrigatório, o erro só é limpo com `validateCnpj` válido.
- **Test store + formato não suportado:** seguir a exceção já existente para indisponibilidade (`defer`, sem grant), sem criar política nova.
- **`/cadastro/cnpj`:** manter a rota/componente e atualizar seu contrato, mesmo que o fluxo atual redirecione para `/loja`; o UAT funcional principal ocorre em `/loja`.
- **`reveal-cnpj`:** permanece exceção administrativa auditada de exibição crua; não alterar a política de auditoria nesta fase.

</decisions>

<specifics>
## Specific Ideas

- Usar `12.ABC.345/01DE-35` como vetor oficial de cálculo e validação positiva.
- Usar `00.000.000/E08G-12` como primeiro CNPJ alfanumérico emitido no smoke opcional.
- Usar `12.ABC.345/01DE-34` como DV inválido; `12.ABC.345/01DE-3A` e `12.ABC.345/01DE-35😀` como formato inválido.
- Distinguir claramente testes com mocks de evidência real de suporte dos provedores. Nenhum provedor pago, flag, deploy ou migration remota.
- Fixar o destino do banco local (instância/container/porta/workdir) no CONTEXT/PATTERNS/RESEARCH antes de qualquer aplicação de migration; documentar identidade e isolamento.
- Testar lookup/submissão bloqueados após entrada inválida, inclusive autosave e respostas de consultas anteriores ainda em andamento.
- Separar validação automática (typecheck/lint/test/build, SQL local) de aprovação visual humana.

</specifics>

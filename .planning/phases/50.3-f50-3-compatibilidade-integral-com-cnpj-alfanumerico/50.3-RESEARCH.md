## User Constraints (from CONTEXT.md)

### Locked Decisions

**Representação canônica**
- CNPJ normalizado tem 14 caracteres: posições 1–12 `[A-Z0-9]`, posições 13–14 `[0-9]`.
- Letras sempre maiúsculas.
- A normalização de domínio/API remove SOMENTE formatação conhecida: `.`, `/`, `-` e espaços. Acentos, emojis, símbolos e letras não ASCII NÃO são removidos; permanecem e invalidam a entrada.
- A raiz continua sendo `normalized.slice(0, 8)`.
- CNPJs numéricos existentes mantêm valor, hash, máscara e chave de cache.

**Validação e DV**
- Algoritmo oficial módulo 11; valor do caractere = `charCode − 48` (`A = 17` … `Z = 42`).
- Pesos: 1º DV `[5,4,3,2,9,8,7,6,5,4,3,2]`; 2º DV `[6,5,4,3,2,9,8,7,6,5,4,3,2]`.
- `resto < 2 → DV = 0`; senão `DV = 11 − resto`.
- Aceitar todas as letras `A–Z`, incluindo `I`, `O`, `U`, `Q` e `F` (IN RFB nº 2.229/2024; exclusão de letras ambíguas não confirmada).
- Rejeitar sequências numéricas conhecidas (`00000000000000`, `11111111111111`, ...).
- Vetores: válido `12.ABC.345/01DE-35`; inválido por DV `12.ABC.345/01DE-34`; inválido por formato `12.ABC.345/01DE-3A`; primeiro CNPJ emitido `00.000.000/E08G-12` para smoke.

**UI fail-closed**
- `formatCnpjInput(raw, previousValue)` mantém o último valor válido se detectar caractere desconhecido; não remove silenciosamente.
- `hasInvalidCnpjChars(raw)` detecta acentos, emojis e símbolos.
- Detecção no `onChange`/colagem, não apenas no blur.
- Com erro local: exibir erro, limpar estado de lookup, bloquear `/api/cnpj/lookup` no blur e bloquear submissão.
- O erro só é limpo após `validateCnpj` retornar sucesso; entradas parciais válidas mantêm o erro.
- Cobrir autosave e respostas de lookup anteriores ainda em andamento (não permitir que resposta antiga limpe erro/grave dado após entrada inválida).
- API/domínio continuam estritos: chamada direta com `12.ABC.345/01DE-35😀` retorna `400`.

**Mascaramento**
- `maskCnpj` preserva o sufixo de 4 caracteres (posições 9–12), que pode ser alfanumérico.
- Entrada fora do padrão retorna placeholder `"CNPJ inválido"`; nunca devolve o identificador fiscal integral.

**Provedores, fallback e cache**
- Interface de provedor declara `supportsAlphanumeric` (capacidade comprovada, não feature flag).
- `404` de CNPJ alfanumérico só é `not_found` conclusivo se o provedor declarar suporte; caso contrário é ambíguo (`unavailable`), aciona fallback e não é cacheado como inexistência.
- `400/422` de CNPJ alfanumérico = `unsupported_format` explícito.
- `unsupported_format` definitivo só quando TODOS os provedores tentados rejeitarem explicitamente o formato.
- `unsupported_format` + `unavailable` = `unavailable` (não foi possível concluir rejeição global).
- `unavailable`, `unsupported_format` e `not_found` ambíguo NÃO são cacheados.
- Cache usa `cnpj_normalized` canônico; caixa/pontuação não criam chaves duplicadas.

**APIs e atomicidade**
- `POST /api/store`: `unsupported_format`/`unavailable` → loja criada com `verification_status = 'defer'`, reason correspondente, sem grant.
- `POST /api/store/update-cnpj`: indisponibilidade → `503` com mensagem controlada, sem persistir dados fiscais.
- `GET /api/cnpj/lookup`: alfanumérico aceito; `unsupported_format` só quando definitivo; mistura → `unavailable`.
- `reconsult-cnpj`: erro controlado, sem sobrescrever dados oficiais.
- Schemas Zod e contratos usam o padrão canônico.
- Preservar atomicidade entre `cnpj_normalized`, `cnpj_root_hash`, `razao_social`, `nome_fantasia` e status de verificação.

**Banco e migration**
- Migration forward-only, transacional e fail-closed.
- Pré-checagem aborta se houver CNPJ não nulo fora do padrão, CNPJ sem root hash ou dados fiscais sem CNPJ.
- Recriar `chk_stores_cnpj_atomic` com `^[A-Z0-9]{12}[0-9]{2}$` via `NOT VALID` + `VALIDATE CONSTRAINT`.
- Nenhum `UPDATE` em `stores.cnpj_normalized`, `cnpj_root_hash` ou `cnpj_lookup_cache`.
- Preservar `idx_stores_cnpj_normalized`, `idx_stores_cnpj_root_hash` e unicidade global.
- Atualizar comentários de colunas apenas onde o contrato mudou.
- Destino do banco local deve ser explicitamente fixado antes de qualquer aplicação de migration; usar instância isolada, nunca remoto/produção.
- Coordenar timestamps de migration com a worktree paralela de assinatura visual; não tocar superfície alheia.

**Rollback**
- Antes de existir CNPJ alfanumérico: rollback da aplicação é possível.
- Depois do primeiro CNPJ alfanumérico: NÃO voltar para versão numeric-only; usar correção forward-only ou versão emergencial que leia/preserve o valor, com write freeze se necessário.
- Só recriar a constraint numérica se a contagem de CNPJs alfanuméricos for zero.

**Fora de escopo preservado**

- Reativação do freemium legado; a limitação `substring(cnpj_normalized, 9, 4) = '0001'` fica registrada para revisão futura.
- Ativação de flags, provedores pagos, migrations remotas, deploy, push, sync ou archive.

## Summary

A fase é uma mudança de **contrato de formato** que atravessa um domínio já centralizado (`src/lib/cnpj/`), dois provedores externos, cinco rotas de API, três formulários e uma constraint PostgreSQL. O código atual confirma exatamente o diagnóstico do design: `normalizeCnpj` usa `replace(/\D/g,"")`, `validateCnpj` usa `^\d{14}$` e `Number()`, `maskCnpj` é fail-**open** (devolve a entrada crua quando inválida) e nenhum provedor declara capacidade alfanumérica. A matriz de arquivos do OpenSpec cobre a quase totalidade dos pontos; a pesquisa encontrou **quatro superfícies fora ou subespecificadas** na matriz (formulário `/cadastro/cnpj` que está morto, exibição não mascarada do CNPJ do próprio lojista, `update-cnpj` persistindo a entrada crua em vez do canônico, e o branch indecidido de test-store para `unsupported_format`).

Os vetores oficiais foram reconferidos por cálculo local independente: `12ABC34501DE` → DV `35`, `00000000E08G` → DV `12`, `123456780001` → DV `95`. O algoritmo `ASCII − 48` e os pesos do design estão corretos (`[CITED: gov.br/receitafederal … cnpj-alfanumerico.pdf]`, `[CITED: IN RFB 2229/2024]`). O `openspec validate --strict` está válido nesta sessão.

O ponto mais sensível para a execução não é o núcleo: é (a) a **corrida de lookup em voo** no onboarding, que exige um guard por sequência (e opcionalmente `AbortController`) além do estado de erro local; (b) o **autosave fiscal**, que hoje dispara `update-cnpj` a partir de `replace(/\D/g,"")` e precisa ser bloqueado quando há erro local — o valor em `formData` não contém o caractere inválido, então o hook **não consegue detectar sozinho** e precisa de plumbing explícito; e (c) o **destino de banco local**, que está fixado e vivo (`vendeo-f562a-isolated`, DB `127.0.0.1:56322`), mas cujo ledger tem 133 migrations e **não registra as 5 migrations de 2026-10-20** (a F50.2 foi aplicada por `psql`). Portanto `supabase migration up` nesse workdir tentaria reaplicar migrations alheias e deve ser proibido; a prova da F50.3 deve ser um arquivo único aplicado por `psql --single-transaction`.

**Recomendação primária:** planejar em **7 planos** (núcleo → provedores → APIs → UI onboarding → UI legado/admin → migration+prova SQL → regressão/gates/documentação), mantendo `supportsAlphanumeric = false` nos dois provedores até um smoke humano opcional, e tratando a migration como arquivo isolado aplicado por `psql` no container `supabase_db_vendeo-f562a-isolated` após preflight de isolamento e dry-run em `BEGIN/ROLLBACK`.

### Pattern 1: Exaustividade de estados na orquestração
**What:** trocar cadeias de `if` por `switch` com caso `default: assertNever(result)`.
**When to use:** `CnpjVerificationService.resolve` e os consumidores (`store`, `update-cnpj`, `reconsult`, `lookup`).
**Why:** hoje `POST /api/store` e `update-cnpj` usam `if` sequenciais; um novo status que não case nenhum `if` **cai silenciosamente** no caminho "unverified/persistir". Com união exaustiva, o compilador obriga a tratar `unsupported_format` em cada consumidor.
```ts
// Source: padrão interno do repo (discriminated unions) + design D7
switch (result.status) {
  case "resolved": /* ... */ break;
  case "not_found": /* ... */ break;
  case "unsupported_format": /* ... */ break;
  case "unavailable": /* ... */ break;
  default: { const _exhaustive: never = result; return _exhaustive; }
}
```

### Pattern 2: Guard por sequência para resposta assíncrona de input
**What:** contador monotônico em `useRef` incrementado a cada mudança do campo e a cada início de lookup; a resposta só aplica estado se `seq === ref.current`.
**When to use:** `onBlur` do CNPJ em `store-identity-form.tsx` (e, por simetria, em `handleReconsultCnpj`).
**Why:** o código atual não tem guard algum; uma resposta antiga pode setar `resolved`, sobrescrever `razaoSocial`/`city`/`billing` e limpar o estado após uma colagem inválida.
```ts
const lookupSeqRef = useRef(0);
// onChange (sempre) e detecção de inválido:
lookupSeqRef.current += 1;
// onBlur:
const seq = ++lookupSeqRef.current;
const res = await fetch(`/api/cnpj/lookup?cnpj=${encodeURIComponent(normalized)}`);
if (seq !== lookupSeqRef.current) return; // resposta obsoleta: não toca em estado
```

### Pattern 3: Erro local com precedence explícita no domínio
**What:** em `validateCnpj`, checar caractere desconhecido **antes** do comprimento, e restringir o uppercase a `[a-z]` ASCII.
**Why:** `12.ABC.345/01DE-35😀` normaliza para 15 caracteres; se o comprimento for checado primeiro, a mensagem vira "14 caracteres" e viola o cenário do spec ("CNPJ inválido"). `toUpperCase()` Unicode pode transformar `ß` em `SS` e mudar o comprimento.

### Pattern 4: Migration como arquivo único, sem `BEGIN/COMMIT` embutido
**What:** autorar a migration sem transação explícita (convenção do repo desde a F56.2b2a) e aplicar com `psql --single-transaction` no alvo isolado.
**Why:** `supabase migration up` já envolve cada arquivo em transação; `BEGIN/COMMIT` embutido quebra em ferramentas que já gerenciam transação. Para aplicação manual via `psql`, `--single-transaction` garante atomicidade.

### Anti-Patterns to Avoid
- **Normalizar na máscara:** `maskCnpj` deve ser fail-closed puro; normalizar dentro dela esconderia dado inválido e contrariaria 9.3 (`maskCnpj("12abc…") === "CNPJ inválido"`).
- **Limpar `razaoSocial`/`nomeFantasia` no onChange inválido:** o código atual faz isso quando o status do lookup não é `idle`; numa colagem hostil isso apaga dados oficiais já carregados.
- **Usar `formData.cnpj.replace(/\D/g,"")` em qualquer lugar:** remove letras e cria o "CNPJ limpo" que o design proíbe.
- **Confiar em `store.cnpj_normalized === cnpjNormalized` antes de canonicalizar:** o input pode vir com pontuação e o teste de idempotência falha, caindo em `cnpj_already_set`.
- **Cachear `not_found` ambíguo:** cria falso negativo permanente (24h) para todo CNPJ alfanumérico enquanto o provedor não suporta o formato.
- **Aplicar `migration up` no workdir isolado:** ver R5.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| DV de CNPJ alfanumérico | parser/validador alternativo inline em cada rota/UI | `validateCnpj` central | O algoritmo é normativo e já existe; duplicar gera divergência TS × SQL |

### Decisão pendente (R2)
"O erro só é limpo após `validateCnpj` sucesso" + campo esvaziado = o lojista pode ficar preso sem conseguir criar loja draft. ## Common Pitfalls

### Pitfall 1: Resposta de lookup antiga sobrescrevendo estado novo
**O que dá errado:** o lojista cola um CNPJ válido, o blur dispara o fetch, ele edita/cola algo inválido; a resposta antiga chega e seta `resolved`, preenche razão social/cidade/billing e apaga o erro.
**Por que acontece:** não há identidade de requisição; o handler aplica estado incondicionalmente.
**Como evitar:** `lookupSeqRef` + `AbortController`, checagem após cada `await`, e nunca limpar `cnpjInputError` em resposta de rede.
**Sinal de alerta:** teste que resolve o fetch depois de um `change` inválido e ainda vê "Dados carregados".

### Pitfall 2: Autosave fiscal durante erro local
**O que dá errado:** com `hasExistingCnpj=false` e um valor válido de 14 chars em `formData`, trocar de aba dispara `update-cnpj` mesmo com erro local visível (porque o valor inválido não entrou no estado).
**Por que acontece:** o hook só vê `formData`, não o erro de input.
**Como evitar:** plumbing explícito `fiscalWriteBlocked`/`hasInvalidCnpjInput` + guard em `fiscalElegivel`.
**Sinal de alerta:** teste de autosave que passa com erro local ativo.

### Pitfall 3: `validateCnpj` com precedência de erro errada
**O que dá errado:** `12.ABC.345/01DE-35😀` retorna "CNPJ deve ter 14 caracteres" em vez de "CNPJ inválido"; cenário do spec falha.
**Como evitar:** checar `[^0-9A-Za-z./\-\s]` antes do comprimento; uppercase só `[a-z]`.
**Sinal de alerta:** teste de mensagem exata.

### Pitfall 4: `update-cnpj` persistindo entrada não canônica
**O que dá errado:** rota valida `cnpjNormalized`, mas calcula hash e persiste a string de entrada; com pontuação, grava `12.ABC...` e a constraint rejeita (ou pior, duplicidade/índice divergem).
**Como evitar:** usar sempre `cnpjResult.normalized` para hash, comparação de idempotência, duplicidade e RPC.
**Sinal de alerta:** teste de rota com entrada mascarada.

### Pitfall 5: `migration up` no workdir isolado
**O que dá errado:** o ledger tem 133 e o diretório 133, mas as 5 migrations de 2026-10-20 já estão aplicadas por `psql`; o CLI as veria como pendentes e tentaria reaplicá-las (falhando ou alterando superfície alheia).
**Como evitar:** aplicar apenas o arquivo da F50.3 por `psql --single-transaction`; nunca `migration up`, `db reset` ou `db push`.
**Sinal de alerta:** CLI listando `20261020000001..5` como pendentes.

### Pitfall 6: Exibição fail-open do CNPJ do próprio lojista
**O que dá errado:** `store-identity-form.tsx:1486` usa regex numérica; para CNPJ alfanumérico a substituição não casa e o campo renderiza os 14 caracteres crus (sem máscara) — e `cnpj-update-form.tsx:144` tem o mesmo padrão.
**Como evitar:** `formatCnpj(normalized)` para exibição completa; `maskCnpj` para telas administrativas.
**Sinal de alerta:** screenshot de CNPJ sem pontuação.

### Pitfall 7: Mocks de teste reimplementando a normalização antiga
**O que dá errado:** testes de rota mockam `validateCnpj` com `raw.replace(/\D/g,"")`; a suíte continua verde mesmo se o código real regredir para numérico.
**Como evitar:** importar o módulo real ou atualizar o mock para `normalizeCnpj`; adicionar ao menos um caso alfanumérico por rota.
**Sinal de alerta:** grep por `replace(/\D/g` em `__tests__`.

## Code Examples

### Normalização e validação canônicas
```ts
// Source: design D1/D2 + RFB (ASCII − 48) — verificado por cálculo local
const FORMATTING = /[./\-\s]/g;
const ALLOWED = /^[0-9A-Za-z./\-\s]*$/;

export function normalizeCnpj(raw: string): string {
  return raw.replace(FORMATTING, "").replace(/[a-z]/g, (c) => c.toUpperCase());
}

export function hasInvalidCnpjChars(raw: string): boolean {
  return !ALLOWED.test(raw);
}

const FIRST_WEIGHTS  = [5,4,3,2,9,8,7,6,5,4,3,2];
const SECOND_WEIGHTS = [6,5,4,3,2,9,8,7,6,5,4,3,2];

function dv(values: number[], weights: number[]): number {
  const sum = values.reduce((acc, v, i) => acc + v * weights[i], 0);
  const rest = sum % 11;
  return rest < 2 ? 0 : 11 - rest;
}

export function validateCnpj(raw: string): CnpjOutput | Error {
  if (hasInvalidCnpjChars(raw)) return new Error("CNPJ inválido"); // precedência
  const normalized = normalizeCnpj(raw);
  if (normalized.length !== 14) return new Error("CNPJ deve ter 14 caracteres");
  if (!/^[A-Z0-9]{12}[0-9]{2}$/.test(normalized)) return new Error("CNPJ inválido");
  if (KNOWN_INVALID_SEQUENCES.includes(normalized)) return new Error("CNPJ inválido");
  const values = normalized.split("").map((c) => c.charCodeAt(0) - 48);
  if (dv(values.slice(0, 12), FIRST_WEIGHTS) !== values[12]) return new Error("CNPJ inválido");
  if (dv(values.slice(0, 13), SECOND_WEIGHTS) !== values[13]) return new Error("CNPJ inválido");
  return { normalized };
}
```

### Máscara progressiva fail-closed
```ts
// Source: design D4
export function formatCnpjInput(raw: string, previousValue = ""): string {
  if (hasInvalidCnpjChars(raw)) return previousValue;
  const c = normalizeCnpj(raw).slice(0, 14);
  const p: string[] = [];
  for (let i = 0; i < c.length; i++) {
    if (i === 2 || i === 5) p.push(".");
    if (i === 8) p.push("/");
    if (i === 12) p.push("-");
    p.push(c[i]);
  }
  return p.join("");
}

export function formatCnpj(canonical: string): string {
  return /^[A-Z0-9]{12}[0-9]{2}$/.test(canonical)
    ? `${canonical.slice(0,2)}.${canonical.slice(2,5)}.${canonical.slice(5,8)}/${canonical.slice(8,12)}-${canonical.slice(12)}`
    : "CNPJ inválido";
}

export function maskCnpj(normalized: string): string {
  if (!/^[A-Z0-9]{12}[0-9]{2}$/.test(normalized)) return "CNPJ inválido";
  return `**.***.***/${normalized.slice(8, 12)}-**`;
}
```

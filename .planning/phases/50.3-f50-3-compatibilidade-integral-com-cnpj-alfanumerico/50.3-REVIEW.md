## Summary

Static review of the 40 source files changed by phase 50.3. The core domain changes are sound: the modulo-11 check-digit algorithm with `charCode − 48` matches the official alphanumeric rule and the specified vectors (`12.ABC.345/01DE-35`, `00.000.000/E08G-12`), normalization removes only known formatting and preserves hostile characters, `maskCnpj` is fail-closed, provider classification (404/400/422) and the service aggregation/fallback/cache matrix match the locked decisions (negative outcomes are never cached; the cache key is canonical), the API routes consistently use `cnpjResult.normalized`/`canonical` for hash, duplicate check, RPC and persistence, and the migration is forward-only with fail-closed preflight, `NOT VALID` + `VALIDATE`, no `UPDATE`, no index/RLS/grant changes. The verifier guards host/port/container identity, uses savepoints with `ROLLBACK`, checks `23514` + constraint name, and its offline self-test passes 14/14.

One real correctness defect was found in the frontend save path (silent CNPJ drop + client/DB state desync reachable through the drift/navigation save path), plus one behavioral regression in the legacy form and test-quality weaknesses that can mask regressions. No security vulnerability introduced by the phase was proven; two pre-existing hardening gaps in a touched route are noted for completeness.

## Critical Issues

### CR-01: `save()` creates a CNPJ-less draft and then marks the store as "has CNPJ" when the local CNPJ is blocked/invalid

**File:** `src/components/flow/use-store-form.ts:307-315` and `src/components/flow/use-store-form.ts:344`
**Severity:** Critical (incorrect behavior + silent loss of user-entered fiscal data + client/DB state desync)

**Issue:**
In create mode, the CNPJ is added to the POST body only when all three conditions hold:

```ts
if (formData.cnpj && !fiscalWriteBlocked) {          // 307
  const cnpjResult = validateCnpj(formData.cnpj);
  if (!(cnpjResult instanceof Error)) {              // 309
    body.cnpj = cnpjResult.normalized;
  }
}
```

If any of them fails, `save()` **continues silently** and posts a draft store with no `cnpj` (line 317). Immediately after success it does:

```ts
if (formData.cnpj || saved.cnpj_normalized) setHasExistingCnpj(true);   // 344
```

`formData.cnpj` is still the local string, so the hook now believes the CNPJ was persisted even when the server never received it. This is reachable because `save()` is used not only by the guarded step-1 submit (`handleStep1Submit` checks `cnpjInputErrorRef`/`validateCnpj`), but also by `persistSaveFromDrift()` (`store-identity-form.tsx:1368-1382`), which is called by the drift/navigation modals (`:2670, :2715, :2724, :2747, :2772`) and performs no CNPJ guard.

Two concrete triggers:
1. **Valid CNPJ + hostile paste:** user types a complete valid CNPJ, then pastes a hostile string (e.g. appends `😀`). `onPaste` calls `preventDefault`, sets `cnpjInputError`/`fiscalWriteBlocked`, and leaves `formData.cnpj` as the valid canonical value. Navigating/saving through a drift modal calls `save()`, which skips `body.cnpj` because `fiscalWriteBlocked` is true.
2. **Invalid-DV CNPJ:** user types `12.ABC.345/01DE-34` (invalid chars: none; invalid DV) and navigates through a drift-save path. `handleStep1Submit` would block, but `save()` is called directly; `validateCnpj` fails, so `body.cnpj` is omitted.

**Impact:** the store is created without the CNPJ (and `razaoSocial`/`nomeFantasia` are sent in the draft POST, which the draft RPC ignores), but `hasExistingCnpj` becomes `true`. Every subsequent `save()` then takes the "store has CNPJ" PATCH branch (`:274-301`) and never calls `/api/store/update-cnpj`; the PATCH route rejects `razaoSocial`/`nomeFantasia` for a store without `cnpj_normalized` with 409 (`src/app/api/store/[id]/route.ts:157-174`). In-session the user cannot register the CNPJ and sees confusing errors; only a full reload recovers (`hasExistingCnpj` is re-initialized from `initialStore`). The previous numeric-only implementation sent the digits unconditionally, so the route's validator rejected the invalid CNPJ with a 400 instead of silently creating a draft — this is a phase-introduced regression.

**Fix:**
```ts
// use-store-form.ts (create mode)
if (formData.cnpj) {
  if (fiscalWriteBlocked) {
    setError("CNPJ inválido");
    setSaveStatus("error");
    return { error: "CNPJ inválido" };
  }
  const cnpjResult = validateCnpj(formData.cnpj);
  if (cnpjResult instanceof Error) {
    setError("CNPJ inválido");
    setSaveStatus("error");
    return { error: "CNPJ inválido" };
  }
  body.cnpj = cnpjResult.normalized;
}

// use-store-form.ts:344 — only trust the server response
if (typeof saved.cnpj_normalized === "string" && saved.cnpj_normalized !== "") {
  setHasExistingCnpj(true);
}
```
Additionally, guard `persistSaveFromDrift()` with the same `cnpjInputErrorRef` condition used by `handleStep1Submit`, or make `save()` itself return the error as above so the drift modal surfaces it instead of creating a draft. Add a regression test in `use-store-form.autosave-fiscal.test.ts` for "create save with blocked/invalid CNPJ does not create a store and does not set hasExistingCnpj".

## Warnings

### WR-01: Removing `setError(null)` from the legacy CNPJ form leaves a stale submit error after correction

**File:** `src/app/(app)/cadastro/cnpj/cnpj-update-form.tsx:36-52` (and rendering at `:229-234`)
**Severity:** Warning (phase-introduced behavioral regression; misleading UI)

**Issue:** The previous `handleCnpjChange` called `setError(null)` on every edit. The new handler only updates `inputError`, so a submit-level error (`error`, rendered via `inputError ?? error`) is not cleared when the user corrects the CNPJ. After a failed submit (`CNPJ inválido. Verifique os dígitos...`), correcting the field to a complete valid CNPJ and even seeing the field mask become valid still displays the old error until the next submit. This conflicts with the phase's stated principle "the error is only cleared by a complete valid entry" — the valid entry clears `inputError` but not `error`.

**Fix:** Clear the submit error when a complete valid entry is detected, e.g.:

```ts
if (!(validateCnpj(next) instanceof Error)) {
  setInputError(null);
  setError(null);
}
```
(or clear `error` at the top of `handleCnpjChange` for any user edit, as before, keeping `inputError` sticky until a valid entry).

### WR-02: The admin CNPJ display "contract test" is a source-string pattern match that can miss the regression it claims to prevent

**File:** `src/app/(app)/admin/__tests__/cnpj-display.contract.test.ts:28`, `:35-49`, `:61-65`
**Severity:** Warning (test quality — a weak/circular assertion can mask a real display regression)

**Issue:** The contract is asserted by reading source text and checking substrings:
- `LOCAL_NUMERIC_CNPJ_REGEX = /\(\\d\{2\}\)\(\\d\{3\}\)/` only matches the literal source shape `(\d{2})(\d{3})`. A reintroduced local formatter written as `/(\d{2})\.(\d{3})\./` (escaped dots, which is exactly what a formatter would use) does **not** match and the test passes.
- The `mask.ts` assertion checks implementation tokens (`"CNPJ inválido"`, `normalized.slice(8, 12)`) rather than executing `maskCnpj`. A refactor from `slice` to `substring` fails the test even with identical behavior, while a behavioral regression (e.g. an additional fail-open branch returning the raw value when a legacy check passes) could still leave both tokens present.
- No test asserts that an admin surface renders `**.***.***/XXXX-**` rather than the raw `cnpj_normalized` for an alphanumeric value.

**Fix:** Keep the import assertion if desired, but add behavior-level coverage: render the admin list/detail components (or at least call the same helper chain) with alphanumeric `cnpj_normalized` and assert the raw value is absent and the masked suffix is present. Replace the numeric-regex check with a broader AST/grep that flags any `\d{2}`-style CNPJ formatting in those files, and avoid asserting implementation substrings in `mask.ts`.

## Info

### IN-01: `update-cnpj` route omits `requireSameOrigin` (pre-existing, touched file)

**File:** `src/app/api/store/update-cnpj/route.ts:28`
**Severity:** Info (security defense-in-depth; pre-existing, not introduced by the phase)

**Issue:** This is a cookie-authenticated state mutation (`update_store_cnpj`), but unlike the sibling mutation routes (`POST /api/store` at `store/route.ts:48`, `reconsult-cnpj` at `:18`) it does not call `requireSameOrigin(request)`. Practical risk is reduced by Supabase's SameSite cookie defaults, but the inconsistency is a defense-in-depth gap. **Fix:** import and call `requireSameOrigin(request)` at the top of the handler, after `request.json()` is not yet needed.

### IN-02: Raw RPC error message returned to the client, and the test codifies it

**File:** `src/app/api/store/update-cnpj/route.ts:210`; test at `src/app/api/store/update-cnpj/__tests__/route.test.ts:437-453`
**Severity:** Info (pre-existing; possible internal-detail disclosure)

**Issue:** Unknown RPC failures return `{ error: error.message }` with status 500, exposing database/RPC internals. The test is named "returns 500 for unknown RPC errors instead of leaking raw SQL" but asserts exactly that the raw message is returned, so it protects the wrong behavior. **Fix:** log the raw error server-side and return a generic controlled message; update the test to assert the generic response and that the internal message is not present.

### IN-03: Canonical CNPJ regex duplicated across three domain files

**Files:** `src/lib/cnpj/validate.ts:22`, `src/lib/cnpj/mask.ts:2`, `src/lib/cnpj/input-mask.ts:9`
**Severity:** Info (maintainability; drift risk)

**Issue:** `^[A-Z0-9]{12}[0-9]{2}$` is defined independently in three modules. A future contract change (e.g. a new allowed character class) could update one and leave the others enforcing the old format. **Fix:** export a single `CANONICAL_CNPJ_PATTERN`/`isCanonicalCnpj` from a shared module (e.g. `normalize.ts` or a new `contract.ts`) and import it in validate/mask/input-mask.

### IN-04: Unused `dataFromLookup` binding

**File:** `src/components/flow/store-identity-form.tsx:1511`
**Severity:** Info (dead code; pre-existing)

**Issue:** `const dataFromLookup = hasStoredCnpj || cnpjLookupStatus === 'resolved';` is never read. It is harmless but indicates leftover logic near the fiscal section and could mislead future maintainers about which flag drives rendering. **Fix:** remove the binding or use it instead of the duplicated expressions.

### IN-05: Weak/tautological assertions and a missing regression case in tests

**Files:** `src/components/flow/__tests__/store-identity-form.cnpj-alfanumerico.test.tsx:428`; `src/components/flow/__tests__/use-store-form.autosave-fiscal.test.ts` (suite)
**Severity:** Info (test quality)

**Issue:**
- Test 10 ends with `expect(VALID_ALPHA_CANONICAL).toBe("12ABC34501DE35")`, a tautology that compares a constant to a literal and proves nothing.
- The hook suite covers `fiscalWriteBlocked` for `autoSave`, but has no case for `save()` in create mode with a blocked/invalid CNPJ, which is exactly the CR-01 path. This gap is why the regression is not caught.
**Fix:** remove the tautology (or assert the actual `update-cnpj` body/field) and add the blocked/invalid `save()` create-mode case asserting no draft store is created (or that `hasExistingCnpj` stays false).

### IN-06: Lookup UI collapses `unsupported_format` into the generic `unavailable` message

**File:** `src/components/flow/store-identity-form.tsx:1686-1690`
**Severity:** Info (UX; distinct from accepted F50.3-UAT-03)

**Issue:** `/api/cnpj/lookup` now returns a dedicated `{ status: "unsupported_format", message }` payload (`src/app/api/cnpj/lookup/route.ts:50-55`), but the blur handler's `else` branch treats every non-`resolved`/non-`not_found` status as `unavailable` and shows "Não foi possível consultar... A loja será criada sem créditos iniciais." The user is never told that the format is permanently unsupported by the providers (a materially different situation from a transient outage). F50.3-UAT-03 only covers the reconsult UI, so this is a separate, lower-impact gap. **Fix:** add a `'unsupported_format'` member to `cnpjLookupStatus` (or branch on `data.status`) and render the message returned by the route.

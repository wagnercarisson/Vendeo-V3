# F50.3 — Plano de rollback da migration de CNPJ alfanumérico

**Migration:** `supabase/migrations/20261021000001_f50_3_cnpj_alfanumerico.sql`
**Objeto alterado:** `public.stores.chk_stores_cnpj_atomic` (+ `COMMENT ON COLUMN` de 3 colunas)
**Escopo:** local/isolado. Nenhuma migration remota, push ou deploy é executado nesta fase.

O rollback tem **duas fases** e o divisor entre elas é a existência de qualquer CNPJ
alfanumérico persistido.

---

## Gate obrigatório antes de qualquer restauração da constraint numérica

```sql
SELECT count(*) FROM public.stores WHERE cnpj_normalized ~ '[A-Z]';
```

- Resultado **0** → é seguro restaurar a constraint numérica (`^\d{14}$`).
- Resultado **> 0** → **NÃO** restaurar a versão numeric-only. Ir para a Fase 2.

Nunca apagar, truncar ou "corrigir" linhas para fazer o gate voltar a 0. A restauração
da constraint numérica não reescreve dados e não é permitida depois do primeiro CNPJ
alfanumérico persistido.

---

## Fase 1 — Antes de existir CNPJ alfanumérico (rollback seguro)

O contrato novo (`^[A-Z0-9]{12}[0-9]{2}$`) é **superconjunto** do anterior
(`^\d{14}$`). Enquanto o gate acima retornar 0, todos os dados existentes são
numéricos e continuam válidos nos dois contratos.

O rollback da **aplicação** é seguro e pode ser feito apenas revertendo o código
(voltar `supportsAlphanumeric`, validação e inputs ao contrato numérico). A constraint
alfanumérica pode permanecer no banco sem risco, pois aceita integralmente o conjunto
numérico.

Restaurar a constraint anterior é **opcional** e só deve ocorrer com o gate em 0:

```sql
-- Executar SOMENTE com `SELECT count(*) ... ~ '[A-Z]'` = 0
ALTER TABLE public.stores DROP CONSTRAINT IF EXISTS chk_stores_cnpj_atomic;
ALTER TABLE public.stores ADD CONSTRAINT chk_stores_cnpj_atomic
  CHECK (
    (cnpj_normalized IS NULL AND razao_social IS NULL AND nome_fantasia IS NULL AND cnpj_root_hash = '')
    OR
    (cnpj_normalized IS NOT NULL AND cnpj_normalized ~ '^\d{14}$' AND cnpj_root_hash <> '')
  );
```

Rollback dos comentários (opcional, sem impacto funcional):

```sql
COMMENT ON COLUMN public.stores.cnpj_normalized IS 'CNPJ normalizado (14 dígitos) — chave única.';
COMMENT ON COLUMN public.stores.cnpj_root_hash IS 'HMAC-SHA256 dos 8 primeiros dígitos (raiz) com pepper server-side.';
COMMENT ON COLUMN public.cnpj_lookup_cache.cnpj_normalized IS 'CNPJ normalizado (14 dígitos) — chave primária.';
```

---

## Fase 2 — Depois do primeiro CNPJ alfanumérico persistido

**Não voltar a uma versão numeric-only.** Reaplicar `^\d{14}$` faria `VALIDATE
CONSTRAINT` falhar (ou, se aplicada como `NOT VALID`, deixaria linhas existentes fora
do contrato e bloquearia qualquer escrita futura nelas).

Opções permitidas, em ordem de preferência:

1. **Correção forward-only (preferida):** manter a constraint alfanumérica e corrigir
   o defeito na aplicação/migration seguinte. Nenhum dado é reescrito.
2. **Versão emergencial que apenas lê/preserva/mascara:** se for indispensável voltar o
   código, a versão emergencial deve aceitar e exibir CNPJs alfanuméricos sem
   descartá-los e sem recriar a constraint numérica.
3. **Write freeze:** se houver necessidade de intervenção manual, congelar escritas em
   `stores` (e no fluxo de cadastro/atualização de CNPJ) durante a janela, preservando
   integralmente os valores existentes.

Proibido em qualquer cenário da Fase 2:

- recriar a constraint `^\d{14}$`;
- executar `UPDATE` em `stores.cnpj_normalized`, `stores.cnpj_root_hash` ou
  `cnpj_lookup_cache` para "normalizar" dados alfanuméricos de volta a numérico;
- apagar lojas, esvaziar `cnpj_lookup_cache` ou remover índices para destravar a
  constraint.

## Verificação pós-rollback (Fase 1)

```sql
SELECT count(*) FROM public.stores WHERE cnpj_normalized ~ '[A-Z]';           -- deve ser 0
SELECT pg_get_constraintdef(oid), convalidated
  FROM pg_constraint
 WHERE conname = 'chk_stores_cnpj_atomic'
   AND conrelid = 'public.stores'::regclass;
SELECT count(*) FROM public.stores;                                            -- baseline 327
SELECT count(*) FROM public.stores WHERE cnpj_normalized IS NOT NULL;          -- baseline 5
SELECT count(*) FROM public.cnpj_lookup_cache;                                 -- baseline 1
```

O fingerprint `md5(string_agg(id::text || '|' || coalesce(cnpj_normalized,'') || '|' ||
cnpj_root_hash, ',' ORDER BY id))` sobre `stores` deve permanecer idêntico ao
capturado antes da migration — prova de que nenhum dado foi reescrito.

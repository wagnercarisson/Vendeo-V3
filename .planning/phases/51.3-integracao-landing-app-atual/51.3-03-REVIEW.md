## Medium

### MD-01: The "success card replaces the form" contract is no longer verified end-to-end — the legacy test's integration assertion was replaced by a mocked-child assertion

**Severity:** Medium (test masking risk; not a shipping bug today)
**Files:**
- `src/components/landing/__tests__/access-request-section.test.tsx:24-32` (the form is mocked and calls `onSuccess` manually)
- `src/components/landing/__tests__/access-request-section.test.tsx:76-85` (asserts the card only through that mock)
- `src/components/landing/__tests__/access-request-form.test.tsx` (submits the real form; asserts payload only, never `onSuccess`)
- `src/components/landing/access-request-form.tsx:49-50`
- `src/components/landing/access-request-section.tsx:25-26,53`

**Issue:** The deleted legacy test
(`src/__tests__/app/landing-page.test.tsx`, removed in `12b39ae4`) exercised the real
chain *page → section → real form → `fetch` → success card → no re-submit*. The
replacement splits it into two tests that no longer touch each other:

1. `access-request-section.test.tsx` mocks `AccessRequestForm` entirely and synthesizes
   `onSuccess` from a "Simular envio" button, so it only proves the section's own
   `setSubmitted(true)` branch.
2. `access-request-form.test.tsx` renders the real form but never passes/asserts
   `onSuccess`, so it cannot catch a regression where `onSuccess?.()` stops being called
   on a 2xx response (`access-request-form.tsx:49-50`).

There is **no** test where the real form's success path drives the card. If
`access-request-form.tsx` were refactored (e.g. `onSuccess` moved behind a different
status check, or an early `return` added), the whole suite stays green while the landing
silently stops replacing the form with "Solicitação enviada" — exactly the regression the
legacy test was there to prevent. `51.3-02-TEST-MIGRATION.md:16-17` overstates this as
migrated ("formulário deixa de ser exibido"), while the assertion only exists against a
mock.

**Fix (pick one, ~15 lines):**
```tsx
// src/components/landing/__tests__/access-request-form.test.tsx
it("chama onSuccess somente após resposta 2xx", async () => {
  const onSuccess = vi.fn();
  vi.stubGlobal("fetch", vi.fn().mockResolvedValue({ ok: true }));
  render(<AccessRequestForm onSuccess={onSuccess} />);
  fireEvent.change(screen.getByLabelText("Email"), {
    target: { value: "loja@example.com" },
  });
  fireEvent.click(screen.getByRole("button", { name: "Solicitar acesso free" }));
  await waitFor(() => expect(onSuccess).toHaveBeenCalledTimes(1));
});
```
or, preferably, restore the real integration in
`src/components/landing/__tests__/landing-page.test.tsx` (no form mock there):
stub `fetch`, submit the real e-mail field, `await` "Solicitação enviada", and assert
`container.querySelector("#acesso form")` becomes `null` while the four
`Solicitar acesso free` CTAs remain. That is the exact contract the legacy file protected.

### LW-01: `.gitignore` hides `node_modules.shared-link/` but neither `tsconfig` nor ESLint excludes it — the local setup that motivated the ignore would break `typecheck`/`lint`

**Severity:** Low (latent tooling trap; directory absent at review time, CI unaffected)
**Files:**
- `.gitignore:43`
- `tsconfig.json:22`
- `tsconfig.typecheck.json:4`
- `eslint.config.mjs:23`

**Issue:** The merge adds `node_modules.shared-link/` to `.gitignore` (a shared/symlinked
`node_modules` used to run the landing locally), but the TypeScript configs only exclude
`node_modules` and ESLint flat-config only ignores `node_modules/`. Neither pattern matches
a sibling directory named `node_modules.shared-link/`:

- `tsconfig.json:22` includes `"**/*.ts"/"**/*.tsx"`, so a re-created
  `node_modules.shared-link` would be typechecked (thousands of foreign `.d.ts`/`.ts`
  files; slow, and likely noisy errors).
- `eslint.config.mjs:23` would lint it.

The phase explicitly rejected the broad `node_modules.*` pattern to avoid hiding product
code — a defensible choice — but then the gitignore-only mitigation is internally
inconsistent: the ignored directory is exactly the one that would leak into the toolchain.
Today the tree has no such directory (`Test-Path node_modules.shared-link` → false), so
this is latent, not active.

**Fix:** Either drop `.gitignore:43` (if the directory is no longer used), or make the
tooling consistent with the ignore:
```jsonc
// tsconfig.json / tsconfig.typecheck.json
"exclude": ["node_modules", "node_modules.shared-link", ".next", "supabase/.temp/landing-lab/.next-web"]
```
```js
// eslint.config.mjs
ignores: [".next/", "node_modules/", "node_modules.shared-link/", "dist/", "supabase/.temp/landing-lab/.next-web/"],
```

### LW-02: `getSurfacePolicy()` is exported as "the single contract" but is wired to nothing, and returns `INDEX_ROBOTS` for `/` unconditionally

**Severity:** Low (dead production export + future foot-gun)
**Files:**
- `src/lib/seo/indexation-policy.ts:89-102` (function), `:62-63,92-94` (unconditional home → `INDEX_POLICY`)
- consumers: only `src/lib/seo/__tests__/indexation-policy.test.ts` and
  `src/__tests__/app/route-indexation-policy.test.ts` (verified by `git grep`)

**Issue:** The module documents `getSurfacePolicy()` as the authoritative per-surface
contract, and its test matrix (`route-indexation-policy.test.ts:39-87`) reads like the
indexation policy is enforced from it. In production code nothing calls it: indexation is
actually enforced by hand in `layout.tsx:28` (default), `page.tsx:63` (home) and the three
legal pages. Two consequences:

1. The matrix can drift from the real routes without any test failing (e.g. a new private
   prefix added to the array has no runtime effect; a route that stops declaring `noindex`
   is not caught by this file).
2. `getSurfacePolicy("/")` returns `{ robots: INDEX_ROBOTS, inSitemap: true }` with **no
   environment input**. The JSDoc says the "consumer" must gate it, but the signature
   invites the opposite; anyone wiring it into route metadata would publish
   `index, follow` in preview/local, defeating the fail-closed design.

**Fix (either):**
- Delete `getSurfacePolicy`, `SurfacePolicy`, `inSitemap` and the two duplicate matrices
  (they are test-only), keeping the constants that are actually consumed; **or**
- make the contract honest and hard to misuse:
```ts
export function getSurfacePolicy(
  pathname: string,
  ctx: { indexableEnvironment: boolean },
): SurfacePolicy {
  if (pathname === HOME_CANONICAL_PATH && ctx.indexableEnvironment) return INDEX_POLICY;
  return NOINDEX_POLICY;
}
```
and consume it from the page/layout instead of hand-rolling the checks.

### IN-01: Home metadata reads the environment at module scope while `robots()`/`sitemap()` read it per request

**File:** `src/app/page.tsx:35` vs `src/app/robots.ts:22-24`, `src/app/sitemap.ts:18-20`

`const indexable = isIndexableEnvironment()` is evaluated once at module load (build/static
metadata), whereas `robots()`/`sitemap()` re-read `VERCEL_ENV`/`NEXT_PUBLIC_SITE_URL` on
each invocation. On Vercel this is equivalent (same env at build and runtime) and the three
compiled scenarios confirm it. On a self-hosted/Docker runtime that injects env after the
build it could disagree (page `noindex` vs sitemap entry, or vice versa). Consider evaluating
inside a `generateMetadata()` for symmetry with the explicit per-call reads elsewhere.

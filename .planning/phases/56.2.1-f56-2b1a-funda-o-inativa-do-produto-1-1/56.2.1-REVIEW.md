## Warnings

### WR-03: Instance-identity contract mismatch between admin input and runtime derivation (OPEN — intentional)

**Severity:** WARNING
**File:** `src/lib/product-1-1/submission/eligibility-context.ts:26-49`, `src/app/api/admin/product-flow-authorizations/route.ts:84-94`, `src/lib/product-1-1/authorization/authorization-decision.ts:121-123`
**Issue:** Runtime derives `expectedInstanceIdentity` from `new URL(NEXT_PUBLIC_SUPABASE_URL).host` (for the documented isolated instance: `127.0.0.1:56321`), while the admin grant stores the free-form `instanceIdentity` submitted by the operator (the fixtures use `vendeo-f562a-isolated`). The two values are not reconciled or validated, so a correctly-intentioned grant targeting the isolated instance is silently ineffective at runtime (`instance_mismatch`). This fails closed, so it is not an activation hole — it is a latent operational footgun. Per the request, this item is **left open pending a human decision** and is retained here as a known warning; it is not a regression from the corrections.
**Fix:** Define one canonical instance identity shared by the admin UI, the vault/env config, and the runtime resolver (e.g. a `PRODUCT_FLOW_INSTANCE_IDENTITY` env consumed by both `resolveEligibilityContext` and the admin schema), or validate the admin value against the derived host.

### WR-06: Authorization DB contract test resolves the migration by filename suffix, not by pinned version

**Severity:** WARNING
**File:** `tests/database/product-flow-stage-authorizations.contract.test.ts:10-22` (assertions at `72-76`)
**Issue:** The test locates its target with `readdirSync(MIGRATIONS_DIR).find(name => name.endsWith("product_flow_stage_authorizations.sql"))`. Only `20261008000001_..._product_flow_stage_authorizations.sql` currently matches, so the WR-01/WR-05 assertions (`ON CONFLICT (operation_id) DO NOTHING` ×2, `RETURNING id INTO v_inserted_id` ×2, `seq BIGINT GENERATED ALWAYS AS IDENTITY`) currently pass because **migration 001 was also retrofitted** with the same logic. The authoritative, actually-applied concurrency fix lives in migration `...04_authorization_rpc_concurrency_and_order.sql`, which this test never opens. Consequently the test cannot detect drift between the two definitions: fixing/reverting only migration 004 (or only 001) leaves the suite green while the effective database behavior diverges. It is also fragile to any future migration whose name happens to end with the same suffix, since `readdirSync` order is not guaranteed.
**Fix:** Pin the migration explicitly, e.g. build the path from the known version (`path.join(MIGRATIONS_DIR, "20261008000001_f56_2b1a_product_flow_stage_authorizations.sql")`) and, for the concurrency/ordering invariants, additionally read migration 004 by its exact filename. Consider matching `/^\d+_.*product_flow_stage_authorizations\.sql$/` and asserting exactly one match to fail loudly on ambiguity.

## Info

### IN-01: Dead exported surface in the authorization module

**Severity:** INFO
**File:** `src/lib/product-1-1/authorization/authorization-decision.ts:9-13,47-56`, `src/lib/product-1-1/authorization/types.ts:16-39`
**Issue:** Re-confirmed by grep: `ENABLING_STAGES`, `isStageCompatible`, `PRODUCT_FLOW_STAGES`, `PRODUCT_FLOW_SCOPES`, and `PRODUCT_FLOW_ENVIRONMENTS` have no consumers. `isEnablingStage` inlines `stage !== "off"` and the decision inlines both compatibility checks, duplicating `isStageCompatible`. Dead exported surface invites divergence (e.g. a stage added to `ENABLING_STAGES` but not to `isEnablingStage`).
**Fix:** Remove them, or have `isEnablingStage`/the decision consume the frozen lists so the constants and logic cannot drift apart.

### IN-02: Raw database/RPC error messages returned to clients

**Severity:** INFO
**File:** `src/app/api/admin/product-flow-authorizations/route.ts:59-68` and `98-104`
**Issue:** The GET 503 branch returns `error.message`, and the POST error branch returns `{ error: message }` verbatim, leaking Postgres/RPC internals. Access is admin-only, so severity is low.
**Fix:** Return a stable error code and log the raw message server-side.

### IN-03: Repository casts DB strings to domain unions without runtime validation

**Severity:** INFO
**File:** `src/lib/product-1-1/authorization/stage-authorization-repository.ts:43-56`
**Issue:** `mapRow` casts `event_type`/`stage`/`scope` via `as` with no validation. A malformed/legacy row whose `stage` is outside the union would make `STAGE_SCOPE_COMPATIBILITY[stage]` `undefined` and throw on `.includes`, surfacing as `read_failure` (fail-closed, but for the wrong reason). The DB `CHECK` constraints make this unreachable today.
**Fix:** Validate discriminants (or reuse the Zod enums from `schemas.ts`) at the mapping boundary.

### IN-04: `product_1_1_get_campaign_credit_operation` lacks NULL-argument guards

**Severity:** INFO
**File:** `supabase/migrations/20261008000002_f56_2b1a_product_1_1_campaign_credit.sql:312-339`
**Issue:** Unlike every sibling RPC, the read function does not guard `p_campaign_id`/`p_operation_id` for NULL; a NULL silently yields an empty `WHERE` and returns `NULL` (indistinguishable from "not found").
**Fix:** Add `IF p_campaign_id IS NULL THEN RAISE EXCEPTION 'missing_campaign_id'; END IF;` (and the operation-id equivalent) for consistency.

### IN-05: `mapError` classifies by fragile substring matching

**Severity:** INFO
**File:** `src/lib/product-1-1/credit-operation/credit-operation-client.ts:54-63`
**Issue:** Error codes are inferred by `text.includes(code)` over the raw message. Postgres error messages embed the function name and can include additional context, so any future message that happens to contain another code as a substring would be misclassified. (Current codes do not collide.)
**Fix:** Prefer structured error codes (Postgres `SQLSTATE`/`DETAIL` or an explicit JSON error envelope from the RPC) over substring matching.

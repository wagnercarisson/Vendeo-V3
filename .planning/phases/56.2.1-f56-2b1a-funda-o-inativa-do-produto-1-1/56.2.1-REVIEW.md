# Phase 56.2.1: Code Review Report

**Reviewed:** 2026-10-08T21:36:57Z
**Depth:** standard
**Files Reviewed:** 27

## Summary

Review of the F56.2b1a inactive Produto 1:1 foundation: two additive, local-only SQL migrations plus the write-path lock, the stage-authorization decision/derivation/repository/service stack, the submission eligibility guard and its wiring into `generate-image`, the atomic credit-operation RPC client, the admin authorization surface, and the offline gate validator.

The core non-activation invariant holds as far as I can prove: the runtime decision (`decideProductFlowAuthorization`) is fail-closed at every branch; no code path grants an enabling stage (the RPC explicitly records a `refused` event and returns `granted: false`); `backgroundDirection` is genuinely absent from the `.strict()` legacy schema; and migration 20261008000003 removes direct `INSERT`/`UPDATE`/`DELETE` from `service_role` on the authorization table. `npx tsc` passes clean and the entire `src/lib/product-1-1` suite (112 tests) passes.

However, one committed test is **already failing** (`tests/database/product-flow-stage-authorizations.contract.test.ts`, verified by running it), and it asserts the exact `INSERT` grant that migration 20261008000003 was created to remove — the test was not updated after the write-path lock. I also found: a concurrency race in the SECURITY DEFINER authorization RPCs (no `ON CONFLICT`, so concurrent `operation_id` reuse raises a raw unique violation and the route returns 500 instead of the documented idempotent/conflict envelope), a missing CSRF guard on the admin mutation endpoint, an unreconciled instance-identity contract between the admin input and the runtime-derived `url.host`, and the credit-operations table still granting direct `INSERT`/`UPDATE` to `service_role` (bypassing the ledger-atomicity RPCs — inconsistent with the write-path lock applied to the authorization table).

## Critical Issues

### CR-01: Committed contract test asserts the removed `INSERT` grant and fails

**Severity:** BLOCKER
**File:** `tests/database/product-flow-stage-authorizations.contract.test.ts:63-65`
**Issue:** The test resolves the migration file via `name.endsWith("product_flow_stage_authorizations.sql")` — which matches **only** `20261008000001_..._product_flow_stage_authorizations.sql` (migration 003 is named `..._authorization_write_path_lock.sql`) — and asserts:

```
expect(activeSql).toMatch(
  /GRANT SELECT, INSERT ON TABLE public\.product_flow_stage_authorizations TO service_role/,
);
```

Migration 001 (line 62) actually executes `GRANT SELECT ON TABLE public.product_flow_stage_authorizations TO service_role;` — there is no `, INSERT`. Migration 003 exists precisely to remove the direct write path. Verified by running the suite:

```
npx vitest run tests/database/product-flow-stage-authorizations.contract.test.ts
→ Test Files 1 failed (1) / Tests 1 failed | 9 passed (10)
→ tests/database/product-flow-stage-authorizations.contract.test.ts:63
```

This is a guaranteed red CI gate, and the assertion encodes the pre-fix (vulnerable) behavior the write-path lock removed.
**Fix:** Align the assertion with the locked-down privilege set (and the 003 invariant):

```ts
expect(activeSql).toMatch(
  /GRANT SELECT ON TABLE public\.product_flow_stage_authorizations TO service_role/,
);
// and assert the direct write path is absent:
expect(activeSql).not.toMatch(
  /GRANT\s+[^;]*\bINSERT\b[^;]*ON TABLE public\.product_flow_stage_authorizations/,
);
```

## Warnings

### WR-01: Grant/revoke RPCs are racy — concurrent `operation_id` reuse returns a raw 500

**Severity:** WARNING
**File:** `supabase/migrations/20261008000001_f56_2b1a_product_flow_stage_authorizations.sql:125-176` (grant) and `217-240` (revoke)
**Issue:** Both RPCs implement idempotency as a `SELECT ... WHERE operation_id = p_operation_id` followed by a plain `INSERT`. There is no `ON CONFLICT` and no exception handler. Two concurrent calls with the same `operation_id` can both observe `FOUND = false` and both attempt the `INSERT`; the loser violates `uq_product_flow_stage_authorizations_operation` and raises a raw `unique_violation`. `CreditOperationClient`-style mapping does not exist here: the admin route (`src/app/api/admin/product-flow-authorizations/route.ts:96-102`) only maps the code strings in `BAD_REQUEST_CODES` to 400 and everything else to **500**. The documented idempotency guarantee ("replay equivalente preserva o resultado") therefore breaks under concurrency, and the caller gets neither the idempotent envelope nor the `409 operation_id_conflict` envelope.

Note migration 20261008000002 solved the identical problem correctly with `ON CONFLICT (campaign_id, operation_id) DO NOTHING RETURNING id` + re-select (lines 108-132); migration 001 did not follow that pattern.
**Fix:** Mirror the reserve pattern inside both RPCs:

```sql
INSERT INTO public.product_flow_stage_authorizations (...)
VALUES (...)
ON CONFLICT (operation_id) DO NOTHING
RETURNING id INTO v_inserted_id;

IF v_inserted_id IS NULL THEN
  -- re-read and return the idempotent/conflict envelope instead of raising
END IF;
```

### WR-02: Missing CSRF (`requireSameOrigin`) on the admin authorization mutation endpoint

**Severity:** WARNING
**File:** `src/app/api/admin/product-flow-authorizations/route.ts:39-71`
**Issue:** `POST` performs a privileged, audited write but never calls `requireSameOrigin`. The `generate-image` route calls it (`src/app/api/campaign/generate-image/route.ts:49`), and several sibling admin mutation routes do too (`access-requests`, `support-credit-requests`, `campaign-reports`, `data-subject-requests`). In b1a the RPC only records `off`/`refused` rows, so the impact is bounded, but a state-changing admin endpoint without CSRF protection is a real gap and inconsistent with the codebase's protected mutation routes.
**Fix:** Import and invoke `requireSameOrigin(request)` at the start of `POST` (and, for consistency, `GET`).

### WR-03: Instance-identity contract mismatch between admin input and runtime derivation

**Severity:** WARNING
**File:** `src/lib/product-1-1/submission/eligibility-context.ts:26-49`, `src/app/api/admin/product-flow-authorizations/route.ts:84-94`, `src/lib/product-1-1/authorization/authorization-decision.ts:121-123`
**Issue:** The runtime derives `expectedInstanceIdentity` from `new URL(NEXT_PUBLIC_SUPABASE_URL).host` (e.g. `127.0.0.1:56321`), while the admin grant stores whatever free-form `instanceIdentity` string the admin submits (the tests use `vendeo-f562a-isolated`). Nothing reconciles or validates the two, so a grant targeting the isolated instance will silently never match at runtime (`instance_mismatch`). It fails closed — so it is not an activation hole — but it is a latent operational footgun: a correctly-intentioned authorization can be silently ineffective, and the admin has no canonical source for the exact string.
**Fix:** Define one canonical instance identity (e.g. `PRODUCT_FLOW_INSTANCE_IDENTITY` env, shared by admin UI and runtime) or have `resolveEligibilityContext` and the admin schema validate against the same derived host value.

### WR-04: Direct `INSERT`/`UPDATE` still granted on the credit-operations table (bypasses RPC atomicity)

**Severity:** WARNING
**File:** `supabase/migrations/20261008000002_f56_2b1a_product_1_1_campaign_credit.sql:51-53`
**Issue:** `GRANT SELECT, INSERT, UPDATE ON TABLE public.product_1_1_campaign_credit_operations TO service_role;` lets any server-side caller write the operation row directly, bypassing the `reserve_credit`/`refund_credit` atomicity, the CAS transitions, and the "one credit per delivery" invariant that the migration's own header says "concentra a garantia de atomicidade". This is exactly the class of hole that migration 003 closed for the authorization table (revoke direct writes, RPC-only). `service_role` is a trusted server secret, so this is defense-in-depth rather than a privilege boundary, but the asymmetry with the authorization table is a real inconsistency.
**Fix:** `REVOKE ALL ... FROM service_role; GRANT SELECT ON TABLE ... TO service_role;` and keep write paths exclusively in the SECURITY DEFINER functions (which run as the owner and would still work).

### WR-05: `deriveCurrentAuthorization` re-sorts by millisecond-truncated timestamps, risking grant/revoke misordering

**Severity:** WARNING
**File:** `src/lib/product-1-1/authorization/derive.ts:23-26`
**Issue:** The repository already returns rows ordered by `created_at` (Postgres microseconds), but `deriveCurrentAuthorization` discards that order and re-sorts by `createdAtMs`, which `stage-authorization-repository.ts:36-40` produces via `Date.parse` (millisecond truncation). Two events in the same millisecond (e.g. a grant immediately followed by a revoke, or vice-versa) have equal `createdAtMs`; stable sort then preserves the repository's order only by luck of the input, and after any intermediate transformation the last-writer determination can invert. Since the derived *current* state is what the decision trusts, an inverted order can mask a later `revoked` with an earlier `granted`. In b1a no enabling grant can exist, so impact is currently nil, but the derivation is the load-bearing safety net for future slices.
**Fix:** Do not re-sort when the caller already guarantees ascending order, or carry a monotonic tiebreaker (the row `id`/`created_at` raw string or a microsecond epoch) so ties are deterministically resolved.

## Info

### IN-01: Unused exported constants / function (dead code)

**Severity:** INFO
**File:** `src/lib/product-1-1/authorization/authorization-decision.ts:9-13,47-56`, `src/lib/product-1-1/authorization/types.ts:16-39`
**Issue:** `ENABLING_STAGES` and `isStageCompatible` have no consumers (`isEnablingStage` inlines `stage !== "off"`, and the decision inlines both compatibility checks, duplicating `isStageCompatible`). `PRODUCT_FLOW_STAGES`, `PRODUCT_FLOW_SCOPES`, and `PRODUCT_FLOW_ENVIRONMENTS` are also unused. Dead exported surface invites drift (e.g. a future enabling stage added to `ENABLING_STAGES` but not to `isEnablingStage`).
**Fix:** Remove them, or have `isEnablingStage`/`isStageCompatible` consume the frozen lists so the constants and logic cannot diverge.

### IN-02: Raw database/RPC error messages returned to clients

**Severity:** INFO
**File:** `src/app/api/admin/product-flow-authorizations/route.ts:59-67` and `96-102`
**Issue:** The GET 503 branch returns `error.message`, and the POST error branch returns `{ error: message }` verbatim, leaking Postgres/RPC internals to the caller. Access is admin-only, so severity is low.
**Fix:** Return a stable error code and log the raw message server-side.

### IN-03: Repository casts DB strings to domain unions without runtime validation

**Severity:** INFO
**File:** `src/lib/product-1-1/authorization/stage-authorization-repository.ts:42-54`
**Issue:** `mapRow` casts `event_type`/`stage`/`scope` via `as` with no validation. A malformed/legacy row whose `stage` is outside the union would make `STAGE_SCOPE_COMPATIBILITY[stage]` `undefined` and throw on `.includes`, surfacing as `read_failure` (fail-closed, but for the wrong reason). The DB `CHECK` constraints make this unreachable today.
**Fix:** Validate discriminants (or reuse the Zod enums from `schemas.ts`) at the mapping boundary.

### IN-04: `product_1_1_get_campaign_credit_operation` lacks NULL-argument guards

**Severity:** INFO
**File:** `supabase/migrations/20261008000002_f56_2b1a_product_1_1_campaign_credit.sql:310-337`
**Issue:** Unlike every sibling RPC, the read function does not guard `p_campaign_id`/`p_operation_id` for NULL; a NULL silently yields an empty `WHERE` and returns `NULL` (indistinguishable from "not found").
**Fix:** Add `IF p_campaign_id IS NULL THEN RAISE EXCEPTION 'missing_campaign_id'; END IF;` (and the operation-id equivalent) for consistency.

### IN-05: `mapError` classifies by fragile substring matching

**Severity:** INFO
**File:** `src/lib/product-1-1/credit-operation/credit-operation-client.ts:54-63`
**Issue:** Error codes are inferred by `text.includes(code)` over the raw message. Postgres error messages embed the function name and can include additional context, so any future message that happens to contain another code as a substring would be misclassified.
**Fix:** Prefer structured error codes (e.g. Postgres `SQLSTATE`/`DETAIL` or an explicit JSON error envelope from the RPC) over substring matching.

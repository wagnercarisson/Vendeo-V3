## 1. Defeito confirmado (por que a garantia atual é insuficiente)

`drainCopyTask` (`src/lib/product-1-1/copy/copy-state.ts`) serializa as escritas numa
fila **EM MEMÓRIA** (`let writeChain: Promise<unknown>`) e usa `boundedRecord` para
limitar cada escrita por um orçamento (`COPY_PERSISTENCE_BUDGET_MS`). Isso resolve a
*espera* do chamador, mas **não** prova nem ordena a persistência:

1. **Contenção em memória.** Uma escrita que NUNCA resolve trava a fila: todas as
   escritas seguintes (`completed`/`failed`/cancelamento) ficam enfileiradas atrás
   dela e só rodam quando a escrita travada resolver.
2. **Retorno por TIMEOUT não é prova.** `boundedRecord` resolve `"timeout"` quando o
   teto esgota — mas o `Promise` REAL da escrita continua VIVO. O drenador retorna
   por TEMPO, não por CONFIRMAÇÃO da persistência.
3. **A ordem morre com o processo/request.** Se a escrita travada resolver DEPOIS do
   retorno da requisição, ela e o restante da fila executam FORA do ciclo — e a
   **última** a gravar no banco pode ser uma escrita `pending`/`completed` que
   **sobrescreve o estado final/cancelado**. A única garantia é a fila em memória;
   ela deixa de existir quando a request termina.
4. **"Não confirmado" não é representável.** Hoje um timeout degrada para `failed` e
   o drenador retorna `{ state: "failed", canceled }` — uma afirmação de estado
   FINAL persistido que, de fato, **NÃO** foi confirmada.

**Objetivo do design:** mover a garantia de ORDEM/TRANSIÇÃO para o BANCO (CAS /
transição condicional com sequência monotônica), de modo que (a) uma escrita
atrasada/travada NUNCA sobrescreva o estado final/cancelado, e (b) um timeout de
persistência seja representado como **NÃO CONFIRMADO**.

## 2. Design do banco — `20261009000005_f56_2b1b_copy_state.sql` (EXPANDIDA)

### 2.1 Colunas adicionais em `public.product_1_1_copy_state`

```sql
ALTER TABLE public.product_1_1_copy_state
  -- Sequência MONOTÔNICA: cada escrita ACEITA incrementa; é a referência de ordem.
  ADD COLUMN IF NOT EXISTS revision            BIGINT      NOT NULL DEFAULT 0,
  -- Estado FINAL (não-reversível): 'completed' | 'failed' são terminais.
  ADD COLUMN IF NOT EXISTS terminal            BOOLEAN     NOT NULL DEFAULT false,
  -- CONFIRMAÇÃO da persistência (a escrita resolveu? o drenador confirmou?).
  ADD COLUMN IF NOT EXISTS confirmation        TEXT        NOT NULL DEFAULT 'unconfirmed',
  ADD COLUMN IF NOT EXISTS confirmed_at        TIMESTAMPTZ,
  -- Origem da última escrita ACEITA (auditoria: 'commit' | 'drainer' | 'budget').
  ADD COLUMN IF NOT EXISTS last_write_source   TEXT;

ALTER TABLE public.product_1_1_copy_state
  ADD CONSTRAINT chk_p1_1_copy_state_confirmation
    CHECK (confirmation IN ('confirmed', 'unconfirmed')) NOT VALID;
```

- `terminal` = `state IN ('completed','failed')` (a coluna é derivada e **congelada**
  pela função de escrita — o caller não a define livremente).
- `confirmation` distingue a persistência **PROVADA** (`confirmed`) da **NÃO
  CONFIRMADA** (`unconfirmed`). Um `pending` é, por definição, `unconfirmed`.

### 2.2 CAS + guard de transição — função `product_1_1_apply_copy_state`

Uma ÚNICA função `SECURITY DEFINER` aplica a escrita de forma ATÔMICA e CONDICIONAL
(compare-and-set sobre o estado atual), incrementando a sequência:

```sql
CREATE OR REPLACE FUNCTION public.product_1_1_apply_copy_state(
  p_campaign_id   UUID,
  p_operation_id  UUID,
  p_state         TEXT,          -- 'pending' | 'completed' | 'failed'
  p_confirmation  TEXT,          -- 'confirmed' | 'unconfirmed'
  p_copy_text     TEXT DEFAULT NULL,
  p_copy_payload  JSONB DEFAULT NULL,
  p_source        TEXT DEFAULT NULL
) RETURNS TABLE (applied BOOLEAN, state TEXT, revision BIGINT, confirmation TEXT)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  v_terminal BOOLEAN := p_state IN ('completed', 'failed');
BEGIN
  -- 1) Primeira escrita: cria a linha (sempre aceita; idempotência via UNIQUE).
  INSERT INTO public.product_1_1_copy_state AS cs
    (campaign_id, operation_id, state, copy_text, copy_payload,
     revision, terminal, confirmation, confirmed_at, last_write_source, updated_at)
  VALUES
    (p_campaign_id, p_operation_id, p_state, p_copy_text, p_copy_payload,
     0, v_terminal,
     p_confirmation,
     CASE WHEN p_confirmation = 'confirmed' THEN now() END,
     p_source, now())
  ON CONFLICT (campaign_id, operation_id) DO UPDATE
    SET state         = EXCLUDED.state,
        copy_text     = COALESCE(EXCLUDED.copy_text, cs.copy_text),
        copy_payload  = COALESCE(EXCLUDED.copy_payload, cs.copy_payload),
        revision      = cs.revision + 1,
        terminal      = EXCLUDED.terminal,
        confirmation  = EXCLUDED.confirmation,
        confirmed_at  = CASE WHEN EXCLUDED.confirmation = 'confirmed' THEN now()
                             ELSE cs.confirmed_at END,
        last_write_source = EXCLUDED.last_write_source,
        updated_at    = now()
    -- ── CAS / GUARD de transição (a ORDEM é imposta AQUI, não na memória) ──
    WHERE
      -- (a) NUNCA sobrescreve um terminal CONFIRMADO: estado final é FINAL.
      NOT (cs.terminal AND cs.confirmation = 'confirmed')
      -- (b) NUNCA troca o VALOR de um estado terminal (failed↛completed e vice-versa).
      AND NOT (cs.terminal AND EXCLUDED.state <> cs.state)
    RETURNING cs.applied, cs.state, cs.revision, cs.confirmation
    INTO applied, state, revision, confirmation;

  IF NOT FOUND THEN
    -- CAS REJEITOU (estado final confirmado ou troca de terminal): devolve a linha
    -- VIGENTE sem alterá-la — o caller sabe que a escrita NÃO foi aplicada.
    SELECT false, cs.state, cs.revision, cs.confirmation
      INTO applied, state, revision, confirmation
      FROM public.product_1_1_copy_state cs
      WHERE cs.campaign_id = p_campaign_id AND cs.operation_id = p_operation_id;
  END IF;
  RETURN NEXT;
END;
$$;
```

**Invariantes garantidas pelo banco (independentemente do Promise):**

| Cenário | Resultado | Regra |
|---|---|---|
| Escrita terminal **confirmada** primeiro | Tudo depois é **rejeitado** (`applied=false`) | (a) |
| Escrita `completed` chega após `failed` terminal | **Rejeitada** (não troca o valor terminal) | (b) |
| Escrita `pending` atrasada chega após o terminal confirmado | **Rejeitada** (não sobrescreve) | (a) |
| Escrita terminal **unconfirmed** primeiro, depois a `confirmed` do MESMO estado | **Upgrade** `unconfirmed → confirmed` (mesmo `state`) | (a)+(b) |
| Escrita `unconfirmed` chega após terminal `confirmed` | **Rejeitada** | (a) |

> A `revision` MONOTÔNICA permite reconstruir a ORDEM de tentativas de escrita
> aceitas (auditoria), mas a garantia de "quem prevalece" é do CAS — não da ordem
> de chegada.

### 2.3 Cancelamento ATÔMICO — função `product_1_1_cancel_copy`

Hoje o drenador faz duas escritas separadas (`failed` no estado + `INSERT` no
cancelamento) que podem divergir. A versão atômica aplica o terminal via CAS E
registra o cancelamento **na MESMA transação** (idempotente pelo UNIQUE existente):

```sql
CREATE OR REPLACE FUNCTION public.product_1_1_cancel_copy(
  p_campaign_id UUID, p_operation_id UUID, p_reason TEXT
) RETURNS TABLE (applied BOOLEAN, state TEXT, confirmation TEXT, canceled BOOLEAN)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  v_applied BOOLEAN; v_state TEXT; v_conf TEXT;
BEGIN
  SELECT a.applied, a.state, a.confirmation
    INTO v_applied, v_state, v_conf
    FROM public.product_1_1_apply_copy_state(
      p_campaign_id, p_operation_id, 'failed', 'confirmed', NULL, NULL, 'budget') a;

  -- O cancelamento só é registrado se o estado terminal foi ACEITO/OBSERVADO como
  -- 'failed' (nunca sobre um 'completed' confirmado).
  IF v_state = 'failed' THEN
    INSERT INTO public.product_1_1_copy_cancellations (campaign_id, operation_id, reason)
    VALUES (p_campaign_id, p_operation_id, p_reason)
    ON CONFLICT (campaign_id, operation_id) DO NOTHING;   -- idempotente
    RETURN QUERY SELECT v_applied, v_state, v_conf, true;
  ELSE
    RETURN QUERY SELECT v_applied, v_state, v_conf, false;
  END IF;
END;
$$;
```

### 2.4 "NÃO CONFIRMADO" durável

- Se o drenador **estoura o orçamento** antes de a escrita de estado resolver, ele
  NÃO pode afirmar o terminal. A representação persistida honesta é:
  - a linha permanece **`pending` com `confirmation='unconfirmed'`** (a escrita
    terminal simplesmente não foi aplicada), **ou**
  - se a escrita travar e ainda assim aplicar mais tarde sob a forma
    `confirmation='unconfirmed'`, o CAS nunca a deixa ir além de `unconfirmed` para
    um estado terminal NÃO-confirmado — e o **upgrade para `confirmed`** só ocorre
    com uma escrita que RESOLVEU.
- O **leitor** (`readCopyDelivery`) passa a devolver `confirmation`; a UI trata
  `confirmation='unconfirmed'` como **NÃO prova** (feedback SEGURO — nunca
  `delivered`/sucesso falso), exatamente como hoje trata `failed`.
- Um `pending`/ausente **não** é `completed`: nenhuma superfície afirma sucesso sem
  `state='completed' AND confirmation='confirmed'`.

## 3. Mudanças de código propostas (NÃO aplicadas nesta tarefa)

`src/lib/product-1-1/copy/copy-state.ts`:

1. `recordCopyState`/`recordCancellation` passam a chamar as RPCs
   (`client.rpc("product_1_1_apply_copy_state", {...})` /
   `client.rpc("product_1_1_cancel_copy", {...})`), que retornam
   `{ applied, state, revision, confirmation }`.
2. `DrainCopyTaskResult` ganha `confirmation: "confirmed" | "unconfirmed"` (ou um
   estado `"unconfirmed"`), e `state` só pode ser `"completed"` quando
   `applied === true` **e** `confirmation === "confirmed"`.
3. O drenador **deixa de** manter a fila `writeChain` em memória como garantia de
   ordem: cada escrita é um CAS independente no banco; a fila em memória vira, no
   máximo, uma OTIMIZAÇÃO (não uma garantia).
4. O caminho de cancelamento passa a usar a RPC ATÔMICA `product_1_1_cancel_copy`
   (estado `failed` + cancelamento numa transação).
5. `readCopyDelivery` devolve `confirmation`; `display.ts`/UI tratam
   `unconfirmed` como NÃO-prova (feedback seguro âmbar — sem `delivered`).

## 4. Prova esperada (quando aprovado/aplicado)

- **CAS vence a fila em memória:** uma escrita de STORE atrasada que resolve APÓS o
  terminal confirmado é REJEITADA pelo banco (`applied=false`) — o estado final
  permanece (prova por Postgres real: `revision` não incrementa; `state` inalterado).
- **Terminal é FINAL:** `completed` não sobrescreve `failed` confirmado e vice-versa.
- **Timeout ⇒ NÃO CONFIRMADO:** uma escrita que estoura o orçamento deixa a linha
  `pending`/`unconfirmed` (ou terminal `unconfirmed`), e o drenador retorna
  `confirmation="unconfirmed"` — nunca `completed` provado.
- **Cancelamento atômico:** não existe estado `failed` sem cancelamento nem
  cancelamento sobre `completed` confirmado.

---

## 5. Por que a migration é necessária

A garantia de ORDEM/TRANSIÇÃO depende de um estado persistido com CAS
(`terminal`/`confirmation`/`revision`) que o banco impõe. Sem a migration, não há
onde representar "NÃO CONFIRMADO" nem onde rejeitar a escrita atrasada — a fila em
memória continuaria sendo a única (frágil) garantia.

---

## 6. Decisão: P2 fica PENDENTE do design aprovado (sem código agora)

A parte "code-only" segura seria apenas mudar o **valor de retorno** do drenador
(ex.: adicionar `confirmation`/`"unconfirmed"` em `DrainCopyTaskResult`). Isso **NÃO
é seguro nem útil isoladamente**:

- o consumidor de leitura é a PÁGINA/UI, que lê o estado __persistido__ em
  `product_1_1_copy_state.state` (CHECK `'pending'|'completed'|'failed'`) — uma
  mudança só no retorno do drenador (que o orquestrador DESCARTA, best-effort) não
  teria visibilidade alguma e não alteraria o que o lojista vê;
- reportar `confirmation` sem a coluna persistida criaria uma semântica de
  "não confirmado" que o banco não sustenta (um `pending`/ausente ainda é
  indistinguível de um terminal não persistido em leitura);
- alterar a união `DrainCopyTaskResult.state` muda o contrato de `copy-state.ts` e
  seus testes sem entregar a garantia real.

Por isso, **P2 permanece PENDENTE até a aprovação deste design** (migration +
código aplicados juntos, sob o gate do Plano 09/O2). Nenhuma migration foi
expandida/aplicada e nenhum arquivo de código de P2 foi alterado nesta tarefa.

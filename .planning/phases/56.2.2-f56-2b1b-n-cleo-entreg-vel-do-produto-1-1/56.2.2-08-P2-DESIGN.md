## 1. Defeito confirmado (por que a garantia atual é insuficiente)

`drainCopyTask` (`src/lib/product-1-1/copy/copy-state.ts`) serializa as escritas numa
fila **EM MEMÓRIA** (`let writeChain: Promise<unknown>`) e usa `boundedRecord` para
limitar cada escrita por um orçamento (`COPY_PERSISTENCE_BUDGET_MS`). Isso resolve a
*espera* do chamador, mas **não** prova nem ordena a persistência:

1. **Contenção em memória.** Uma escrita que NUNCA resolve trava a fila: todas as
   escritas seguintes (`completed`/`failed`/cancelamento) ficam enfileiradas atrás
   dela e só rodam quando a escrita travada resolver.
2. **Retorno por TIMEOUT não é prova.** `boundedRecord` resolve `"timeout"` quando o
   teto esgota — mas o `Promise` REAL da escrita continua VIVO. O drenador retorna
   por TEMPO, não por CONFIRMAÇÃO da persistência.
3. **A ordem morre com o processo/request.** Se a escrita travada resolver DEPOIS do
   retorno da requisição, ela e o restante da fila executam FORA do ciclo — e a
   **última** a gravar no banco pode ser uma escrita `pending`/`completed` que
   **sobrescreve o estado final/cancelado**. A única garantia é a fila em memória;
   ela deixa de existir quando a request termina.
4. **"Não confirmado" não distinguível localmente.** Hoje um timeout degrada para
   `failed` e o drenador retorna `{ state: "failed", canceled }` — uma afirmação de
   estado FINAL persistido que, de fato, **NÃO** foi observada pelo chamador.

**Objetivo do design:** mover a garantia de ORDEM/TRANSIÇÃO para o BANCO (transição
CONDICIONAL + terminal PROTEGIDO + replay vinculado a CONTEÚDO + cancelamento
ATÔMICO), de modo que (a) uma escrita atrasada/travada NUNCA sobrescreva o estado
final/cancelado; e (b) a incerteza LOCAL do chamador (timeout) seja resolvida por
uma **RE-LEITURA** do estado efetivamente persistido — nunca por um segundo write.

## 2. Design do banco — `20261009000005_f56_2b1b_copy_state.sql` (REVISADA)

> **AUTORADO apenas.** Não aplicar (`db push`/`migration up`); a aplicação local

### 2.1 Conjunto MÍNIMO de colunas — **ZERO colunas novas**

A versão anterior propunha CINCO colunas (`revision`, `terminal`, `confirmation`,
`confirmed_at`, `last_write_source`). Nenhuma tem função PROVADA; todas são
deriváveis ou desnecessárias:

| Coluna proposta (removida) | Por que NÃO é necessária |
|---|---|
| `terminal` | **Derivável** de `state IN ('completed','failed')` — expressão booleana trivial na própria RPC; não precisa ser persistida nem congelada. |
| `confirmation` / `confirmed_at` | **Removidas (A1).** "Não confirmado" é incerteza LOCAL do CHAMADOR, não um fato do BANCO: se a RPC grava e a resposta se perde, **uma leitura posterior prova a persistência**. Exigir um SEGUNDO write só para "confirmar o recebimento do primeiro" é errado. O `state` PERSISTIDO é AUTORITATIVO. |
| `revision` | **Removida (A4).** Um contador INCREMENTAL **sem comparação de valor esperado NÃO é CAS** por si só (não rejeita nada). Não há uso de auditoria que `updated_at` não cubra. |
| `last_write_source` | **Removida.** Sem função provada (não governa transição nem leitura; era só metadado de auditoria sem consumidor). |

**Conclusão:** o schema existente — `state` (CHECK `'pending'|'completed'|'failed'`),
`copy_text`, `copy_payload`, `updated_at`, `UNIQUE (campaign_id, operation_id)` — é
SUFICIENTE. As quatro garantias (transição condicional, terminal protegido, replay
vinculado a conteúdo, cancelamento atômico) são expressas por RPC sobre essas
colunas. **Nenhum `ALTER TABLE`.**

> Se no futuro se exigir um CAS VERDADEIRO com valor esperado (otimista), a adição
> correta seria uma coluna `revision BIGINT` **acompanhada** de um parâmetro
> `p_expected_revision` comparado explicitamente na RPC. Sem essa comparação, a
> coluna não é CAS e não deve existir (A4).

### 2.2 Transição CONDICIONAL + terminal PROTEGIDO + replay por CONTEÚDO — RPC `product_1_1_apply_copy_state`

Uma ÚNICA função `SECURITY DEFINER` aplica a escrita de forma ATÔMICA e CONDICIONAL.
A ORDEM é imposta AQUI (no banco), não na fila em memória. O retorno é um objeto
explícito `{ applied, outcome, state }` — **não** há coluna `applied` (a versão
anterior devolvia `cs.applied`, que NÃO EXISTE; corrigido em A4).

```sql
CREATE OR REPLACE FUNCTION public.product_1_1_apply_copy_state(
  p_campaign_id  UUID,
  p_operation_id UUID,
  p_state        TEXT,          -- 'pending' | 'completed' | 'failed'
  p_copy_text    TEXT  DEFAULT NULL,
  p_copy_payload JSONB DEFAULT NULL
) RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  v_row        public.product_1_1_copy_state%ROWTYPE;
  v_terminal   BOOLEAN;
  v_equivalent BOOLEAN;
  v_inserted   UUID;
BEGIN
  IF p_campaign_id  IS NULL THEN RAISE EXCEPTION 'missing_campaign_id';  END IF;
  IF p_operation_id IS NULL THEN RAISE EXCEPTION 'missing_operation_id'; END IF;
  IF p_state IS NULL OR p_state NOT IN ('pending','completed','failed') THEN
    RAISE EXCEPTION 'invalid_state';
  END IF;

  -- TRAVA por operação: serializa as transições DESTA operação (a ordem mora aqui).
  SELECT * INTO v_row
  FROM public.product_1_1_copy_state
  WHERE campaign_id = p_campaign_id AND operation_id = p_operation_id
  FOR UPDATE;

  -- 1) PRIMEIRA escrita: cria a linha. `ON CONFLICT DO NOTHING` resolve a corrida
  --    de dois creadores concorrentes sem erro incidental de unicidade.
  IF NOT FOUND THEN
    INSERT INTO public.product_1_1_copy_state
      (campaign_id, operation_id, state, copy_text, copy_payload, updated_at)
    VALUES
      (p_campaign_id, p_operation_id, p_state, p_copy_text, p_copy_payload, now())
    ON CONFLICT (campaign_id, operation_id) DO NOTHING
    RETURNING id INTO v_inserted;

    IF v_inserted IS NULL THEN
      -- PERDEU a corrida: NÃO aplicou. O chamador RE-LÊ para conhecer o persistido.
      RETURN jsonb_build_object('applied', false, 'outcome', 'rejected', 'state', NULL);
    END IF;

    RETURN jsonb_build_object('applied', true, 'outcome', 'applied', 'state', p_state);
  END IF;

  -- `terminal` é DERIVADO do `state` (nenhuma coluna dedicada — A4).
  v_terminal := v_row.state IN ('completed','failed');

  -- 2) TERMINAL PROTEGIDO: um estado final é FINAL. Só um replay EQUIVALENTE é aceito.
  IF v_terminal THEN
    IF v_row.state = p_state THEN
      -- Replay do MESMO estado terminal: exige CONTEÚDO EQUIVALENTE (A3).
      v_equivalent := (v_row.copy_text    IS NOT DISTINCT FROM p_copy_text)
                  AND (v_row.copy_payload IS NOT DISTINCT FROM p_copy_payload);
      IF v_equivalent THEN
        -- Idempotente: NADA é gravado (nenhum "upgrade" — o persistido já é a verdade).
        RETURN jsonb_build_object('applied', false, 'outcome', 'idempotent', 'state', v_row.state);
      END IF;
      -- MESMO estado, CONTEÚDO DIVERGENTE ⇒ CONFLITO (nunca sucesso enganoso).
      RETURN jsonb_build_object('applied', false, 'outcome', 'conflict', 'state', v_row.state);
    END IF;
    -- Estado terminal DIFERENTE (completed↔failed) ou escrita não-terminal tardia ⇒ REJEITADO.
    RETURN jsonb_build_object('applied', false, 'outcome', 'rejected', 'state', v_row.state);
  END IF;

  -- 3) NÃO-terminal (`pending`): replay de `pending` é no-op idempotente.
  IF v_row.state = p_state THEN
    RETURN jsonb_build_object('applied', false, 'outcome', 'idempotent', 'state', v_row.state);
  END IF;

  -- Transição permitida (`pending` → `completed`/`failed`).
  UPDATE public.product_1_1_copy_state
     SET state        = p_state,
         copy_text    = p_copy_text,
         copy_payload = p_copy_payload,
         updated_at   = now()
   WHERE id = v_row.id;

  RETURN jsonb_build_object('applied', true, 'outcome', 'applied', 'state', p_state);
END;
$$;
```

**Invariantes garantidas pelo banco (independentemente do Promise):**

| Cenário | Resultado (`outcome`) | Regra |
|---|---|---|
| Escrita terminal chega DEPOIS de um terminal persistido (`completed`→`failed` etc.) | **rejected** (`applied=false`) — persistido INALTERADO | terminal protegido |
| Escrita `pending` atrasada chega após um terminal | **rejected** — não sobrescreve | terminal protegido |
| Replay do MESMO terminal com conteúdo EQUIVALENTE | **idempotent** — nenhuma escrita | replay por conteúdo (A3) |
| Replay do MESMO terminal com conteúdo DIVERGENTE | **conflict** | replay por conteúdo (A3) |
| Escrita `pending` → `completed`/`failed` | **applied** | transição permitida |
| `pending` → `pending` | **idempotent** | no-op |

### 2.3 Cancelamento ATÔMICO — RPC `product_1_1_cancel_copy`

Hoje o drenador faz duas escritas separadas (`failed` no estado + `INSERT` no
cancelamento) que podem divergir. A versão atômica aplica o terminal via a RPC
condicional E registra o cancelamento **na MESMA transação** (idempotente pelo
UNIQUE existente). A **ATOMICIDADE vale para a AÇÃO DE CANCELAR** — não para toda
falha:

> **CORREÇÃO (A4):** a versão anterior afirmava "nenhum `failed` existe sem
> cancelamento". Isso é **falso**: uma FALHA COMUM da copy (erro de geração) é
> persistida como `failed` SEM cancelamento algum. O que a atomicidade garante é
> que, QUANDO há cancelamento por orçamento, o `failed` terminal e o motivo do
> cancelamento são gravados numa ÚNICA transação (nunca um `failed` sem o motivo,
> nem um motivo sem o `failed`).

```sql
CREATE OR REPLACE FUNCTION public.product_1_1_cancel_copy(
  p_campaign_id  UUID,
  p_operation_id UUID,
  p_reason       TEXT
) RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  v_apply JSONB;
  v_state TEXT;
BEGIN
  IF p_campaign_id  IS NULL THEN RAISE EXCEPTION 'missing_campaign_id';  END IF;
  IF p_operation_id IS NULL THEN RAISE EXCEPTION 'missing_operation_id'; END IF;
  IF p_reason IS NULL OR p_reason = '' THEN RAISE EXCEPTION 'missing_reason'; END IF;

  -- (1) Aplica o terminal `failed` sob a MESMA transação (mesmo escopo atômico).
  v_apply := public.product_1_1_apply_copy_state(
    p_campaign_id, p_operation_id, 'failed', NULL, NULL);
  v_state := v_apply->>'state';

  -- (2) O cancelamento só é registrado quando o estado terminal OBSERVADO é
  --     `failed` (nunca sobre um `completed` persistido). Idempotente pelo UNIQUE.
  IF v_state = 'failed' THEN
    INSERT INTO public.product_1_1_copy_cancellations (campaign_id, operation_id, reason)
    VALUES (p_campaign_id, p_operation_id, p_reason)
    ON CONFLICT (campaign_id, operation_id) DO NOTHING;
    RETURN jsonb_build_object(
      'applied', (v_apply->>'applied')::boolean, 'state', 'failed', 'canceled', true);
  END IF;

  -- Já `completed` persistido (ou corrida de criação) ⇒ NÃO cancela.
  RETURN jsonb_build_object(
    'applied', (v_apply->>'applied')::boolean, 'state', v_state, 'canceled', false);
END;
$$;
```

### 2.4 "NÃO CONFIRMADO" é LOCAL (do CHAMADOR), resolvido por **RE-LEITURA** (A1)

Não existe — e NÃO deve existir — uma coluna `confirmation`/`confirmed_at`. A
semântica correta:

- O **`state` PERSISTIDO é AUTORITATIVO**. A verdade é o que está na linha.
- Um **timeout LOCAL** (a RPC de escrita não respondeu dentro do orçamento do
  chamador) NÃO significa que a escrita não ocorreu — significa apenas que o
  chamador **ainda NÃO SABE**. A resolução é uma **RE-LEITURA**
  (`readCopyDelivery`): se a linha já está `completed` com o texto, a persistência
  está PROVADA (sem nenhum segundo write); se ainda está `pending` (ou ausente), a
  escrita não foi aplicada.
- **NUNCA** um segundo write só para "confirmar o recebimento" do primeiro (isso era
  o defeito da versão anterior: um "upgrade" `unconfirmed → confirmed` exigindo
  outro write).
- O **leitor** (`readCopyDelivery`) devolve o estado/`copy_text`/`copy_payload`
  persistidos (a RPC de leitura já existente; **sem** campo `confirmation`).
- A **UI deriva feedback SEGURO do que está REALMENTE persistido** (nunca de um
  sucesso presumido): `completed` + conteúdo ⇒ entrega; `failed`/cancelado ⇒
  feedback âmbar; `pending`/ausente ⇒ sem entrega. Incerto local ⇒ **re-ler** até
  resolver; nunca afirmar sucesso sem `state='completed'` persistido.
- O retorno LOCAL do drenador pode sinalizar incerteza (ex.: um valor local
  `"unconfirmed"` quando o orçamento esgota sem observação) — mas esse valor **NÃO
  é persistido** e **não** é usado para renderizar terminal: é apenas um gatilho
  para a RE-LEITURA.

### 2.5 Privilégios/RLS — **RPC-only writes** (A2)

Manter `INSERT`/`UPDATE` direto para `service_role` permite **BURLAR as transições**
(um caller faria `UPDATE` sem passar pela RPC condicional). A correção:

- `service_role` recebe **SELECT ONLY** em `product_1_1_copy_state` e em
  `product_1_1_copy_cancellations`.
- `REVOKE INSERT, UPDATE, DELETE FROM service_role` (explícito; idempotente sobre o
  grant atual).
- **TODAS** as mutações passam pelas RPCs `SECURITY DEFINER`
  (`product_1_1_apply_copy_state`, `product_1_1_cancel_copy`), com
  `REVOKE ALL ON FUNCTION ... FROM PUBLIC, anon, authenticated` +
  `GRANT EXECUTE ... TO service_role` (mesmo padrão das migrations `...000001` /
  `...000003`).
- `anon`/`authenticated` permanecem **sem acesso** (REVOKE ALL).
- A policy de `service_role` passa de `FOR ALL` para `FOR SELECT` (alinhada ao padrão
  de `product_1_1_generation_attempt_claims`); o gate real é o privilégio de tabela.
- O bloco **REVERT** é estendido (drop das funções + restauração dos grants
  originais `SELECT, INSERT[, UPDATE]` — ver §5).

```sql
-- REVISÃO de grants (idempotente; a migration original concedia INSERT/UPDATE)
REVOKE INSERT, UPDATE, DELETE ON TABLE public.product_1_1_copy_state FROM service_role;
GRANT  SELECT ON TABLE public.product_1_1_copy_state TO service_role;

REVOKE INSERT, UPDATE, DELETE ON TABLE public.product_1_1_copy_cancellations FROM service_role;
GRANT  SELECT ON TABLE public.product_1_1_copy_cancellations TO service_role;

DROP POLICY IF EXISTS "Service role can read/write product 1:1 copy state"
  ON public.product_1_1_copy_state;
CREATE POLICY "Service role reads product 1:1 copy state"
  ON public.product_1_1_copy_state FOR SELECT TO service_role USING (true);

DROP POLICY IF EXISTS "Service role can read/insert product 1:1 copy cancellations"
  ON public.product_1_1_copy_cancellations;
CREATE POLICY "Service role reads product 1:1 copy cancellations"
  ON public.product_1_1_copy_cancellations FOR SELECT TO service_role USING (true);

REVOKE ALL ON FUNCTION public.product_1_1_apply_copy_state(UUID, UUID, TEXT, TEXT, JSONB)
  FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.product_1_1_apply_copy_state(UUID, UUID, TEXT, TEXT, JSONB)
  TO service_role;

REVOKE ALL ON FUNCTION public.product_1_1_cancel_copy(UUID, UUID, TEXT)
  FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.product_1_1_cancel_copy(UUID, UUID, TEXT)
  TO service_role;
```

## 3. Tabela de TRANSIÇÕES (revisada)

`state ∈ {pending, completed, failed}`; terminal = `completed|failed`.
Conteúdo = `(copy_text, copy_payload)` comparado com semântica NULL-safe
(`IS NOT DISTINCT FROM`).

| Estado PERSISTIDO | Escrita que chega | Conteúdo vs. persistido | `outcome` | Efeito |
|---|---|---|---|---|
| (ausente) | qualquer válido | — | `applied` | cria a linha |
| `pending` | `pending` | — | `idempotent` | no-op |
| `pending` | `completed` | — | `applied` | transição |
| `pending` | `failed` | — | `applied` | transição |
| `completed` | `completed` | **equivalente** | `idempotent` | no-op (nenhum write) |
| `completed` | `completed` | **divergente** | **`conflict`** | persistido INALTERADO |
| `completed` | `failed` | — | `rejected` | terminal protegido |
| `completed` | `pending` | — | `rejected` | terminal protegido |
| `failed` | `failed` | equivalente (null≈null) | `idempotent` | no-op |
| `failed` | `completed` | — | `rejected` | terminal protegido |
| `failed` | `pending` | — | `rejected` | terminal protegido |

**Contrato de CONFLITO (A3):** "mesmo estado ≠ mesma requisição". Para um estado
terminal, um replay com o MESMO `state` mas conteúdo DIVERGENTE devolve
`{ applied: false, outcome: 'conflict' }`; o registro persistido permanece
INALTERADO e o chamador **NÃO** pode tratá-lo como sucesso. Isso vale **ANTES de
qualquer "upgrade"** de confirmação (não há upgrade — A1).

## 4. Mudanças de código propostas (NÃO aplicadas nesta tarefa)

`src/lib/product-1-1/copy/copy-state.ts`:

1. `recordCopyState` passa a chamar `client.rpc("product_1_1_apply_copy_state", {...})`
   e trata o retorno `{ applied, outcome, state }` (`applied`/`idempotent` = ok;
   `conflict`/`rejected` = não aplicado — o chamador decide/re-lê).
2. `recordCancellation` passa a chamar `client.rpc("product_1_1_cancel_copy", {...})`
   (estado `failed` + cancelamento numa ÚNICA transação).
3. O drenador **deixa de** manter a fila `writeChain` como GARANTIA de ordem: cada
   escrita é uma transição condicional no banco; a fila em memória vira, no máximo,
   uma OTIMIZAÇÃO.
4. `DrainCopyTaskResult` ganha um sinal LOCAL `"unconfirmed"` (incerteza do
   CHAMADOR no timeout) — **não persistido** e **não** usado para renderizar
   terminal: resolve-se por `readCopyDelivery` (§2.4). Sem `confirmation` persistido.
5. `readCopyDelivery` continua devolvendo `{ state, copyText, copyPayload }`
   (o estado AUTORITATIVO). **Nenhum** campo `confirmation` é adicionado.
6. A UI trata `pending`/ausente/`"unconfirmed"` local como **NÃO prova** (feedback
   seguro — nunca `delivered`/sucesso falso), e **re-lê** para resolver a incerteza.

## 5. PROVAS a serem adicionadas (quando aprovado/aplicado)

> Doc-only nesta tarefa: nenhum teste é escrito agora. Lista do que a implementação
> aprovada DEVE provar (Postgres real, na instância isolada do Plano 09).

1. **Ordem/transição no BANCO** — uma escrita `pending` ATRASADA que chega após um
   terminal persistido é **rejected** (`applied=false`); o `state` persistido
   permanece INALTERADO (nenhuma sobrescrita tardia). *(A4/§2.2)*
2. **Terminal protegido** — `completed` não sobrescreve `failed` nem vice-versa
   (`rejected`); o terminal é FINAL. *(A4/§2.2)*
3. **Replay por CONTEÚDO (A3)** —
   (a) replay de `completed` com conteúdo **EQUIVALENTE** ⇒ `idempotent`, nenhuma
   escrita, exatamente UMA linha;
   (b) replay de `completed` com `copy_text` **DIVERGENTE** ⇒ `conflict`;
   (c) replay de `completed` com `copy_payload` **DIVERGENTE** ⇒ `conflict`;
   (d) em todos os conflitos o registro persistido permanece INALTERADO.
4. **Timeout local resolvido por RE-LEITURA (A1)** — a RPC de escrita "pendura" além
   do orçamento do chamador ⇒ o drenador retorna o sinal LOCAL `"unconfirmed"`;
   **nenhum** segundo write de confirmação é emitido; um `readCopyDelivery`
   subsequente devolve o estado REALMENTE persistido (`completed`+texto se a escrita
   chegou; `pending` se não) — a UI só afirma entrega quando a LEITURA mostra
   `completed` persistido (nunca sucesso falso).
5. **Cancelamento ATÔMICO (A4)** — `cancel_copy` aplica `failed` + registra o motivo
   numa ÚNICA transação; `readCopyCancellation` devolve o motivo; **NUNCA** cancela
   sobre um `completed` persistido (`canceled=false`, nenhuma linha de cancelamento).
6. **Falha COMUM sem cancelamento (correção A4)** — um `apply('failed')` simples
   (erro de geração) resulta em `state='failed'` **SEM** linha de cancelamento,
   provando que **`failed` NÃO exige cancelamento** (a atomicidade é da AÇÃO de
   cancelar).
7. **RPC-only writes (A2)** — `service_role` tem **SELECT only**; um `INSERT`/
   `UPDATE`/`DELETE` DIRETO de `service_role` nas tabelas é **NEGADO**; as mutações
   só sucedem pelas RPCs; `anon`/`authenticated` são negados.
8. **Cancelamento idempotente** — `cancel_copy` reenviado ⇒ uma só linha de
   cancelamento (UNIQUE) e estado `failed` estável.
9. **Nenhuma coluna nova** — a expansão da migration NÃO adiciona colunas;
   `terminal` é derivado de `state` (asserção estática sobre o SQL da migration).

## 6. Por que a migration é necessária (e por que code-only isolado não basta)

A garantia de ORDEM/TRANSIÇÃO depende de transições CONDICIONAIS **no banco**, com
terminal protegido e replay vinculado a conteúdo. Sem as RPCs, não há onde rejeitar a
escrita atrasada nem onde distinguir replay idempotente × conflito — a fila em
memória continuaria sendo a única (frágil) garantia. A parte "code-only" (ex.: só
mudar o retorno do drenador) **não** entrega a garantia: o consumidor de leitura é a
página/UI, que lê o `state` PERSISTIDO em `product_1_1_copy_state`.

## Summary

Reviewed the inactive Product 1:1 delivery core (F56.2b1b): the `POST /api/campaign/generate-image`
new-flow branch, the NDJSON orchestrator, snapshot/evidence persistence, artifact store + download
gate, copy state machine, administrative pending resolution, the public/campaign pages, the
upload-eligibility/form wiring, and the five LOCAL-ONLY migrations.

Overall the implementation is unusually careful: the fail-closed patterns are consistent
(terminal-state precedence over the historical `unknown` marker, `absent`-proven-only refunds,
content-only artifact verification, RPC-only writes for copy state, `SECURITY DEFINER` +
`SET search_path = ''` on every new function, authorization/evidence derived server-side and never
trusted from the client). The layered authorization in the route is strong *except* for one
ordering gap (CR-01) on the existing-operation short-circuit.

Key concerns:

1. **CR-01** — the new-flow branch delegates to the orchestrator on an existing operation
   **before** the campaign↔store binding check that the same file performs further down, so the
   ownership check on `campaignId` is skipped on that path (broken object-level authorization).
   Not exploitable today only because the flow is gated off (flags `false`, authorization `off`).
2. The administrative pending surface can display N pendências but only ever resolves the first.
3. Several dead/unreachable branches and duplicated fingerprint helpers.

Nothing indicates a credit/data-loss defect: reserve happens after evidence persistence, refunds
require proven artifact absence, and the copy subsystem is strictly best-effort.

## Critical Issues

### CR-01: Missing campaign↔store binding check on the existing-operation short-circuit (IDOR)

**File:** `src/app/api/campaign/generate-image/route.ts:336-347` and `:430-434` (check that should
precede them lives at `:713-744`)

**Issue:** In the new-flow branch, ownership is validated only for the **store**
(`requireOwnership(rawStoreId, guardUser.userId)` at `:276`). The `campaignId`/`operationId` pair
is then used directly:

```ts
// :340
existingNewFlowOperation = await readProductOneToOneOperation(newFlow.campaignId);
...
// :430
if (existingNewFlowOperation) {
  return await runProductOneToOneGeneration(newFlowOrchestrationInput);
}
```

The campaign→store binding check (`existingNewFlowCampaign.data.store_id !== newFlowStoreId` → 409)
only runs at `:713-744`, i.e. **after** this early `return`. The orchestrator's step (0)
(`generation-orchestrator.ts:799-822`) re-reads the operation for the same `campaignId` and only
enforces `existing.operationId === input.operationId` — it never compares the campaign's `store_id`
to `input.storeId`. Consequently an authenticated user who knows another tenant's
`(campaignId, operationId)` and submits a payload with **their own** eligible `storeId` +
`backgroundDirection` receives that tenant's persisted operation state over NDJSON
(`type:"result"` + `campaignUrl`, `type:"error"` with `operation_in_progress`/`generation_failed`,
or `type:"unknown"` + the tenant's `supportReference`), and the credit-operation read is performed
against the other store's rows.

Exploitation currently requires (a) eligibility of the caller's store, and (b) knowledge of the
victim's `operationId` (a client-generated UUID), and the flow is gated OFF in this phase
(`resolveProductFlowAuthorization` + `assertSubmissionEligible` refuse before reaching this code),
so there is no live exposure today. It becomes a real cross-tenant read the moment the flags/
authorization are enabled for b2 — it must be fixed before activation.

**Fix:** enforce the binding *before* the short-circuit (reorder or add a guard), e.g.:

```ts
// Before delegating/reading the existing operation:
const campaignBinding = await supabaseAdmin
  .from("campaigns")
  .select("store_id")
  .eq("id", newFlow.campaignId)
  .maybeSingle<{ store_id: string }>();
if (campaignBinding.error) {
  return Response.json({ error: { message: "Erro ao verificar a campanha." } }, { status: 500 });
}
if (campaignBinding.data && campaignBinding.data.store_id !== newFlow.storeId) {
  return Response.json(
    { error: { code: "operation_identity_conflict", message: "Identidade de campanha divergente." } },
    { status: 409 },
  );
}
// ...only now: existingNewFlowOperation = await readProductOneToOneOperation(...)
```

Alternatively add the missing `storeId` check inside `generation-orchestrator.ts` step (0) so the
invariant is enforced on every entry path, not just in the route.

## Warnings

### WR-01: Administrative pending surface can only resolve the first pendência

**File:** `src/app/(app)/admin/product-1-1-pending/page.tsx:95`

**Issue:** `PendingOperationsList` renders every visible pendência, but the resolution panel is
bound to the first element only: `{operations.length > 0 && <ResolutionForm item={operations[0]} />}`.
There is no selection mechanism in `PendingOperationsList` and no `key`/state that switches the
`item` prop (see `resolution-form.tsx:200-232` — `useState` is initialised once from the initial
prop and never re-synced). With two or more pendências (`reserved`/`art_uploaded`), the admin sees
all of them but can act on exactly one; the others are operationally unresolvable (`refund_once`
requires proven `absent`, and D13 blocks the residual-claim case anyway), so a real pending credit
hold can be left stranded.

**Fix:** make the panel operate on a selected item (client state + `key={item.campaignId + item.operationId}`
on `ResolutionForm` so the draft re-initialises), or render one `ResolutionForm` per operation:

```tsx
{operations.map((item) => (
  <ResolutionForm key={`${item.campaignId}:${item.operationId}`} item={item} />
))}
```

### WR-02: `persisted` shadowed inside the unknown-result branch

**File:** `src/lib/product-1-1/orchestration/generation-orchestrator.ts:1116`

**Issue:** The outer `let persisted: PersistProductOneToOneSnapshotResult` (`:863`) is shadowed by
`const persisted = await markUnknownOutcome(reference)` inside the `if (isUnknownResult(...))`
block (`:1116`). Both names are live in the same scope chain and mean completely different things
(persisted snapshot vs. unknown-outcome persistence). This is legal JS but is exactly the shape
that produces a future bug if the block is edited (e.g. someone reads `persisted.snapshotOriginalId`
after the loop). Lint with `no-shadow` would reject it.

**Fix:** rename the inner binding, e.g. `const markerPersisted = await markUnknownOutcome(reference);`
and use `if (markerPersisted)` below.

### WR-03: Migrations 3/4/5 create triggers without `DROP TRIGGER IF EXISTS` (breaks re-apply)

**File:** `supabase/migrations/20261009000003_f56_2b1b_frozen_evidence.sql:57,99,147,183`;
`supabase/migrations/20261009000004_f56_2b1b_campaign_artifacts.sql:45`;
`supabase/migrations/20261009000005_f56_2b1b_copy_state.sql:112`

**Issue:** These migrations are written in an idempotent style for tables/indexes
(`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`) and
migration 1 correctly pairs its trigger with `DROP TRIGGER IF EXISTS`
(`20261009000001_...:103-107`). Migrations 3, 4 and 5 do **not**: they call bare `CREATE TRIGGER`.
If a run applies the SQL but fails (or is interrupted) before the version is recorded in
`supabase_migrations.schema_migrations`, the re-run aborts with `trigger ... already exists`,
leaving the isolated instance in a half-applied state that the Plan 09 runner cannot recover from
without manual intervention. The same applies to any dev loop that replays the files.

**Fix:** mirror migration 1:

```sql
DROP TRIGGER IF EXISTS trg_product_1_1_frozen_evidence_immutable
  ON public.product_1_1_snapshot_frozen_evidence;
CREATE TRIGGER trg_product_1_1_frozen_evidence_immutable ...
```

(apply the same pattern to all five triggers across migrations 3, 4 and 5).

### WR-04: New-flow 409 conflict response drops `suggestedProductName` (legacy parity)

**File:** `src/app/api/campaign/generate-image/route.ts:569-576`

**Issue:** The legacy path returns `suggestedProductName` on `product_image_conflict` /
`product_image_strong_conflict` (`:1097`, `:1109`), and the client renders the corrective
`Usar "<sugestão>"` action only when it is present (`campaign-input-form.tsx:216-224`, `:261-269`).
The new-flow branch returns the same `status`/`reason`/`message` but omits `suggestedProductName`.
`InputValidationService` does produce it (`validationResult.suggestedProductName` is available in
the branch), so eligible users silently lose the one-click correction that legacy users get, and
`handleConflictCorrect` (`use-campaign-form.ts:1288-1293`) becomes a no-op for the new flow.

**Fix:** include it in the new-flow 409 payloads:

```ts
return Response.json({
  status: "needs_user_action",

  message: "O nome do produto digitado não corresponde à imagem enviada.",
  suggestedProductName: newFlowValidation.suggestedProductName,

```

## Info

### IN-01: `readFileSync`-style duplicate fingerprint helpers

**File:** `src/app/api/campaign/generate-image/route.ts:65-113` vs `src/lib/product-1-1/snapshot/persist-snapshot.ts:190-237`

**Issue:** `stableStringify` + `canonicalFrozenSnapshot` (route) and `stableJson` +
`computeContentFingerprint` (persist-snapshot) are two independent stable-serialization
implementations used for two different content fingerprints (campaign reuse vs. binding repair).
They must stay semantically aligned; a change to one (key-sorting, `undefined` handling, array
handling) that is not mirrored silently changes reuse semantics.
**Fix:** extract a single shared `stableStringify` helper (e.g. `@/lib/campaign/stable-json`) and
reuse it in both.

### IN-03: Unused destructured `setSubmitError`

**File:** `src/components/flow/campaign-input-form.tsx:75`

### IN-04: `preflight.frozenEvidence` is computed and discarded

**File:** `src/lib/product-1-1/orchestration/preflight.ts:197-208` and `:219-224` → consumed nowhere

**Issue:** The preflight performs three extra reads to classify the frozen-evidence state
(`no_snapshot`/`complete`/`repairable`/`corrupt`) and returns `frozenEvidence`, but
`generation-orchestrator.ts` never reads `preflight.frozenEvidence`. The `repairable` repair is
performed unconditionally by `persistProductOneToOneSnapshot` (which is correct), so the
classification is effectively dead weight (the `corrupt` fail-closed path is also duplicated by the
RPC). The behavior is right; the surface is misleading.
**Fix:** either consume the classification (skip the snapshot write when `complete`) or document
explicitly that it exists only as a contract/test surface.

### IN-05: `execution_ended` fast-path branch is unreachable

**File:** `src/lib/product-1-1/pending/resolve-pending-operation.ts:230-243`

**Issue:** `const executionEnded = !state.processing;` followed by
`if (state.processing) throw "operation_in_progress";` makes the later
`if (input.action === "refund_once" && !executionEnded) throw "execution_not_ended";` dead code
(`!executionEnded` ⟺ `state.processing`). Same tautology in
`20261009000002_...:239-241` (`IF v_in_progress AND NOT v_execution_ended`).
**Fix:** drop the unreachable check, or restructure so the two refusal codes remain distinguishable
intent (currently `execution_not_ended` can never be returned to the caller).

### IN-06: `reconstructAttemptSequence` is production-dead

**File:** `src/lib/product-1-1/orchestration/instrumentation.ts:85-96`

**Issue:** The function is only referenced by contract tests (`copy-instrumentation.contract.test.ts`);
no runtime module consumes it. It documents the intended correlation capability but currently adds
surface area without a caller.
**Fix:** keep it (it is a documented contract) but mark it clearly as test/contract-only, or wire it
into the read path so the correlation is actually exercised.

### IN-07: Duplicate React keys for repeated hashtags

**File:** `src/app/(app)/campanhas/[id]/client.tsx:539` (and `:283` in the legacy `ReadyView`)

**Issue:** `copy.hashtags.map((tag) => <span key={tag}>)` – a payload with a repeated hashtag emits
duplicate keys (React reconciliation warning; the map content is identical so the visible impact is
limited, but it can hide/drop a chip on re-order).
**Fix:** `key={`${tag}-${index}`}`.

### IN-08: `amount` rendered as "Reserva temporária · {n}" for every status

**File:** `src/app/(app)/admin/product-1-1-pending/resolution-form.tsx:135`

**Issue:** The credit line is labelled "Reserva temporária" unconditionally, including for a
`delivered`/`refunded` operation (reachable through `findPendingOperation` if the row becomes
terminal between the list query and the per-row read). Misleading wording for an already-settled
operation.
**Fix:** derive the label from `item.status`/`item.terminal`.

### IN-09: `hashtext` advisory lock can collide across distinct resolution identities

**File:** `supabase/migrations/20261009000002_f56_2b1b_pending_resolution.sql:165`

**Issue:** `pg_advisory_xact_lock(hashtext('p1_1_pending_resolution:' || p_resolution_operation_id::text))`
uses a 32-bit hash of the identity prefix; two *different* `resolution_operation_id` values may map
to the same lock key (or to a key already used by another advisory-lock namespace in this database),
causing unnecessary serialization (not a correctness defect — the correctness guarantee comes from
the unique partial index on `admin_audit_log.operation_id`). A namespaced two-key
`pg_advisory_xact_lock(int4, int4)` (constant namespace + `hashtext(id)`) would reduce both
collision classes.
**Fix:** use a two-argument advisory lock with a fixed namespace constant.

### WR-03 — avaliação (sem alterar migrations aplicadas)

**Evidência no repositório:** a migration `000001` emparelha `CREATE TRIGGER` com `DROP TRIGGER IF EXISTS` (`20261009000001_...:103-107`); as migrations `000003/000004/000005` usam `CREATE TRIGGER` **nu** (000003: 57/99/147/183; 000004: 45; 000005: 112). Tabelas/índices/funções são idempotentes (`IF NOT EXISTS`/`CREATE OR REPLACE`), mas os triggers **não**.

**Questão que exige documentação externa (NÃO consultada nesta tarefa):** o cenário *execução parcial → reexecução* depende de o **Supabase CLI** envolver **cada arquivo de migration numa transação** (registro de versão atômico em `supabase_migrations.schema_migrations`). Se cada migration roda em uma transação única ⇒ um erro faz **rollback total** (nenhum trigger órfão) ⇒ WR-03 inócuo; se **não** ⇒ um trigger órfão faz a reexecução abortar com `trigger ... already exists`.

- **Fonte pretendida (consulta futura, quando autorizado):** documentação oficial do **Supabase CLI** sobre aplicação local (`supabase migration up`; transaction wrapping / `supabase_migrations.schema_migrations`).
- **Proposta (forward-only):** nos **PRÓXIMOS** migrations, espelhar a migration 1 com `DROP TRIGGER IF EXISTS <trg> ON <tabela>;` antes de cada `CREATE TRIGGER`. **Nenhuma** alteração foi feita em `000003/000004/000005` e **nenhuma** migration foi reaplicada.

> As migrations `000003/000004/000005` estão aplicadas **apenas** na instância isolada descartável (`vendeo-f562a-isolated`); nenhuma migration foi aplicada ao repositório/produção.

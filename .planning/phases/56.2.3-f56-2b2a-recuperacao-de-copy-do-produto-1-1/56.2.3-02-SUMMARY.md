### FIX 1 — Classificar a falha do gateway pelo `retryable` normalizado (`e5a7507c`)

- **Problema:** o dreno classificava via `isRetryableError` (erros de **domínio** de copy apenas). O gateway lança `AiInvocationError` (network/timeout/transiente) com `retryable: true`, que **não** era reconhecido ⇒ a falha transitória era lida como `definitive` e **encerrava o ciclo automático indevidamente**.
- **Correção:** classificador PURO exportado `classifyCopyFailure` em `copy-recovery.ts` — duck-type do campo BOOLEAN `retryable` (sem importar internos do gateway só para `instanceof`): `retryable ? "transient" : "definitive"`; fora disso, cai na classificação de **domínio** existente (`isRetryableError`). Passado EXPLICITAMENTE como `classifyFailure` no `drainCopyTask` do serviço (`recoverCopyAttempt`) **e** na tentativa INICIAL do orquestrador (`startCopy`). O default do `copy-state.ts` (Plano 01) permanece **intacto** (`classifyFailure` continua OPCIONAL).
- **Testes:** unit do classificador (`AiInvocationError` retryable true/false, `NetworkError`/`ProviderRateLimitError` de domínio, `Error` genérico, `retryable` não-boolean) + **gateway REAL** (`AiGateway` com resolver/adapter FAKE espelhando `src/lib/ai/__tests__/gateway.test.ts`) dirigido pelo caminho vivo serviço → runner → `CopyDirectorService` → gateway → adapter, provando a `copy_payload.recovery.failureClass` PERSISTIDA: `transient` (retryable:true) × `definitive` (retryable:false).

```ts
export function classifyCopyFailure(error: unknown): CopyFailureClass {
  const retryable =
    error !== null && typeof error === "object"
      ? (error as { retryable?: unknown }).retryable
      : undefined;
  if (typeof retryable === "boolean") {
    return retryable ? "transient" : "definitive";
  }
  return isRetryableError(error) ? "transient" : "definitive";
}
```

### FIX 2 — Usar fallback SÓ quando disponível (`13aa8723`)

- **Problema:** `resolveTarget` devolvia `"fallback"` após QUALQUER falha transitória anterior, **sem checar disponibilidade**.

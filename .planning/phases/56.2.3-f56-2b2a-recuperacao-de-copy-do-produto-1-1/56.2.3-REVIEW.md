### CR-01 (HIGH): UI POST body omits `attemptSeq`/`attemptToken` required by the route schema

**File:** `src/app/(app)/campanhas/[id]/client.tsx:552-556` (producer) — `src/lib/product-1-1/copy/recovery-schemas.ts:19-29` (consumer)

**Issue:**
The route validates the POST body with `CopyRecoveryRequestSchema`, which is `.strict()` and requires **all** of:

```ts
operationId: z.string().uuid(),
mode: z.enum(["auto_retry", "manual"]),
attemptSeq: z.number().int().min(1).max(6),   // REQUIRED
attemptToken: z.string().min(1),              // REQUIRED
requestToken: z.string().uuid(),
```

But the only UI emitter sends exactly three fields:

```ts
body: JSON.stringify({
  mode,
  operationId,
  requestToken: newRequestToken(),
}),
```

`attemptSeq`/`attemptToken` are absent, so `CopyRecoveryRequestSchema.safeParse(body)` fails and the route returns **400 `invalid_body`** for *every* UI action:
- the manual CTA `onRecover → emitAttempt("manual")`, and
- the driving tab's automatic retry `emitAttempt("auto_retry")`.

The client cannot fix this locally either: the mapped view it receives (`NewFlowCopyRecoveryView`, `src/lib/campaign/display.ts:201-211`) exposes only `state`, `autoAttempts`, `manualAttempts`, `waitRemainingMs`, `canRetry` — it has **no** `attemptSeq`/`attemptToken`. So the UI is structurally incapable of satisfying the schema.

Consequence: on activation, the recovery feature never progresses — the manual retry silently shows the generic failure message and the automatic retry loop stalls after its first rejected emit (the `lastEmittedAutoRef` guard prevents re-emission for the same `autoAttempts`, so it cannot recover). This is a latent but total functional break of the deliverable's core action.

Why tests pass anyway (adversarial note — do not mistake green tests for correctness):
- `src/lib/product-1-1/__tests__/copy-recovery.contract.test.ts:2542-2548` builds `validRouteBody()` **with** `attemptSeq`/`attemptToken`, so route tests never exercise the real UI body.
- `src/app/(app)/campanhas/[id]/__tests__/copy-recovery-driving.test.tsx:83-91` stubs `fetch` and its `bodies()` type only asserts `mode`/`operationId`/`requestToken` — it never asserts the fields the route requires, so the mismatch is invisible.

**Fix (choose one, they must agree):**
1. Relax the schema — the service ignores these fields anyway (`copy-recovery.ts:255-371` reads only `requestToken` and `mode`), and the UI cannot supply them. Make them optional or drop them:
```ts
export const CopyRecoveryRequestSchema = z
  .object({
    operationId: z.string().uuid(),
    mode: z.enum(["auto_retry", "manual"]),
    requestToken: z.string().uuid(),
  })
  .strict();
```
2. Or make the UI able to send them: thread `attemptSeq`/`attemptToken` from the persisted summary through `NewFlowCopyRecoveryView` and include them in the `emitAttempt` body (`client.tsx:552`). Given the comments explicitly state these are "SOLICITAÇÕES — NUNCA AUTORIDADE" and the server resolves identity itself, option 1 is the minimal, correct fix.

Add a regression test that the real emitter body satisfies the real schema for both `manual` and `auto_retry`.

### WR-01 (MEDIUM): `newRequestToken()` fallback yields a non-UUID, failing the UUID schema

**File:** `src/app/(app)/campanhas/[id]/client.tsx:32-37`

**Issue:**
```ts
function newRequestToken(): string {
  if (typeof crypto !== "undefined" && typeof crypto.randomUUID === "function") {
    return crypto.randomUUID();
  }
  return `req-${Date.now()}-${Math.random().toString(16).slice(2)}`;
}
```
`requestToken` is validated as `z.string().uuid()`. In any environment lacking `crypto.randomUUID`, the fallback (`req-…`) is not a UUID and the POST fails with 400. The fallback therefore does not actually provide the resilience its name implies.

**Fix:** Generate a valid UUID v4 in the fallback, or import a UUID helper already used in the codebase; alternatively relax `requestToken` to a bounded non-empty string if the DB column is genuinely a UUID-typed token, keep the UUID and generate one:
```ts
// fallback: build a v4-shaped UUID from crypto.getRandomValues
```

## Verified CORRECT (explicitly checked, no issue found)

**Anti-duplication / server-side state (migrations `…000001`, `…000002`)**
- Acquisition decides the winner under a stable per-operation lock in the fixed order advisory (`pg_advisory_xact_lock`) → C4 credit row (`FOR UPDATE`, when present) → `copy_state` (`FOR UPDATE`); the same order is used in `apply`/`cancel`, so no lock-order inversion/deadlock (`…000002:100-120`, `…000001:179-205`).
- Real reasons returned: `attempt_in_progress`, `attempt_already_completed`, `wait_not_elapsed` (with remaining ms), `attempt_limit_reached`, `already_acquired` (with existing identity), `automatic_closed`; no `operation_terminal` is ever produced (`…000002`).
- Separate limits 3 auto + 3 manual + hard total cap 6, counted by `copy_payload.recovery.kind` (historical backfilled row is `kind='auto'`) (`…000002:228-256`).
- `stale_attempt` for a lesser `attempt_seq` completion is returned **before** touching persisted state (`…000001:216-221`).
- Terminal protection: a `completed` on **any** attempt is terminal and rejects later non-terminal/higher-seq writes (`…000001:223-236`); per-attempt terminal only allows a null-safe equivalent replay as `idempotent`, divergent content as `conflict` (`…000001:284-296`).
- Lease TTL 45s matches `COPY_LEASE_TTL_MS = 45_000`; expired `pending` is atomically closed as `failed` with `recovery.staleAttempt=true` via `jsonb_set` (preserving sibling `recovery.*`) and the next attempt is acquired in the same transaction (`…000002:160-184`).
- Server-side wait uses `updated_at + recovery.nextWaitMs` and returns `wait_not_elapsed` with remaining ms (`…000002:214-226`).
- Cancel registers the reason and declares `canceled:true` **only** on `applied`/`idempotent`; all refusals leave state untouched and insert nothing (`…000001:370-392`, `…000003:187-204`).
- Migration `…000003` performs the backfill atomically under the CLI transaction with no explicit `BEGIN/COMMIT` (deliberate), disables and **restores** the cancellation immutability trigger within the same migration, and recreates `product_1_1_cancel_copy` with the 6-arg signature and per-attempt `ON CONFLICT` — correct for the new `NOT NULL`/UNIQUE columns.

**Scope = texts only**
- The route imports no credit/artifact module and calls no `reserve/deliver/refund` (asserted and corroborated by source). The runner performs only copy generation and the deliverable art is untouched.

**Route barriers (`src/app/api/campaign/[id]/copy-recovery/route.ts`)**
- `requireSameOrigin` + `requireApiUser` + `requireOwnership` run before any IA; `requestToken` required by `.strict()` schema (absent ⇒ 400).
- `classifyCampaignFlow` gates legacy (403) and indeterminate (409) fail-closed; `operationId` from the body must equal the persisted operation (409 on absent/divergent); `resolveProductFlowAuthorization` must allow (403 otherwise) — all before `recoverCopyAttempt`.
- GET is query-only; operation read failure ⇒ **503 `recovery_unavailable`** (never a 200 with empty payload) and genuine absence is preserved as an explicit empty state. State-read failure also maps to 503. Error feedback is a closed code with a generic message (no internal reason leaked).

**Acquisition client (`copy-acquisition-client.ts`)**
- Closed envelope: winner requires numeric `attempt_seq` 1..6, non-empty `attempt_token`, `mode` present and equal to the request, and `reason` null/undefined; refusals require a `reason` from the closed set, with mandatory `attempt_seq`/`attempt_token` for `already_acquired` and mandatory finite `wait_remaining_ms` ≥ 0 for `wait_not_elapsed`.
- Strict numeric typing (`typeof`, `Number.isInteger`, `Number.isFinite`) with no coercive `Number(...)`.
- No `crypto.randomUUID()` in any service module (only the server orchestrator's internal initial `requestToken` and the client's UI token).

**Drain / envelopes (`copy-state.ts`)**
- Envelope validation is fail-closed, including contradiction checks (`applied:true` ⇒ `outcome='applied'` and non-null state; `canceled:true` ⇒ `state='failed'` and outcome `applied`/`idempotent`).
- Terminal confirmation requires the RPC to prove the persisted state (`applied`/`idempotent`); `conflict`/`rejected`/`invalid_content`/timeout/error never declare success; a persisted `completed` always wins over a refused `failed`.

**G-NA / UI invariants**
- `src/lib/campaign/display.ts` and `src/lib/campaign/copy-recovery-driving.ts` contain no `product-1-1` import (verified by reading both).
- `mapNewFlowCopyRecovery` precedence matches the spec (`concluida` > `ativa`/`aguardando` > `indeterminada` > `falha_definitiva` > `falha` > `interrompida`), with `record===null` ⇒ `indeterminada` (`canRetry=false`) and no attempt ⇒ no surface.
- Counters are never rendered; the manual-limit final message (no new-try CTA) is implemented (`manualLimitReached` hides the CTA; `finalFailure` shows the support message).
- Driving handle is module-memory per tab with no persisted token; only the initiating tab auto-emits `auto_retry`; non-driving tabs never POST. Expired wait on a non-driving tab ⇒ panel rendered as `interrompida` (no timer, no "em andamento", no spinner) and polling stops (poll requires `waitRemainingMs > 0 || drivesAutomaticRecovery`).

**Harness / fixtures**
- `prepare-visual-uat.ts` fails closed unless the isolated preflight env is supplied, verifies feature flags remain OFF and the bucket is private, and makes no remote/push calls.
- `fixture-readiness.mjs` is a pure guard that blocks the backfill unless both fixtures exist with NULL identity; its `parseReturnedUuid` correctly ignores the psql command tag.

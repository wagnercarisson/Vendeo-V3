## Medium

### M1: Estimativa ZERO é aceita — contraria o contrato “estimativa obrigatória (nunca zero)”

**Files:**
- `src/lib/product-1-1/pilot/spend-control.ts:153`
- `src/lib/product-1-1/copy/default-copy-runner.ts:209`
- `src/lib/product-1-1/orchestration/generation-orchestrator.ts:1262`
- `src/lib/product-1-1/pilot/resolve-pilot-spend-gate.ts:82`
- `supabase/migrations/20261017000002_f56_2b2c_pilot_spend_control.sql:67` e `:184`

**Issue:** O contrato afirma “estimativa obrigatória (nunca zero)” e os próprios comentários prometem “nunca contabiliza US$ 0”, mas todas as guardas usam `< 0` (ou `>= 0`), permitindo `0`:

```ts
// spend-control.ts:153
if (!Number.isFinite(input.estimatedUsd) || input.estimatedUsd < 0) { ... }
// default-copy-runner.ts:209 / generation-orchestrator.ts:1262 — mesma forma
// resolve-pilot-spend-gate.ts:82 → `value >= 0 ? value : undefined`
// SQL: estimated_usd NUMERIC NOT NULL CHECK (estimated_usd >= 0)
```

Consequências reais de `0` passar:
1. `VENDEO_PILOT_COPY_ESTIMATED_USD="0"` (ou `"0.0"`) faz a copy do piloto ser contabilizada como US$ 0 — o teto acumulado (`spent_usd + p_estimated_usd > cap_usd`) nunca avança por essas chamadas.
2. No orquestrador, `internalCost.estimatedCostUsd` vem da pricing; um valor `0` legítimo (modelo sem preço cadastrado retornando custo zero) permite chamadas pagas ao provider fora da contabilidade — exatamente a “chamada gratuita” que o contrato proíbe.

Os testes só cobrem `Number.NaN` (`behavioral.test.ts:236`) e nunca exercitam `0`; os testes armed de rota usam `toBeGreaterThan(0)`, mascarando a lacuna.

**Fix:** exigir estritamente `> 0` (e documentar que “zero” é tratado como ausente ⇒ bloqueio). Ex.:

```ts
if (!Number.isFinite(input.estimatedUsd) || input.estimatedUsd <= 0) {
  return { acquired: false, outcome: "blocked", reason: "estimate_required" };
}
```

```ts
// resolve-pilot-spend-gate.ts
return Number.isFinite(value) && value > 0 ? value : undefined;
```

```sql
-- migration 000002 (spend_state check e begin_paid_call)
estimated_usd NUMERIC NOT NULL CHECK (estimated_usd > 0)
...
IF p_estimated_usd IS NULL OR p_estimated_usd <= 0 THEN RAISE EXCEPTION 'invalid_estimated_usd'; END IF;
```

### M2: `resolvePilotSpendGate` retorna `inactive` (fluxo SEM gate) para estágio habilitador não-estreito

**File:** `src/lib/product-1-1/pilot/resolve-pilot-spend-gate.ts:55-57`

**Issue:**

```ts
if (decision.stage !== "isolated_pilot") {
  return { kind: "inactive" };
}
```

`decision.allowed === true` com `stage` habilitador **diferente** de `isolated_pilot` (ex.: `test_stores`, `all_stores` — ambos existem em `STAGE_SCOPE_COMPATIBILITY`) cai no mesmo ramo de `inactive` usado para o legado `off`. Resultado: o fluxo novo roda **sem nenhum controle de gasto** (`pilotSpendDep = undefined`) para um estágio que o próprio código de autorização considera “habilitador”. O princípio declarado do resolver é fail-closed para incerteza; um estágio habilitador inesperado é uma **inconsistência**, não “piloto desligado”.

Hoje a barreira da migration 000001 só persiste `off`/`isolated_pilot`, o que torna o cenário latente (não explorável pelo caminho atual). Mas o resolver não deve depender dessa garantia externa: se um evento `test_stores`/`all_stores` algum dia existir (migração futura, dado histórico, ajuste manual), o gasto fica sem gate silenciosamente.

**Fix:** tratar qualquer estágio habilitador não-estreito como `blocked` (incerteza), reservando `inactive` **apenas** para a leitura determinística `off`:

```ts
if (decision.stage === "off") {
  return { kind: "inactive" }; // legado/inerte comprovado
}
if (decision.stage !== "isolated_pilot") {
  return { kind: "blocked", reason: "eligibility_context_failure" };
}
```

### M3: Falha simultânea de `markUnknown` + `blockGlobal` reclassifica um resultado DESCONHECIDO e pode terminar em `failed`/estorno

**File:** `src/lib/product-1-1/orchestration/generation-orchestrator.ts:1288-1295` (com `:1385`)

**Issue:** No caminho de imagem, quando a invocação indica resultado desconhecido:

```ts
} catch (invokeError) {
  if (pilotSpend && pilotHandle) {
    if (controllerAbort.signal.aborted || isUnknownPilotOutcome(invokeError)) {
      await pilotSpend.markUnknown({ handle: pilotHandle, reason: "timeout_or_unknown" });
    } else { ... }
  }
  throw invokeError;   // <-- só alcançado se markUnknown resolver
}
```

`spend-control.markUnknown` só rejeita quando **ambos** `markUnknown` e a rede de segurança `blockGlobal` falham (`spend-control.ts:224-230`). Nesse caso a exceção **substitui** o erro original (o `throw invokeError` nunca é alcançado), e o `failure` passa a ser o erro do `markUnknown`/`blockGlobal`. Na sequência:

- `isUnknownResult(failure, aborted)` (`:1385`) classifica esse erro genérico como **não** timeout/network ⇒ cai no ramo de **falha confirmada**;
- se `attempts.recordOperationOutcome(outcome='failed')` conseguir persistir (`failedMarkerPersisted = true`), o `settleConfirmedFailure({ allowPfClosure:true })` pode encerrar a operação (PF) e **estornar** — tratando como “falha técnica” um resultado que era DESCONHECIDO (o provider pode ter gerado e cobrado a imagem).

A intenção do contrato (“resultado desconhecido ⇒ terminal `unknown`, nunca estorna”) é perdida justamente quando o subsistema de bloqueio está degradado. O terminal correto nesse caso é `unknown` (pendência), não `failed`.

**Fix:** preservar a natureza desconhecida mesmo quando `markUnknown` rejeita — capturar a falha do gate e rotear para pendência:

```ts
} catch (invokeError) {
  if (pilotSpend && pilotHandle) {
    if (controllerAbort.signal.aborted || isUnknownPilotOutcome(invokeError)) {
      try {
        await pilotSpend.markUnknown({ handle: pilotHandle, reason: "timeout_or_unknown" });
      } catch {
        // bloqueio global também falhou: permanece DESCONHECIDO (pendência),
        // NUNCA reclassifica como falha confirmada.
      }
    } else {
      await pilotSpend.endPaidCall({ handle: pilotHandle, actualEstimatedUsd: pilotEstimatedUsd });
    }
  }
  throw invokeError; // preserva o erro original (AbortError/timeout) para isUnknownResult
}
```

(O mesmo padrão reaparece no runner de copy em `default-copy-runner.ts:239-249`; menor impacto por ser best-effort, mas merece o mesmo tratamento.)

### L1: `attemptSeq` da copy inicial fixado em `1`, ignorando a identidade adquirida

**File:** `src/lib/product-1-1/orchestration/generation-orchestrator.ts:575` (runner construído antes de `startCopy`/`acquire`)

**Issue:** O runner default da copy é criado com `attemptSeq: 1` **antes** da aquisição server-autoritativa; a identidade real (`acquired.attemptSeq`) só é conhecida em `startCopy` (`:938-993`). O valor `1` é então usado como `p_attempt_seq` do gate (`copy_initial`), podendo divergir do `attempt_seq` efetivo da tentativa. Hoje o `attempt_seq` do gate só é usado para armazenamento/eco (o `call_id` é a PK do ledger), então o impacto é cosmético — mas a contabilidade por chamada fica com um rótulo de sequência incorreto em replays/retomadas.

**Fix:** propagar `attemptSeq: acquired.attemptSeq` do ponto de aquisição até o runner (ex.: parametrizar `createDefaultProductOneToOneCopyOps` por uma factory que recebe `acquired`), como já é feito em `copy-recovery.ts:325` (`attemptSeq: input.runnerDeps?.attemptSeq ?? acquired.attemptSeq`).

### L2: `spend-preservation` trata `null` como `0` em `spent_usd`

**File:** `src/lib/product-1-1/pilot/spend-preservation.ts:44-45`

**Issue:** `Number(input.current.spent_usd)` converte `null` em `0` (`Number(null) === 0`), então `spent_usd: null` e `spent_usd: 0` são considerados idênticos pelo classificador de preservação. O campo é `NOT NULL DEFAULT 0` no banco, mas `PreservationState.spent_usd` é tipado `number | string | null`, então a borda existe no contrato. Uma divergência `null ↔ 0` (ex.: leitura parcial/coluna ausente) passaria como “igual” e autorizaria a restauração.

**Fix:** resolver `null` explicitamente antes de comparar (espelhando `numOrNull`, que já existe no arquivo para `cap_usd`):

```ts
const curSpentRaw = input.current.spent_usd;
const expSpentRaw = input.expected.spent_usd;
if (curSpentRaw === null || expSpentRaw === null) {
  if (curSpentRaw !== expSpentRaw) return { ok: false, reason: "spent_divergence" };
} else {
  const curSpent = Number(curSpentRaw);
  const expSpent = Number(expSpentRaw);
  if (!Number.isFinite(curSpent) || !Number.isFinite(expSpent)) return { ok: false, reason: "spent_not_finite" };
  if (Math.abs(curSpent - expSpent) > epsilon) return { ok: false, reason: "spent_divergence" };
}
```

### L3: Constantes de limite “DURIOS” exportadas mas não aplicadas em produção

**File:** `src/lib/product-1-1/pilot/spend-control.ts:26-37`

**Issue:** `PILOT_PAID_CALL_KINDS`, `PILOT_IMAGE_CALL_LIMIT` (3) e `PILOT_COPY_CALL_LIMIT` (6) são exportados e descritos como “Limites DURIOS de chamadas do piloto”, mas **nenhum consumidor de produção** os referencia — o único uso é a asserção de literal em `pilot-spend-control.contract.test.ts:253-254`. O gate é puramente monetário (cap em USD); os tetos de contagem são de fato garantidos em outros subsistemas (política de imagem `MAX_IMAGE_GENERATION_ATTEMPTS=3`, aquisição de copy `attempt_seq 1..6`). As constantes, do jeito documentado, sugerem uma invariante que o gate não implementa.

**Fix:** ou remover as constantes (dead code) e ajustar o comentário, ou documentá-las explicitamente como espelho informativo dos tetos impostos fora do gate (evitando a leitura de que o gate as aplica).

## Info

### I1: Envelope `conflict` da RPC é mapeado para `read_failure`, perdendo `operation_identity_conflict`

**File:** `src/lib/product-1-1/pilot/spend-control.ts:182-194`

**Issue:** `begin_paid_call` pode devolver `{ success:false, conflict:true, reason:'operation_identity_conflict' }` sem lançar; como `identityMatches` exige `call_id === callId` e o envelope de conflito não traz a identidade completa, o serviço cai no default `outcome: "blocked", reason: "read_failure"`. O diagnóstico fica impreciso (perde o código real). Não há risco de autorizar provider.

**Fix:** reconhecer `data.conflict === true` e devolver um `reason` específico (ex.: `operation_identity_conflict`) para telemetria/diagnóstico.

### I2: `void error;` é um no-op

**File:** `src/lib/product-1-1/pilot/spend-control.ts:229`

**Issue:** `void error;` não tem efeito algum; o catch descarta o erro silenciosamente depois de instalar o bloqueio global. Pode confundir leitura (parece “tratar” o erro).

**Fix:** remover a linha, ou logar o erro de forma estruturada (`console.error("[pilot] mark_unknown_failed", error)`) antes do `blockGlobal`.

### I3: `isUnknownPilotOutcome` classifica `kind: "network"` como desconhecido ⇒ bloqueio global

**File:** `src/lib/product-1-1/pilot/spend-control.ts:113-134`

**Issue:** `e.kind === "network"` (e vários sinais de rede: `ECONNREFUSED`, `ENOTFOUND`, `fetch failed`) são tratados como resultado DESCONHECIDO, o que aciona `markUnknown` e o **bloqueio global** do piloto (todas as chamadas, inclusive de outras campanhas, exigem reconciliação humana). Um erro de rede em que a requisição nunca chegou ao provider não gerou custo e não deveria exigir reconciliação manual. É uma escolha conservadora assumida no CONTEXT, mas o efeito operacional (parada global por um blip de rede na copy, que é best-effort) é desproporcional.

**Fix (opcional):** distinguir falhas de conexão pré-envio (`ECONNREFUSED`/`ENOTFOUND`) de timeout/abort pós-envio; manter `markUnknown` apenas para resultados genuinamente indeterminados (timeout, abort, conexão derrubada após envio).

### I4: Inconsistência de status HTTP para falha de leitura de autorização

**File:** `src/app/api/campaign/[id]/copy-recovery/route.ts:295-310` vs `:323-329`

**Issue:** A rota lê a autorização por conta própria (`resolveProductFlowAuthorization`) e trata `read_failure` como `authorizationAllowed = false` ⇒ responde **403**; em seguida `resolvePilotSpendGate` trata a MESMA condição como `blocked` ⇒ **503**. Dois estágios diferentes da mesma rota retornam códigos distintos para a mesma falha de leitura. Não é falha de segurança (ambos negam), mas é inconsistência de contrato de erro.

**Fix:** unificar — responder 503 (`recovery_unavailable`) para `code === "read_failure"`/`flags_unavailable` e reservar 403 para negação determinística (`stage_not_enabling`, `missing_authorization`, etc.).

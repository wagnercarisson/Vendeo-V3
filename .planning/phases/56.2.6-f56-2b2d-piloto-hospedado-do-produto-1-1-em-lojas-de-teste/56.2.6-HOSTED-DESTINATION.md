## 1. Por que esta decisão existe

O plano herdado assumia implicitamente "Vercel Preview + Supabase não-produção" sem definir **provisionamento, migrations, credenciais, custo e descarte**. Isso é uma decisão de ambiente, não um detalhe de teste. Ela precisa ser tomada **antes de qualquer prova hospedada** porque muda:

- onde as migrations são aplicadas e qual ledger é afetado;
- qual blast radius existe se uma fixture/limpeza falhar;
- quais credenciais e custos são necessários;
- o que cada prova realmente demonstra (banco vs execução Vercel);
- a posição das provas no grafo de dependências (antes ou depois de 06/07).

## 2. Três classes de prova (não confundir)

| Classe | O que prova | O que NÃO prova | Onde roda |
|--------|-------------|-----------------|-----------|
| **P1 — Reuso local** | Contrato de recuperação/segurança: fence, `unknown`, `delivered`, `refund_once`, kill simulado, idempotência | Nada sobre Vercel, RLS efetiva no hospedado ou banco remoto | Harness local isolado (`requireIsolatedEnv`), provider **simulado local** |
| **P2 — Prova de banco remoto** | RPCs, fence, RLS/grants, ledger e semântica de encerramento **no banco remoto decidido** | **Não prova execução dentro da função Vercel** (o vitest roda localmente e só fala com o banco) | vitest local apontando para o Supabase remoto **não-produção** decidido (somente se a alternativa escolhida tiver esse banco) |
| **P3 — Prova de execução no Vercel** | A orquestração **real** roda dentro da função Vercel hospedada, com o route real, crédito real e provider real | Não prova kill determinístico da plataforma | Rota real `generate-image` no deployment hospedado, sob `test_stores`, loja de teste, **chamada paga** com checkpoint |

### 2.1 Regra sobre provider simulado

O provider simulado é **fixture de teste local** (`src/lib/product-1-1/__tests__/fixtures/simulated-provider.ts`). Ele **não é importável por nenhuma rota** (`src/app/api/**`), **não tem rota pública** e **não é selecionável pelo cliente**. Portanto:

- **não existe** "provider simulado disparado via Preview";
- a prova P3 usa o **provider real** (é o mesmo caminho do piloto);
- qualquer prova com provider simulado é P1 (local).

### 2.2 Regra sobre platform kill

Um **deadline cooperativo** (abort + `Promise.race` + marcador `unknown` best-effort) **não é equivalente** a um kill abrupto da plataforma Vercel. O kill real:

- não é deterministicamente reproduzível por HTTP em Preview/produção;
- pode impedir a última escrita;
- **não prova ausência de upload** e **não autoriza** nenhuma via de encerramento.

Consequência: **P3-kill** é marcado como **não deterministicamente reproduzível** e registrado como **limitação** na evidência. Se uma observação exclusiva de Preview for desejada, ela é um **passo separado, explicitamente autorizado** (ex.: função Preview com duração deliberada), e **ainda assim** não cria rota pública de simulação. A semântica de timing continua coberta por P1 (deadline/race) e pela via administrativa existente — nunca por um kill fingido.

## 3. Alternativas de destino

### Alt A — Supabase dedicado NÃO-produção + Vercel Preview

**Desenho:** criar um projeto Supabase separado (ref próprio) e um deployment Preview; aplicar ali o conjunto definitivo de migrations; semear lojas de teste; rodar P2 nesse banco e P3 no Preview com provider real (chamada paga gated).

| Dimensão | Impacto |
|----------|---------|
| Isolamento | **Forte** — nenhuma fixture/limpeza toca produção |
| Blast radius | Baixo para dados de produção; alto apenas no ambiente descartável |
| Pré-requisitos | Provisionar projeto, credenciais, migrations próprias, seed, Vercel Preview apontando para o ref não-prod |
| Custo | Plano Supabase (tier necessário para o projeto extra) + esforço de migrations/credenciais/seed + chamadas pagas de P3 + descarte |
| Descarte | Derrubar projeto Supabase, deployment Preview, segredos e dados de teste |
| Limitações | Ainda não reproduz kill determinístico; P3 continua sendo chamada paga real |
| Efeito no grafo | Exige um passo de provisionamento **separado e autorizado**; P2/P3 só rodam depois dele |

### Alt B — Vercel Preview + Supabase de PRODUÇÃO

**Desenho:** usar o Preview da Vercel apontando para o Supabase de produção (`gvbzwihwgzujwsviufgy`); rodar P2/P3 contra produção.

| Dimensão | Impacto |
|----------|---------|
| Isolamento | **Fraco** — fixtures, claims e créditos de teste convivem com dados reais |
| Blast radius | **Alto** — limpeza/erro pode afetar lojas e créditos de produção |
| Pré-requisitos | Conjunto definitivo de migrations **já aplicado** em produção (portanto só faz sentido **depois** do Plano 06) |
| Custo | Nenhum projeto novo; custo = chamadas pagas de P3 + risco operacional |
| Descarte | Nenhum ambiente a descartar; exige limpeza manual de fixtures em produção |
| Limitações | Mistura prova e produção; dificulta provar que a prova não contaminou estado real |
| Efeito no grafo | P2/P3 obrigatoriamente depois de 06 e 07; não pode ser pré-condição de 06/07 |

### Alt C — Sem ambiente novo: produção restrita a lojas de teste (CANDIDATA RECOMENDADA)

**Desenho:** **não criar ambiente**. Reutilizar as migrations e o deploy de produção. Rodar a prova de execução Vercel (P3) e o piloto **diretamente em produção**, restritos a lojas de teste (`is_test_store=true`) sob a autorização estreita `test_stores` + `test_stores`, com o novo fluxo **OFF** fora da janela. As provas simuladas permanecem **locais (P1)**. O kill de plataforma **não é deterministicamente reproduzível** e é documentado como limitação.

| Dimensão | Impacto |
|----------|---------|
| Isolamento | **Médio** — a barreira é a autorização estreita + loja de teste + flags, não um ambiente separado |
| Blast radius | Limitado por `test_stores`, `all_stores=false`, fluxo OFF e teto de gasto; qualquer falha de contenção atinge produção |
| Pré-requisitos | Plano 06 (migrations) e Plano 07 (deploy OFF + config) concluídos; autorização `test_stores` disponível (Plano 01) |
| Custo | **Nenhum** projeto/plano novo; somente chamadas pagas do piloto (dentro do teto) |
| Descarte | Nenhum ambiente; desligamento = flag OFF + revogação (nunca pausa global) |
| Limitações | P2 (banco remoto não-prod) **não existe**; semântica de banco/fence/RLS coberta por P1 + leitura de produção + piloto. Kill de plataforma não reproduzível |
| Efeito no grafo | P3 roda **depois de 07** como primeira operação paga do Plano 08; P1/aceite continuam antes de 06/07 |

## 4. Comparação e recomendação

| Critério | Alt A | Alt B | Alt C |
|----------|-------|-------|-------|
| Isolamento de produção | Forte | Fraco | Médio (contido por `test_stores`) |
| Custo de ambiente | Tier Supabase + operação | Zero | Zero |
| Esforço de migrations/credenciais/seed/descarte | Alto | Baixo (mas usa produção) | Zero de ambiente |
| Prova P2 (banco remoto) | Sim | Sim (produção) | Não (P1 + leitura + piloto) |
| Prova P3 (execução Vercel) | Sim (Preview, paga) | Sim (Preview, paga) | Sim (produção, paga, restrita) |
| Risco de contaminar produção | Muito baixo | Alto | Médio, controlado |
| Coerência com a fase "piloto hospedado restrito" | Alta, porém mais pesada | Baixa | **Alta** |

**Recomendação: Alt C**, como candidata. Racional:

1. A fase já define a barreira correta para produção: `test_stores` + `all_stores` recusado + fluxo OFF + orçamento + revogação. Um ambiente novo adiciona custo e superfície sem melhorar a prova de **execução** (P3), que é o objetivo central.
2. A prova P2, quando muito, demonstra banco; sob Alt C ela é substituída por P1 (contrato local) + leitura de produção + comportamento observado no piloto, com a limitação declarada.
3. Evita provisionar e descartar infraestrutura dentro de uma fase cujo escopo é **planejar** a liberação.

**Mas a escolha é humana.** Alt A é defensável se o operador exigir isolamento forte e aceitar o custo; Alt B só é defensável se as migrations já estiverem em produção e o operador aceitar explicitamente o blast radius.

**Regras do checkpoint:**

- `autonomous: false` — a decisão não pode ser auto-aprovada.
- Nenhum provisionamento, migration, deploy, credencial ou seed pode ocorrer como efeito deste checkpoint.
- Se Alt A/B forem escolhidas, o provisionamento é um **passo separado explicitamente autorizado** e precisa registrar custo, refs, credenciais, migrations do alvo e plano de descarte **antes** de P2/P3.
- Se Alt C for escolhida, P2 é marcada como **não aplicável** e a limitação entra na evidência; P3 continua sendo a **primeira operação paga** do Plano 08.

## 6. Consequências no grafo de planos

1. **Plano 04** — decide o destino (Task 1), constrói P1 + harness de P2 + fixture local do provider simulado e **aceita** o conjunto de provas (Task 3). Não provisiona nada.
2. **Planos 06 e 07** — declaram `depends_on` incluindo **Plano 04**, pois o aceite das provas simuladas + a decisão de destino precedem qualquer efeito irreversível (migrations, deploy, configuração).
3. **Plano 08** — executa a **prova P3 (execução Vercel)** como primeira operação paga, depois do deploy (07), com provider real, rota real e autorização `test_stores`, sob checkpoint de chamada paga. O provider simulado **não** participa de P3.
4. **Platform kill** — permanece como limitação documentada; nenhum plano finge reproduzi-lo deterministicamente.

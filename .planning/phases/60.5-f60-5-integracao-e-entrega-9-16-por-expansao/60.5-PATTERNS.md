### 3. `orchestration/status-view.ts` — closed status derivation

**Analog:** `src/lib/product-1-1/orchestration/resend-query.ts:93-131` (persisted state mapping, terminal precedence, unknown only when non-terminal) + `pending-operations-repository.ts:280-332` (canonical origin/stage/claims/outcome).

**Mapping rules (design D10 / spec `Consulta de status é somente leitura`):**
```ts
// precedence: terminal delivered/refunded > unknown persisted (non-terminal) > processing
if (credit.delivered) return { state: "delivered", terminal: true, ... };
if (credit.refunded) return { state: "refunded", terminal: true, ... };
if (outcome === "unknown" && !terminal) return { state: "unknown", terminal: false, supportReference };
return {
  state: "processing", terminal: false,
  phase: activeClaim ? "step_in_progress"
       : base.status === "done" && expansion.status !== "done" ? "between_steps"
       : deliveredProjectionPending ? "delivery_pending"
       : preparationIndeterminate ? "preparation_retry"
       : suspended,
  canContinue, nextStep,
};
```
`canContinue` derives only from persisted state: no active claim, no terminal `unknown`/`failed`, and next F60 action is not `wait`/`blocked`. Never infer from elapsed time or object presence.

**Pitfalls / guards:**
- Pure mapper only; no I/O. Keep the DB read in `getOperationView`.
- `processing` is distinct from `unknown` (spec explicitly separates them). `unknown` is terminal-for-UX but non-terminal financially: no retry, no refund.
- Precedence terminal wins over a stale `unknown` outcome (F60 outcome rows are immutable).

### 4. `orchestration/acquisition-ids.ts` — per-stage identities

**Analog:** `format-resolution.ts` pair validation + `types.ts:90-96` (`AcquireStepRequest.requestId` is per acquisition).

**Contract (design D3, spec `Identidade de aquisição distinta e estável por etapa`):**
```ts
export function parseAcquisitionIds(raw: unknown):
  | { readonly ok: true; readonly ids: { base: string; expansion: string } }
  | { readonly ok: false; readonly reason: "invalid_pair" | "same_id" } {
  const base = uuid(raw?.base);
  const expansion = uuid(raw?.expansion);
  if (!base || !expansion) return { ok: false, reason: "invalid_pair" };
  if (base === expansion) return { ok: false, reason: "same_id" }; // compare lowercased
  return { ok: true, ids: { base, expansion } };
}
export function newAcquisitionIds(): { base: string; expansion: string } {
  return { base: crypto.randomUUID(), expansion: crypto.randomUUID() };
}
```
- `initial`: server generates the pair.
- `continue`: client supplies `requestIds: { base, expansion }`; route maps to `acquisitionIds`.
- Same pair is reused only for an identical repetition of the same HTTP invocation; a new continuation gets a new pair.
- Never reuse the base id for expansion; never reuse an attempt id for a new attempt.

**Pitfalls / guards:**
- F60 uniqueness is `(campaign_id, operation_id, request_id)`; cross-stage reuse returns `operation_identity_conflict`/`query_only`. Validate before calling F60 so the route returns a typed 400/409 and never touches the provider.
- UUID normalization must be consistent (lowercase) or the equality check is bypassable.

### 6. `orchestration/failure-mapping.ts` — D6 outcome table

**Analog:** `src/lib/campaign/square-base/failure.ts` (module outcome → provider class) + design D6 (lines 148-161).

**Mapping contract (must be exhaustive):**

| Module outcome | `finish` | `recordOutcome` | Financial |
|---|---|---|---|
| `completed` / `expanded` / `reused` | `completed` | — | none |
| transient `provider_failure` | `failed`/`transient` | — | `processing` if attempts remain, else definitive |
| definitive / `invalid_output` | `failed`/`definitive` | `failed` | refund once if no vertical |

- A failed `finish` (late response) must not produce effects: re-read the financial authority and emit `result`/`error`/`unknown` from persisted state.

### 7. `orchestration/durable-input.ts` — exact data-URL reconstruction primitives

**Analog:** `src/lib/campaign/square-base/frozen-state.ts:581` (`hashImageDataUrl`) — reuse it; do not re-implement the hash.

```ts
import { hashImageDataUrl } from "@/lib/campaign/square-base/frozen-state";

export interface DurableInputDescriptor {
  readonly kind: "product" | "identity";
  readonly role: "primary" | "variation" | "combo_item" | "reference" | "identity";
  readonly index: number;
  readonly contentId: string;      // sha256(dataUrl EXACT), not sha256(bytes)
  readonly storagePath: string;
  readonly mimeType: string;
  readonly dataUrlPrefix: string;  // exact, e.g. "data:image/jpeg;base64,"
  readonly byteSize: number;
}

export function reconstructDataUrl(prefix: string, bytes: Buffer): string {
  return `${prefix}${bytes.toString("base64")}`;
}
export function verifyReconstructed(descriptor, bytes): boolean {
  const dataUrl = reconstructDataUrl(descriptor.dataUrlPrefix, bytes);
  return bytes.byteLength === descriptor.byteSize &&
    hashImageDataUrl(dataUrl) === descriptor.contentId;
}
```
At creation, verify the same equality against the received data URL **before** `reserveOperationOnce`; reject unrepresentable input before reserving. The F60.4 hash function must not change.

**Pitfalls / guards:**
- Hash of the data URL ≠ hash of bytes. Never store/compare `sha256(bytes)` as `contentId`.
- Preserve prefix/mime/encoding/whitespace exactly; no base64 normalization.
- `dataUrlToCampaignImage` (`persistence.ts:42-65`) accepts only `png|jpeg|webp`; use it to extract bytes/mime, then re-verify.

## Findings / Risks (flag, do not invent behavior)

1. **Admin pending adapter probes the wrong bucket for two-stage.** `pending-operations-repository.ts:343-347` already dispatches by canonical origin, but the injected `verticalArtifacts` is `VerticalArtifactStore` (direct `campaign-images` path) created in `pending-adapter.ts:32`. Two-stage verticals live in `campaign-internal-artifacts`. Requires the additive `twoStageArtifacts` seam + composition projection; otherwise admin `deliver_existing_art`/`refund_once` see `absent` and can refund a delivered operation.
2. **Architecture guard must be symbol-specific, not module-specific.** `src/app/api/campaign/[id]/image-recovery/route.ts:239-241` and `product-vertical-9-16/recovery/pending-adapter.ts:9` legitimately import `makeVerticalProjection` from `product-vertical-9-16/orchestration/entrypoint`. A guard that forbids importing the module will fail. Guard must assert zero occurrences of `runProductVertical9x16Generation` in `src/app/**` (and zero runtime loading), not zero imports of the entrypoint module.
3. **Origin marker vs. idempotent content hash.** The route hashes `newFlowFrozenSnapshot` (lines 905-925) and compares stored snapshot minus `frozenContentReferences` (944-957). `economicSnapshot` contains volatile USD/BRL rates. If persisted in `input_snapshot` **and** included in the hash, a legitimate resubmission with a new rate becomes a false `operation_identity_conflict`. Only `inputFiles` descriptors are mandated in the frozen content hash; `copyContext`/`economicSnapshot` must be excluded from the hash (or compared against persisted values), while still being persisted for reconstruction.
4. **Historical 9:16 must be classified before the new snapshot is composed.** `readProductOneToOneOperation` (472-483) finds both new-flow and historical direct credit operations. If a historical campaign reaches `runNewFlowGeneration("9:16")`, it would be dispatched to the new orchestrator (and the new marker keys would make its hash diverge). The route must branch: `existingCampaign && origin === "historical"` → safe persisted response (`delivered` → result, `refunded` → error, pending/unknown → `legacy_vertical_pending`), no new marker, no generation.
5. **`repairable` frozen state has no payload.** `readSquareBaseFrozenState` returns `payload` only for `complete` (`frozen-state.ts:668-676` vs 723-730). Design D9 says a `repairable` state may be repaired before copy generation; the copy route cannot read `copyContext`/`briefing` from `repairable`. Either invoke the F60.4 repair path first or fail closed — do not assume payload presence.
6. **Two different probe shapes.** `TwoStageFinancialService` consumes `VerticalArtifactProbeResult` (`format/width/height/mimeType/storagePath/evidenceRef`), while `PendingArtifactProber` consumes `ArtifactProbe` (`ref/width/height/mimeType/storagePath`). The composition probe must expose both (two methods or two thin adapters); a single shape will fail one consumer.
7. **No signed-URL helper on `CompositionArtifactStorage`.** It only has `downloadBytes`, `readObjectInfo`, `uploadImmutable` (`storage.ts:91-136`). Preview signing must be new code; model it on `display.generateSignedPreviewUrl` + `VerticalArtifactStore.getSignedArtifactUrl`, validate canonical vertical path, and never sign `square_*`.
8. **`generation-status` response shape vs. consumers.** `unknown-result-panel` reads `data.operation.state`; the new status uses `processing`. Detail/new-flow display expects `reserved|art_uploaded|delivered|refunded`. Map `processing` to a safe shape or update consumers deliberately; do not let it fall into "unknown" (amber) or success.
9. **`GenerationProgress.isNewFlowPhases` misroutes 9:16 phases.** `campaign_base`/`campaign_preparation`/`campaign_expansion` are not in `NEW_FLOW_PHASE_ORDER`, so without a dedicated detector the component renders the **legacy** five-step layout. Add `TWO_STAGE_PHASE_ORDER` and check it first.
10. **Input helper must not transcode.** Reusing `uploadCampaignInputImage` (`persistence.ts:168-191`) transcodes to JPEG and destroys the exact `dataUrlPrefix + base64` representation; reconstruction then fails the hash check. Add a new helper and leave the legacy one untouched.
11. **Flag listing affects admin UI.** Adding `product_9_16_two_stage_enabled` to `ALL_FEATURE_FLAG_KEYS` changes the operational controls surface and its tests. Add the key/method first; decide the admin listing deliberately (activation checkpoint).
12. **Route body uses `requestIds`, orchestrator input uses `acquisitionIds`.** Design has both names. Keep the public body contract `requestIds: { base, expansion }` and map explicitly in the continue route; do not expose `acquisitionIds` to the browser.
13. **No structural migration.** Everything fits `campaigns.input_snapshot` JSONB + existing F60/F60.1/F60.4 tables. The new flag row is data-only at activation; do not create a migration, seed, or enable anything in implementation.
14. **`listCampaigns` needs verification, not a rewrite.** It signs the derived thumbnail from `campaign-images` (correct) and excludes non-ready campaigns. Once `thumbnail-path.ts` recognizes `{store}/{campaign}/{operation}/vertical.jpg`, cards work; without that change they silently show placeholders.

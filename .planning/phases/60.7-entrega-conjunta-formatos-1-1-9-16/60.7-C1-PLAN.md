## 0. Decisões fechadas (resolvem as seis lacunas)

1. **Identidade:** a **rota `generate-image` é a única responsável** por gerar e persistir `squareDeliveryId` e `initialRequestIds.base` **no INSERT da campanha** (`input_snapshot.jointResumeContext`). O orquestrador apenas lê; nunca persiste nem gera. `initialRequestIds.base` serve **somente à primeira abertura/ação inicial**; novas continuações/tentativas autorizadas usam um `requestId` novo do corpo, preservado apenas no reenvio daquela mesma requisição. **Não existe ID inicial de expansão.**
2. **`processing` encerra a resposta:** o terminal do stream é `result | error | unknown | processing`. `processing` fecha o stream e informa `operationTerminal:false`; não inventa resultado.
3. **Limites:** no máximo **1 ação de `resumeJointOperation`** e **1 etapa paga** por invocação. A abertura não é ação de resume. `initialRequestIds.base` é usado somente na **primeira abertura/ação inicial**; POST inicial repetido é read-only. Cada nova continuação/tentativa usa um `requestId` novo, e o mesmo `requestId` só se repete no reenvio daquela mesma requisição. `attemptReference` é por invocação; alvo é derivado da autoridade persistida.
4. **Replay não é operação nova:** a rota lê a autoridade durável **antes de preflight/abertura**; operação existente usa seleção congelada, não reserva, não relê configuração atual e funciona mesmo com flag OFF/configuração indisponível.
5. **Ordem de rota:** classificação persistida **antes** do schema específico na `continue`; a `generation-status` ganha o ramo conjunto **read-only**. Same-origin/auth/ownership preservados.
6. **Guards:** o novo composition root entra na allowlist por **pares exatos**, com teste negativo de caminho não registrado. Nenhum prefixo novo.

## 1. Contratos de entrada e saída

### 1.1 Geração — `NewFlowGenerateImageRequestSchema`

Em `src/lib/image-generation/schema.ts`:

- `campaignFormat: z.enum(["1:1", "9:16", "1:1+9:16"]).optional()`.
- `1:1` e `9:16` individuais permanecem inalterados.

- O body **não** aceita `squareDeliveryId`, `initialRequestIds`, `requestId`, listas ou campos extras.

### 1.2 Continuidade — `ContinueTwoFormatRequestSchema`

Novo schema estrito (mesmo arquivo):

```ts
{ operationId: UUID, requestId: UUID }
```

- Uma única ação por requisição; sem conteúdo do navegador; sem `campaignFormat`; sem identidades financeiras.
- `requestId` é o ID da **nova tentativa/continuação**. O cliente deve reenviar o **mesmo** `requestId` ao repetir a mesma requisição (replay); para uma nova tentativa autorizada, usa um **novo** `requestId`.
- O servidor nunca reutiliza `initialRequestIds` em continuações nem aceita `squareDeliveryId` no corpo.
- `ContinueGenerationRequestSchema` existente (9:16) permanece intacto.

### 1.3 Status read-only — contrato

`POST /api/campaign/generation-status` recebe o `GenerationStatusRequestSchema` existente (`campaignId`, `operationId`). Quando a origem persistida é `two_format_two_stage`, responde **sem efeitos**:

```ts
{
  operation: {
    origin: "two_format_two_stage",
    campaignId: string,
    operationId: string,
    formats: {
      "1:1": { state: "delivered|processing|absent|unknown|unavailable", deliveryOperationId: string | null },
      "9:16": { state: "delivered|processing|absent|unknown|unavailable", deliveryOperationId: string | null }

    canContinue: boolean,
    operationTerminal: boolean
  }
}
```

- Sem provider, reserva, RPC mutável ou URL assinada.
- Origem 9:16 e 1:1 continuam com os contratos atuais.

## 2. Identidade durável e concorrência

### 2.1 Forma persistida

`joint-resume-context.ts` define e valida:

```ts
input_snapshot.jointResumeContext = {
  squareDeliveryId: UUID,
  initialRequestIds: {
    base: UUID
  }
}
```

- `squareDeliveryId` e `initialRequestIds.base` são **distintos**; `squareDeliveryId !== operationId`.
- `initialRequestIds.base` pertence **somente à primeira abertura/ação inicial**. Não é ID fixo da etapa para sempre e **não existe ID inicial de expansão**.
- A chave fica **fora do hash de conteúdo**, como `resumeContext`; `computeFrozenContentHash` e as comparações de replay devem excluí-la.
- O contexto é criado **somente no INSERT da campanha**. Nunca há `UPDATE` dessa chave.

### 2.2 Responsável único e CAS

**Responsável: rota `generate-image`.** O orquestrador recebe o contexto já persistido e é somente leitura.

Ordem:
1. calcular o contexto com UUIDs novos;
2. `createCampaign` com o snapshot contendo `jointResumeContext` (INSERT é o CAS da identidade);
3. se o INSERT falhar por corrida, **reler** a campanha vencedora, validar loja/conteúdo e **usar o contexto vencedor**; nunca sobrescrever;
4. somente depois abrir a operação no orquestrador.

- Duas submissões concorrentes da mesma campanha: uma vence; a outra relê e reutiliza `squareDeliveryId`/`initialRequestIds` vencedores.
- Falha entre INSERT e abertura: a campanha existe com o contexto; retry/reload lê o mesmo contexto e chama abertura idempotente. Nenhum novo ID.
- Operação existente com contexto ausente/divergente do vínculo: **falha fechada** (`operation_identity_conflict`), sem abrir/reservar/adotar.
- Campanha existente sem `jointResumeContext` não inicia joint; não há backfill silencioso.

### 2.3 Aquisição, replay e retry

- **`squareDeliveryId`** é a identidade financeira estável do quadrado; nunca muda.
- **Primeira abertura:** usa `initialRequestIds.base` para a ação inicial `run_base`. **POST inicial repetido com operação existente é read-only e não usa esse ID.**
- **Continuação/tentativa autorizada:** usa o `requestId` do corpo. Um **novo** `requestId` é obrigatório para uma nova tentativa/fallback/retry; o **mesmo** `requestId` é reenviado apenas no replay daquela mesma requisição.
- **Não existe `initialRequestIds.expansion`**; expansão sempre exige continuação explícita com `requestId` novo. IDs fixos por etapa não podem bloquear retry legítimo.
- `settle_square`/`repair_only` não usam acquisition ID.
- `attemptReference` é gerado por invocação via `deps.callIdFactory()` (não persistido, não compartilhado entre etapas).
- `attemptTarget` é derivado da autoridade persistida (`view.nextAction`/alvo de retry) por helper puro; nunca inventado pela rota.
- Testes negativos cobrem: replay com mesmo `requestId` = `query_only` sem gasto; falha transitória + novo `requestId` = nova aquisição permitida pela autoridade; uso indevido de `initialRequestIds` em continuação = recusa.

## 3. Ordem de chamadas nas rotas

### 3.1 `generate-image`

1. `requireSameOrigin` → `requireApiUser` → `requireOwnership` (a loja é a do body/campanha).
2. Parse estrito do body (sem efeitos).
3. Ler a campanha por `campaignId` e validar o binding campanha↔loja.

**A. Campanha INEXISTENTE (não é campanha legada):**
4. Validar o pedido conjunto (contrato/declaração) e a flag vertical.
5. Flag OFF ⇒ **erro de indisponibilidade/nova submissão** **antes de criar campanha/contexto, preflight, reserva ou provider**; sem `processing`/`suspended`.
6. Flag ON ⇒ `preflightJointSelection`; construir no servidor o snapshot conjunto + `jointResumeContext` (`squareDeliveryId`, `initialRequestIds.base`); `createCampaign` INSERT (CAS).
7. Se o INSERT perder a corrida, **reler** a campanha vencedora e seguir o ramo “campanha existente”; nunca sobrescrever o contexto.
8. Abrir a operação (se ainda não existir) e executar **uma** ação inicial (`run_base`) com `initialRequestIds.base`; responder terminal/`processing`.

**B. Campanha EXISTENTE:**
9. **Classificar o snapshot persistido com `classifyTwoFormatCampaign` antes de `resolveCampaignFormat`/`resolveCampaignGenerationOrigin`:**
   - `two_format` → exige body `campaignFormat:"1:1+9:16"` + declaração conjunta; divergência ⇒ conflito, **nunca** individual;
   - `inconsistent` → conflito/erro sem efeitos, **nunca** reinterpretar como 1:1/9:16;
   - `not_two_format` → body conjunto ⇒ conflito; caso contrário, segue o caminho individual existente.
10. Ler a autoridade durável antes de qualquer preflight/abertura: `jointResumeContext` e operação conjunta (`getOperationView`/vínculos).
11. **Se a operação conjunta existe (POST inicial repetido):**
    - é **replay read-only**: **não** chama `resumeJointOperation`, **não** adquire, **não** consome `initialRequestIds`, **não** reserva, **não** chama preflight/provider;
    - retorna `result`/`processing`/`unknown`/`error` conforme o estado persistido; `processing` pode indicar `nextStep:"expansion"` com `canContinue:true`;
    - a nova etapa paga exige **continuação explícita** com `requestId` novo;
    - funciona com flag OFF/configuração atual indisponível.
12. **Se a operação não existe:**
    - se a campanha já existe sem `jointResumeContext` ⇒ conflito, sem efeitos;
    - se flag OFF ⇒ **erro de indisponibilidade** antes de preflight/reserva/provider; sem `processing`/`suspended` e sem promessa de retomada;
    - caso contrário, preflight (`preflightJointSelection`), abrir e executar **uma** ação inicial (`run_base`) com `initialRequestIds.base`; responder terminal/`processing`.

**Regra:** `processing`/`suspended` só existe para **operação existente**. Operação ausente + flag OFF retorna erro de nova submissão indisponível, sem reserva e sem `canContinue`. **POST inicial com operação existente nunca autoriza etapa paga.**

### 3.2 `continue`

1. `requireSameOrigin` → `requireApiUser` → `getCampaign` → `requireOwnership`.
2. **Classificar a origem persistida primeiro com `classifyTwoFormatCampaign`:**
   - `two_format` → ramo conjunto;
   - `inconsistent` → conflito/erro sem efeitos, nunca individual;
   - `not_two_format` → aí sim usar `resolveCampaignGenerationOrigin` para 9:16/1:1.
   **Não** chamar `resolveCampaignGenerationOrigin` antes: ele retorna `indeterminate` para a origem conjunta.
3. Só então escolher o schema:
   - `two_format` → `ContinueTwoFormatRequestSchema`;
   - `two_stage_9_16` → `ContinueGenerationRequestSchema` atual;
   - outra origem → conflito/erro sem efeitos.
4. Ler `jointResumeContext` + autoridade da operação; validar `requestId`/identidade.
5. Executar **uma** ação de `resumeJointOperation`; sem conteúdo novo; sem reserva/abertura.
6. Terminal/`processing`; flag OFF só bloqueia etapa paga de operação existente; nunca consulta/download/reparo.

### 3.3 `generation-status`

1. Same-origin/auth/ownership.
2. Parse do schema de status.
3. **Classificar com `classifyTwoFormatCampaign` antes do resolvedor legado:**
   - `two_format` → ramo conjunto read-only;
   - `inconsistent` → erro/conflito, nunca individual;
   - `not_two_format` → resolvedor legado 9:16/1:1.
4. Origem conjunta → leitura read-only (`readTwoFormatDelivery` + view/status); retornar o contrato §1.3.
5. 9:16/1:1 mantêm o comportamento atual; nenhum desses ramos chama provider/RPC mutável.

## 5. Eventos: terminal da resposta × desfecho da operação

`two-format-events.ts` define:

- `phase`; `processing`; `result`; `error`; `unknown`.
- Todo evento terminal tem `responseTerminal: true` e `operationTerminal: boolean`.
- **`processing` é terminal da resposta e `operationTerminal:false`:** o stream fecha, `nextStep`/`canContinue`/`formats` informam o que falta; nenhum `result` é inventado.
- `result`/`error`/`unknown` também fecham a resposta; `operationTerminal` reflete o desfecho real (entregue/parcial/estornado/indeterminado).
- Exatamente um terminal por stream; fases `running` são fechadas; exceção não tratada vira `unknown` seguro.

`two-format-stream.ts` reutiliza o padrão do stream 9:16 (NDJSON, `Cache-Control: no-store`, um terminal).

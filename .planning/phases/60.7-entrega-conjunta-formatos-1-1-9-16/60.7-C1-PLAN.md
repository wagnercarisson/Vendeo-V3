## 2. Contratos exatos

### 2.1 Request de geração — `NewFlowGenerateImageRequestSchema`

Em `src/lib/image-generation/schema.ts`:

- `campaignFormat` passa a `z.enum(["1:1", "9:16", "1:1+9:16"]).optional()`.
- `1:1` e `9:16` individuais permanecem com o mesmo comportamento e campos.
- `1:1+9:16` exige o contrato conjunto persistido no snapshot:
  - `campaignFormat: "1:1+9:16"`
  - `formatContractVersion: "f60.7-two-format-v1"`
  - `generationOrigin: "two_format_two_stage"`
  - `generationContractVersion: "f60.7-two-format-v1"`
- O corpo **não** aceita `squareDeliveryId`, listas de formatos ou campos extras; schema estrito.
- `campaignId` e `operationId` continuam vindo do formulário como identidades de controle; `operationId` é a identidade do vertical.

### 2.2 Continuidade — `ContinueTwoFormatRequestSchema`

Novo schema estrito em `src/lib/image-generation/schema.ts`:

```ts
{ operationId: UUID, requestId: UUID }
```

- **Uma ação por requisição** (o executor de B executa no máximo uma etapa).
- Sem conteúdo do navegador, sem `campaignFormat` no corpo, sem `squareDeliveryId`.
- `ContinueGenerationRequestSchema` existente (9:16) permanece **intacto**.

### 2.3 Eventos NDJSON — `two-format-events.ts`

Novo contrato discriminado, reutilizando o envelope existente (`campaignId`, `operationId`):

- `phase`: `phase` (`square_base`, `square_delivery`, `vertical_preparation`, `vertical_expansion`, `vertical_delivery`, `projection`) + `status` (`running|complete|failed|skipped`) + `message?`.
- `processing`: `state`, `nextStep` (`base|expansion|delivery|square_delivery|none`), `canContinue`, `formats` (`1:1`/`9:16` com estado `delivered|processing|absent|unknown|unavailable`), `preferredFormat`.
- `result`: `campaignUrl`, `formats`, `preferredFormat`, `partial` (boolean).
- `error`: `code`, `message`, `format?`, `refunded?`.
- `unknown`: `reference` (sem prometer sucesso).
- **Exatamente um terminal** por stream (`result|error|unknown`); fases `running` são fechadas no terminal; exceção não tratada vira `unknown` seguro.

### 2.4 Identidade `squareDeliveryId`

Novo `joint-resume-context.ts`:

- `squareDeliveryId` é gerado **uma única vez no servidor** (UUID) e persistido no snapshot da campanha em chave **fora do hash de conteúdo**:
  `input_snapshot.jointResumeContext = { squareDeliveryId }`.
- `computeFrozenContentHash` e as comparações de replay **ignoram** `jointResumeContext` (assim como já ignoram `resumeContext`).
- Em replay/reload/continue: ler o valor persistido; **nunca** gerar outro, **nunca** aceitar do navegador.
- Se a operação conjunta já existe e o valor persistido está ausente/divergente do vínculo do banco ⇒ falhar fechado (`operation_identity_conflict`), sem abrir nova identidade.
- Campanha existente sem `jointResumeContext` **não** pode iniciar operação conjunta; retorna conflito/indisponível sem efeitos.

## 3. Composição de runtime

### 3.1 Novo orquestrador `run-two-format.ts`

Responsabilidades:

- entrada `RunTwoFormatInput`:
  - `mode: "new" | "continue"`;
  - `storeId`, `campaignId`, `operationId`, `authorization`;
  - `requestId` (continue) / `requestStartedAtMs`;
  - `allowNewPaidStep` (flag);
  - `deadlineAtMs`, `signal?`.
- **new:** valida snapshot conjunto; executa `preflightJointSelection` antes de qualquer efeito; gera/persiste `squareDeliveryId`; chama `openJointOperation`; entra no sequenciador.
- **continue:** lê `jointResumeContext`; não aceita conteúdo; chama `resumeJointOperation` em **uma ação por requisição**.
- Sequenciador limitado (máximo de passos e deadline; sem loop infinito):
  1. `run_base` → `runJointBase`; fase `square_base`;
  2. `settle_square` → `deliverJointSquare`; fase `square_delivery`;
  3. `run_vertical_only` → `deliverTwoFormatVertical`; fases `vertical_preparation`/`vertical_expansion`/`vertical_delivery`;
  4. `repair_only` → `repairJointProjection`; fase `projection`;
  5. falha definitiva/parcial → `finalizeJointFailure`; mapear `partial`/`refunded`/`blocked` para `result`/`error` sem duplicar efeito;
  6. `blocked`/`processing` → `processing` ou terminal seguro, conforme o motivo (nunca “sucesso”).
- Terminais: `result` quando ambos entregues ou parcial conforme contrato; `error` para falha definitiva/estorno; `unknown` para indeterminação/exceção. Sem terminal duplicado.
- Nenhuma escrita direta em crédito/outcome; efeito somente pelas RPCs/clientes existentes.

### 3.2 Composição `run-two-format-deps.ts`

Compor com as fábricas/classes existentes, **mesmo `SupabaseClient`** injetado; nunca `supabaseAdmin` global quando um client é fornecido:

- `createJointDeps({ client })` → base, probes, crédito, `jointClient`, `preflight`, `generateThumbnail`;
- `createNineSixteenDeps({ client })` → `prepare`, `expand`, `resume`, `reconstruction` e passos reais;
- `ProductTwoStageOperationClient` → `getOperationView` e `finish`/`recordOutcome` quando necessário;
- `ProductOneToOneCreditOperationClient` → `beginPublication`/`abortPublication`/`getPublicationEpoch`;
- `ProductOneToOneAttemptStartClient` → outcome próprio do quadrado quando aplicável;
- `readTwoFormatDelivery` → leitura por formato;
- `finalizeJointFailure` deps → finish/outcome/probes/epoch/refund/read statuses usando os mesmos clientes.

**Regra:** nenhuma rota monta dependências à mão; `run-two-format-deps.ts` é o único composition root de C1. Nenhuma chamada global em teste com client injetado.

## Pattern Assignments

### Format and origin contracts

**Analogs:** `src/lib/campaign/format-resolution.ts`, `src/lib/product-9-16-two-stage/orchestration/origin.ts`

- Keep pure, no `server-only`, no Supabase/Next.
- In A, define the joint resolution in a dedicated module that delegates every non-joint snapshot to the existing resolver; do **not** edit the shared resolver or add a new union case in A. The shared resolver integration is C.
- Reject malformed, missing, unknown and incoherent pairs; no fallback to 1:1.
- `generationOrigin: "two_format_two_stage"` is a new origin kind; existing `two_stage_9_16`, `historical` and `indeterminate` remain unchanged.
- Tests must assert 1:1 snapshot remains byte-compatible and 9:16 individual still resolves with `f59-vertical-9-16-v1`.

### Request schema

**Analog:** `src/lib/image-generation/schema.ts`

- In A, define an unconnected strict joint declaration schema in `product-two-format/request-contract.ts`; do **not** extend the production `NewFlowGenerateImageRequestSchema` in A. That extension and dispatch are C.
- Do not accept list/array formats, arbitrary multi-format strings or fields like `campaignFormats`.
- Keep the legacy schema unchanged; it must reject joint/format fields.
- Add a strict test that production schemas still reject the joint value in A and that `1:1`/`9:16` remain unchanged; C will add the positive production-schema test.

### Financial/read contracts

**Analogs:** `src/lib/product-9-16-two-stage/types.ts`, `src/lib/product-1-1/credit-operation/types.ts`

- Define per-format delivery identities and the two-credit operation envelope.
- Keep `amount = 1` per financial row; never define a single `amount: 2`.
- Define the read-model state union exactly: `delivered | processing | absent | unknown | unavailable`.
- Include `creditRefunded`, support reference, artifact path/role and preferred thumbnail source as typed fields.
- Pure derivation from credit status + artifact row; no I/O in the state derivation.
- No inference from `storagePath`, object presence or filename.
- A per-format credit/artifact read failure yields `unknown` for that format only; the other delivered format stays visible. Campaign/link failure is top-level `read_failed`.

### Access and thumbnail eligibility

**Analogs:** `src/lib/product-9-16-two-stage/orchestration/vertical-access.ts`, `src/lib/campaign/composition-artifacts/role-policy.ts`, `src/lib/campaign/thumbnail/thumbnail-path.ts`

- Contract preview/download uses the original artifact; thumbnail uses a derived path.
- `square_original` (1024×1024, `1:1`, JPEG) is the only square artifact granted delivery/thumbnail eligibility.
- `square_prepared` (1152×1152) is not deliverable and not thumbnail-eligible for delivery.
- `vertical` remains 1080×1920, `9:16`, JPEG.
- Extend `deriveThumbnailPath`/eligibility only for the canonical composition path `{storeId}/{campaignId}/{operationId}/square_original.jpg`; no fallback to the original.
- Keep authorization identity (store/campaign/operation/role) explicit; no path from client.

### RPC clients

**Analogs:** `two-stage-operation-client.ts`, `credit-operation-client.ts`

- Server-only, client injectable, no global client hidden in pure contracts.
- Parse envelopes with closed unions and typed errors; reject missing/extra identity.
- Methods should map directly to the four RPCs: open joint delivery, deliver format, refund format, project campaign.
- Do not call `markArtUploaded`/`deliver` separately in the joint client; the deliver-format RPC wraps them.
- The client accepts the publication token after the canonical artifact is persisted/verified; it does not upload.
- Idempotent replay and terminal/unknown statuses are represented explicitly.
- Open replay validates the returned frozen selection against the requested selection (`operation_config_conflict` on divergence); it never reads current catalog/config.
- Joint RPCs acquire the campaign lock before link/credit locks; projection reads both deliveries under that common lock.

### Migration/RPCs

**Analogs:** F60 control migration, F60.6 v2 migration, F56.2b1a credit migration.

- Forward-only, authored with real UTC timestamp and uniqueness check; not applied.
- New table `product_two_format_deliveries` with FK to the control operation, unique `(campaign_id, operation_id, format)`, unique `delivery_operation_id`, role/format checks, RLS service-only read.
- `service_role` gets only `SELECT`; writes exclusively through SECURITY DEFINER RPCs.
- Open RPC reuses `product_9_16_open_operation_v2`, creates both links and reserves the second credit in one transaction.
- Deliver/refund RPCs operate per `delivery_operation_id`; projection is in the same transaction.
- Projection prefers `square_original`, falls back to `vertical`, preserves `ready`, and never updates `render_snapshot`/copy/approval.
- No changes to existing RPC bodies, `amount = 1`, artifact tables, flags or pricing.
- Static SQL tests assert the above; they do not prove PostgreSQL transactions/concurrency (Gate de banco later).

### Tests

- Pure tests: no `server-only`, no Supabase/Next/Sharp imports.
- Client tests: fake Supabase client and RPC envelopes; assert error mapping, missing fields, identity mismatch, idempotent replay and terminal/unknown behavior.
- Static migration tests: read the SQL file as text and assert object names, constraints, grants, `amount = 1` unchanged, no destructive DDL/DML, no `DROP TABLE`, and no accidental application steps.
- Preservation tests: existing format/origin suites and 1:1/9:16 individual contracts remain green.

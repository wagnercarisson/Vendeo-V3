# PLANO: Feedback Visível no Onboarding — Overlay de Feedback Crítico

## 1. Diagnóstico Breve dos Pontos Atuais no Código

### O Problema

O `StoreIdentityForm` renderiza **todos os feedbacks como banners inline no topo do formulário** (linhas 1128-1157):

| Variável | Tipo | Renderizado em | Problema |
|----------|------|----------------|----------|
| `warningMessage` | hook | linha 1128 (topo) | Some ao scrollar |
| `error` (hook) | hook | linha 1138 (topo) | **Some ao scrollar — crítico** |
| `successMessage` (step 1) | hook | linha 1145 (topo) | **Some ao scrollar — crítico** (mitigado por `scrollTo(0,0)` na linha 441-445, mas desorientador) |
| `step2Success` | local state | linha 1152 (topo) | **Some ao scrollar — crítico** (mitigado por `scrollTo(0,0)` na linha 447-451) |
| `formError` | local state | linha 1547 (próximo ao botão submit) | Parcialmente visível |
| `acceptedTermsError` | local state | linha 1539 (inline checkbox) | OK (inline) |
| `billingError` | local state | linha 1645 (inline billing) | OK (inline) |

### Fluxo do Problema

1. Usuário preenche Step 1 (formulário longo: CNPJ, nome, segmento, cidade/estado, direção marketing, aceite legal, billing)
2. **Scrollea até o final** para clicar "Salvar"
3. Se ocorre **erro de API** → `error` é setado no hook → inline banner renderiza na **linha 1138** — **fora da viewport**
4. Se ocorre **sucesso** → `successMessage` é setado → inline na **linha 1145** — idem; o `scrollTo(0,0)` joga o usuário pro topo, mas é desorientador

**O mesmo problema ocorre no Step 2:** `step2Success` (linha 1152), `driftError`, `logoError` e falhas de salvar/realinhar aparecem em regiões que podem ficar fora da viewport se o usuário estiver interagindo com áreas mais abaixo do formulário de direção visual.

### Mitigações Existentes

- `useEffect` com `scrollTo({ top: 0 })` para `successMessage` (linha 441) e `step2Success` (linha 447)
- **Não existe** solução equivalente para `error` — o usuário simplesmente não vê o erro

### Padrão Visual Existente

O projeto usa `fixed inset-0 z-50 flex items-center justify-center bg-black/60` para modais (DriftDecisionModal, DriftCriticalModal, VisualSignatureApprovalModal, etc.) com container `bg-bg-surface border border-border rounded-xl`. **Não há** sistema de toast instalado (sonner, react-hot-toast, etc.).

## 2. Proposta de UX Escolhida e Alternativas Consideradas

### Proposta Escolhida: FeedbackOverlay — Abordagem Híbrida (Erro Bloqueante + Sucesso Não Bloqueante)

Criar um componente `FeedbackOverlay` com dois modos de operação, evitando fricção desnecessária:

| Modo | Tipo | Comportamento | ARIA |
|------|------|---------------|------|
| **Bloqueante** | `error` | Overlay modal centralizado (`fixed inset-0 z-50 bg-black/60`) — bloqueia interação até dismiss | `role="alertdialog"` + `aria-modal="true"` |
| **Não bloqueante** | `success` | Banner fixo no topo da viewport (`fixed top-16 left-1/2 -translate-x-1/2 z-40`) sem backdrop — não bloqueia interação | `role="status"` + `aria-live="polite"` |

**Características do modo erro:**
- Aparece imediatamente após `error`, `formError` ou qualquer falha de persistência/API pós-ação
- Fundo escuro semi-transparente (`bg-black/60`), centralizado
- Ícone `AlertCircle` vermelho + mensagem clara
- Botão "Fechar" + backdrop click + Escape para dismiss
- Focus trap + **salva e restaura** `document.activeElement` ao abrir/fechar

**Características do modo sucesso:**
- Aparece como banner fixo no topo da viewport (sempre visível, não bloqueante)
- Ícone `CheckCircle2` verde + mensagem
- Auto-dismiss após 5s **ou** clique no X para fechar
- Não bloqueia — usuário pode continuar interagindo com o formulário
- Transição suave (opacity)

**Gatilhos híbridos:**
- **Erro de API / readiness / validação pós-submit** → modo bloqueante (`alertdialog`)
- **Sucesso de save / direção visual salva** → modo não bloqueante (banner fixo)
- **Redirect (`router.push`)** → não mostra feedback local; o redirect em si é o feedback (usuário vê a página destino). Alternativa via query param se necessário no futuro.

### Alternativas Consideradas e Rejeitadas

| Alternativa | Motivo da Rejeição |
|-------------|-------------------|
| **Toast system (sonner/react-hot-toast)** | Nova dependência; provider wrapping; não segue padrão visual existente; quebra consistência |
| **Modal bloqueante para tudo** | Cria fricção desnecessária em sucessos simples ("Loja salva..." não merece clique extra) |
| **Apenas scrollTo para erro também** | Já existe para sucesso (desorientador); não resolve visibilidade (usuário pode ignorar) |
| **Snackbar inferior (fixed bottom)** | Novo padrão visual que não existe no app; inconsistente |

### Por que a abordagem híbrida é a melhor escolha:
1. **Erro: blocking garante atenção** — impossível de ignorar, crítico para erros de API/readiness
2. **Sucesso: não bloqueante evita fricção** — usuário vê a confirmação sem perder contexto
3. **ARIA correta** — `alertdialog` para erro (interrompe), `status` + `aria-live` para sucesso (anuncia sem interromper)
4. **Focus return** — salva activeElement ao abrir, restaura ao fechar (acessibilidade real)
5. **Surgical** — não requer refatoração do StoreIdentityForm (2458 linhas), adiciona ~100 linhas de componente + ~40 linhas de integração

### Task 1: Criar componente FeedbackOverlay

**Arquivo:** `src/components/flow/feedback-overlay.tsx` (novo)

**Props:**
```tsx
type FeedbackOverlayProps = {
  message: string | null;
  type: 'error' | 'success';
  onDismiss: () => void;
};
```

**Responsabilidade:**

**Modo erro (`type="error"`):**
- Renderizar overlay modal bloqueante quando `message` não for null
- ARIA: `role="alertdialog"`, `aria-modal="true"`, `aria-label="Erro"`
- Usar classes Tailwind idênticas aos modais existentes:
  - Overlay: `fixed inset-0 z-50 flex items-center justify-center bg-black/60`
  - Card: `bg-bg-surface border border-border rounded-xl shadow-2xl w-full max-w-md mx-4 p-6`
  - Ícone: `AlertCircle w-8 h-8 text-accent-red` (erro)

  - Botão: `min-h-[44px] px-4 py-2 ... font-heading font-semibold text-sm rounded-lg`
- Comportamentos:
  - Escape key → `onDismiss`
  - Backdrop click → `onDismiss` (com `onPointerDown` + `e.stopPropagation` no card)
  - Focus trap: autoFocus no botão "Fechar"
  - **Focus return:** salvar `document.activeElement` ao montar, restaurar ao desmontar

**Modo sucesso (`type="success"`):**
- Renderizar banner fixo **não bloqueante** no topo da viewport
- ARIA: `role="status"`, `aria-live="polite"`
- Posicionamento: `fixed top-16 left-1/2 -translate-x-1/2 z-40` (top-16 para offset visual abaixo da topbar; z-40 para ficar abaixo de z-50 de modais bloqueantes — o banner success não deve sobrepor alertdialog ou ApprovalModal)
- Estilo: fundo verde (`bg-green-900/20 border border-green-700/30 rounded-lg`), padding, ícone `CheckCircle2`
- Comportamentos:
  - Auto-dismiss após 5s (via `useEffect` com `setTimeout`)
  - Botão X para fechar imediatamente
  - **Sem backdrop** — não bloqueia interação com o formulário
  - Transição: opacity simples via estado local

**Estado compartilhado:**
- `message === null` → renderiza `null` (ambos os modos)
- `onDismiss` limpa o estado no pai

**Não fazer:**
- ❌ Não adicionar animação complexa (manter simples)
- ❌ Não adicionar suporte a `warning` type (apenas error/success)

const handleStep2Submit = async (e: React.FormEvent) => {

### Task 3: Remover scrollTo Effects Obsoletos

**Arquivo:** `src/components/flow/store-identity-form.tsx`

- Remover o `useEffect` de `successMessage → scrollTo` (linhas 441-445)
- Remover o `useEffect` de `step2Success → scrollTo` (linhas 447-451)

**Justificativa:** O FeedbackOverlay é fixo na viewport por definição. O modo `error` usa `fixed inset-0`, o modo `success` usa `fixed top-16`. Ambos são visíveis independente da posição de scroll. O `scrollTo(0,0)` se torna desnecessário e desorientador.

## 7. Riscos e Cuidados

| Risco | Impacto | Mitigação |
|-------|---------|-----------|
| **FeedbackOverlay aparece em momentos não pós-ação** | Médio | Eliminado pela mudança para disparo direto nos handlers. Apenas `error` do hook usa useEffect como safety net — e `error` só muda durante `save()` no hook. |
| **Ciclo infinito de feedback** (erro → overlay → fecha → erro resseta → reabre) | Alto | Mitigado: o hook resseta `error` no início de `save()` (linha 192). O overlay é controlado por estado separado (`feedbackOverlay`), então o dismiss não interage com o ciclo de save. |
| **StoreIdentityForm é enorme (2458 linhas)** — risco de edição causar conflito | Alto | Foco cirúrgico: adicionar import + estado + handler + JSX no final. Não reorganizar, não refatorar, não tocar nos banners inline. Revisar diff linha a linha. |
| **Remover scrollTo effects quebra UX de outros fluxos** | Médio | Verificar que os `scrollTo(0,0)` (linhas 441-451) só são usados para feedback. Confirmar que o overlay substitui completamente a necessidade. |
| **Focus return não implementado** — usuário perde contexto ao fechar modal | Médio | FeedbackOverlay no modo `error` deve salvar `document.activeElement` no mount e restaurar no unmount (via `useEffect` cleanup). |
| **Banner success z-index conflita com modais** | Médio | Topbar não é fixed, então não há conflito com ela. Mas banner `z-40` fica abaixo de modais `z-50` — se um modal abrir enquanto banner está visível, o banner some atrás do backdrop. Isso é aceitável porque modais são sempre mais prioritários. Testar coexistência: sucesso Step 1 + DriftCriticalModal ao salvar Step 2. |
| **FeedbackOverlay e inline banners mostram mesma mensagem** → duplicação visual | Baixo (aceitável) | Overlay/bloqueante aparece primeiro (visibilidade imediata). Ao fechar, banners inline no topo servem como referência posterior. É intencional. |
| **Sucesso com redirect** (`router.push` na linha 967) perde feedback | Baixo | O redirect em si é o feedback — o usuário vê a página destino (dashboard). Não há mensagem importante a mostrar. Se necessário no futuro, usar query param (`?onboarding=complete`) + flash message na página destino. |

### Observação sobre `formError`

O `formError` é setado em dois contextos:
- **Linha 934:** `setFormError("Verifique os campos obrigatórios")` — validação pré-submit no `handleStep1Submit`. Com a abordagem revisada, o overlay é disparado **diretamente no handler**, então o timing é preciso: ocorre após clique em Salvar, que é o comportamento desejado.
- **Linha 957:** `setFormError("Os dados fiscais não foram salvos...")` — pós-submit readiness. Também disparado diretamente no handler, com overlay correto.

Com a abordagem handler-based, não há risco de overlay aparecer fora do contexto de submit, ao contrário do useEffect global.

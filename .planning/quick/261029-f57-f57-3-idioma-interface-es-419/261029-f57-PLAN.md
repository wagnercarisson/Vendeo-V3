```ts
/** Idiomas da interface do aplicativo. Independente do conteúdo/campanha. */
export const SUPPORTED_UI_LOCALES = Object.freeze(["pt-BR", "es-419"] as const);
export type SupportedUiLocale = (typeof SUPPORTED_UI_LOCALES)[number];
```

Alterar apenas os tipos de UI:

- `UserLocalePreference.uiLocale: SupportedUiLocale`
- `UserLocaleResolution.uiLocale: SupportedUiLocale`

Manter `SUPPORTED_CONTENT_LOCALES = ["pt-BR", "es-PY"]` e `SupportedContentLocale` **intactos**.
Corrigir o comentário atual “Idiomas de conteúdo/aplicativo suportados” para explicitar que ele
cobre **somente conteúdo**.

Em `validation.ts`, adicionar `isSupportedUiLocale` usando `SUPPORTED_UI_LOCALES`; manter
`isSupportedLocale` como guard de conteúdo.

Em `user-preference.ts`, trocar o guard de `isSupportedLocale` para `isSupportedUiLocale` e o tipo
local `SupportedContentLocale` para `SupportedUiLocale`. A regra de legado continua resolvendo
`pt-BR` com fonte `legacy_br`; entrada mista continua falhando; país/mercado continuam ignorados.

Em `index.ts`, exportar `SUPPORTED_UI_LOCALES`, `SupportedUiLocale` e `isSupportedUiLocale`.

### 1.2 Consumidores da interface

- `dtos.ts`: `UserLocalePreferenceDTO.uiLocale: SupportedUiLocale`; `assertSupportedUiLocale`
  passa a usar `isSupportedUiLocale`. O DTO de loja continua com `SupportedContentLocale`.

  e a variável interna `uiLocale` idem. Leitura/escrita/CAS permanecem iguais.

- Nenhuma alteração em `store-market-settings-service.ts`, `dtos.ts` (parte de loja),
  `/api/store/market-settings`, perfis `BR`/`PY`, onboarding ou fiscal.

### 1.3 Preservações explícitas

- `null` continua limpando a escolha (`ui_locale = NULL`, fonte `legacy_br`, versão +1).
- `uiLocale` omitido continua apenas validando a versão, sem materializar linha e sem RPC.
- `expectedVersion` continua obrigatório; conflito continua `409` com versão vigente.
- Valor fora do contrato continua `400`, sem escrita.
- Leitura sem linha continua `pt-BR`/`legacy_br`/versão 0.
- Par incoerente persistido continua `500 stored_preferences_invalid`.

## 2. Migration nova (pontual)

Nome: `supabase/migrations/YYYYMMDDHHmmss_f57_3_ui_locale_es_419.sql`, com timestamp UTC real
(horas/minutos/segundos) gerado **no momento da execução**, conforme
`docs/fluxo-de-desenvolvimento.md`. Antes de criar, conferir unicidade do prefixo na worktree, na
branch de integração e nas branches paralelas conhecidas; se colidir, gerar outro timestamp.

Conteúdo planejado, **tudo em uma única transação** (uma migration = uma unidade atômica, sem
`COMMIT` intermediário). Se qualquer passo falhar — incluindo a adição da nova constraint — a
transação inteira é revertida e nenhum valor fica convertido. A ordem é obrigatória:

1. `ALTER TABLE public.user_preferences DROP CONSTRAINT IF EXISTS chk_user_preferences_ui_locale;`
2. Converter somente `public.user_preferences`, **apenas os registros efetivamente convertidos**:
   ```sql
   UPDATE public.user_preferences
      SET ui_locale = 'es-419',
          version = version + 1
    WHERE ui_locale = 'es-PY';
   ```
   - `version + 1` só ocorre nas linhas atingidas pelo `UPDATE`; as demais não têm versão,
     fonte nem timestamps alterados.
   - `ui_locale_source` permanece `explicit`.
   - `created_at` não é tocado; `updated_at` é atualizado pelo trigger existente
     `trg_user_preferences_updated_at`.
   - `version + 1` mantém o CAS honesto: clientes com versão antiga recebem `409` em vez de
     sobrescrever a conversão.
   - Nenhuma outra tabela é tocada; nenhum registro é apagado.
3. Recriar a constraint:
   ```sql
   ALTER TABLE public.user_preferences
     ADD CONSTRAINT chk_user_preferences_ui_locale
     CHECK (ui_locale IS NULL OR ui_locale IN ('pt-BR', 'es-419'));
   ```
   A constraint só é adicionada depois da conversão; se existir valor inesperado, a migration
   falha fechada e nada é mascarado.
4. `CREATE OR REPLACE FUNCTION public.write_user_locale_preference(...)` com **assinatura idêntica**
   `(p_user_id UUID, p_ui_locale TEXT, p_expected_version BIGINT)`, `SECURITY DEFINER`,
   `SET search_path = ''`, e **somente** a linha de validação alterada:
   ```sql
   IF p_ui_locale IS NOT NULL AND p_ui_locale NOT IN ('pt-BR', 'es-419') THEN
   ```
   Preservar literalmente: checagem de usuário existente, derivação de fonte
   (`NULL` → `legacy_br`, valor → `explicit`), insert com versão temporária 1 + delete e
   `preferences_version_conflict` com `HINT/DETAIL = '0'` quando `expectedVersion ≠ 0` na primeira
   escrita, `FOR UPDATE`, conflito com versão vigente, update de `ui_locale`/fonte/versão,
   `RETURN to_jsonb(v_pref)`.
5. Reemitir `REVOKE ALL ... FROM PUBLIC, anon, authenticated` e
   `GRANT EXECUTE ... TO service_role` para a mesma assinatura (idempotente).
6. Atualizar comentários de tabela/coluna que citam `pt-BR`/`es-PY` como idioma do app.
7. Incluir bloco `-- REVERT` comentado, sem executar, seguindo **a mesma ordem atômica** da
   aplicação, em transação única e sem apagar registros:
   - dropar a constraint nova `chk_user_preferences_ui_locale`;
   - converter de volta `es-419 → es-PY` em `user_preferences` (apenas linhas afetadas,
     `version + 1`, `updated_at` pelo trigger, `created_at` preservado);
   - **depois** recriar a constraint antiga `CHECK (ui_locale IS NULL OR ui_locale IN ('pt-BR', 'es-PY'))`;
   - restaurar a RPC da migration `20261028145738`.

   Recriar a constraint antiga antes da conversão é inválido (os valores `es-419` ainda
   existiriam); o bloco deve refletir explicitamente a ordem acima.

**Não alterar:** `store_market_settings`, `chk_store_market_settings_locale`, as quatro RPCs de
onboarding/fiscal, `admin_create_store_for_user`, RLS/policies, grants de tabela, triggers de loja.

**Observação de janela:** código antigo lê `es-419` como inválido (`500`) e rejeita escrita
`es-419`. Código novo escreve `es-419` e falha contra a constraint antiga. Migration e deploy
devem ocorrer na mesma janela controlada; não promover um lado sozinho.
